# 从零开发售后数据分析系统

一家生鲜电商发现售后处理变慢了。老板想知道问题有多严重，售后主管想知道慢在哪个环节。是某类问题处理更复杂，某个团队积压增加，还是订单在等待客户或物流反馈？要回答这些问题，得先定指标口径，再把指标落实到数据模型、同步任务、API 和看板上。系统上线后，还要能判断数据是否可信，遇到故障时能恢复。

这次学习以 **Aftersales Analytics 售后数据分析系统**为贯穿案例。起点是已有后端和数据处理经验，希望独立开发一套完整系统。最初拟了十课大纲，实际学习从售后业务需求逐步推进到生产运维，第九课转入项目初始化。对话中的订单、指标数字和发布故障均为教学案例。

## 课程速览

以下概览保留各章的主要设计取舍。

## 第一课　认识数据分析系统

课程最初设想做一个电商经营看板，覆盖销售、售后、客服和异常分析。案例逐渐收敛到售后，是因为它可以用一条具体的业务过程串起整个系统。客户发起申请，客服首次响应，订单可能转交、等待外部反馈，最后解决或关闭。每一步都能产生数据，也都可能成为指标出错的地方。

从一笔售后单往下看，订单系统提供交易上下文，售后系统提供申请与状态，客服系统记录处理过程。数据处理层统一主键、状态和时间字段，再生成适合查询的明细与汇总。FastAPI 提供统一查询接口，React 和 ECharts 把结果展示给业务用户。业务人员可以从总览发现异常，按团队、类型或环节缩小范围，最后核对订单明细并安排处理。这条使用路径决定了后续要收集哪些数据、做哪些页面。

## 第二课　把售后问题写成需求和指标

实战从一句话开始：“发现问题，定位原因，如何改善。”它把产品目标落实到了管理动作。老板或管理层通过总览掌握规模、效率和风险，售后主管频繁使用看板排查问题、协调资源，一线客服则需要看到可处理的明细。需求文档要写清楚每类人要做的决定，以及他们可以访问的数据范围。

假设平均解决时长上涨，先确认变化出现在哪些日期、哪些问题类型，再按团队、物流等维度对比。即使物流公司 B 的平均反馈时间最长，也要查看具体订单和处理过程，核对是否有少数极端值，比较的是否是同类订单，等待是否集中在某个环节。维度下钻缩小范围，明细和过程记录用来验证原因。对照组、样本量和订单构成都会影响结论。

在效率题里，首响时长、解决时长和 SLA 超时率分别回答三个问题：客服多快开始响应，客户从申请到解决等了多久，有多少订单超过承诺时限。实战中曾选择只统计客服实际处理时间，以便更公平地评价客服。讲评把时间拆成三个指标：**端到端解决时长、客服实际处理时长、外部等待时长**。客户体验看完整历时，绩效分析看实际处理用时，流程改进可以进一步追踪等待客户或物流的时间。外部等待是否暂停 SLA，需要按业务规则明确。

首页设计从全局概况出发。需求阶段选择了售后订单量、平均解决时长、售后超时率和客户投诉量，分别覆盖规模、效率、承诺履行与客户反馈。总览页用 KPI、趋势和异常入口帮助用户决定下一步查什么，再进入团队、问题类型或订单明细。第九课首轮开发使用了更小的 KPI 集合，服务于第一条数据链路。

| 指标 | 时间口径和适用场景 |
| --- | --- |
| 售后申请量 | 按申请时间计入，反映这一时期新增的售后需求。 |
| 平均首次响应时长 | 以首次有效响应时间减申请时间，明确有效响应的定义和未响应样本的处理。 |
| 解决量与平均解决时长 | 按解决时间归属，衡量这一时期实际完成的处理结果。若要跟踪某天新建订单的后续解决表现，按创建批次对同一批订单跟踪。 |
| SLA 超时率 | 明确适用订单、评估时点、截止时间、暂停规则、分子和分母。服务时限与订单业务状态分别记录。 |
| 客户投诉量 | 明确何为一次有效投诉、按哪个时间计入，以及同一售后单发生多次投诉时怎样去重。 |

SLA 练习给出三笔教学订单，判断结果是 A001 超时、A002 未超时、A003 超时。已解决的订单可能已经违约，尚未解决的订单也可能仍在时限内。以解决 SLA 为例，已解决订单比较解决时间与截止时间，未解决订单以评估时点核对截止时间。需要约定的还包括时区、截止时点是否包含边界、哪些类型走不同规则、规则版本怎样追溯。整节课逐步形成 PRD V1.0 草稿，把用户、页面、指标字典、数据来源、更新频率和验收规则放到了同一份需求依据中。

## 第三课　用事实表记录业务，用维度保留历史

项目数据规模和维护成本支持先使用 MySQL。课程讲了 ODS、DWD、DWS、ADS 四层职责。第一版保留 **ODS 原始层 → DWD 标准明细层 → ADS 应用层**，需要在多个场景复用中间汇总时，再评估是否单设 DWS。ODS 保留来源与批次以便追查，DWD 统一明细与业务主键，ADS 提供固定粒度和口径的日汇总。架构选择同时考虑业务时效、查询复杂度和团队维护能力。

建表先回答“这一行代表什么”。售后订单事实表一张售后单一行，记录申请、当前状态、首次响应和解决等信息。事件事实表每个处理事件一行，记录发生时点、操作与操作者。客服分配历史表每段负责关系一行，用生效和结束时间表达订单在某阶段由谁负责。团队、客服、问题类型、物流商和 SLA 规则等维度，为事实提供可筛选的业务属性。ER 图、建表 SQL 和索引都要以这些粒度为基础。

课程用两笔单演示 JOIN 扇出。A001 用了 100 分钟，A002 用了 20 分钟，按订单计算平均是 60 分钟。如果关联事件后，A001 出现两次，直接求平均会得到约 73.33 分钟。实战回答识别出了重复风险，讲评进一步区分了笛卡尔积和有连接条件的一对多扇出。需要按订单聚合的指标应在订单粒度计算，或者先将事件聚合到订单粒度，再关联。

另一个例子是客服后来调到新团队。使用当前团队字段回查历史，会改变过去的业绩归属。SCD Type 2 用多个版本记录同一客服的团队变化，事实加载时根据业务发生时点定位有效版本，保留对应的维度版本键，并检查有效区间是否重叠或缺失。客服的组织归属历史和订单的分配历史分别记录，后者还能处理同一订单在不同客服或团队间转交的情况。

团队接手量、参与处理量、最终解决量和负责时长各有自己的事件与计算粒度。一次转交可能让两支团队都参与，但按最终解决口径只记给解决该单的团队。团队日汇总以日期和团队为粒度，参与量跨团队相加后可能重复计入同一售后单。数据库收官题中，发现订单和事件重复时，先阻断受影响的汇总发布，再修复源头或去重逻辑、重算、复核。数据库评审因此同时涵盖粒度、主键、历史归属、SLA 口径和发布版本。

## 第四课　让 ETL 可以重跑、续跑和补数

Python 与 SQLAlchemy 负责抽取、标准化和写入 MySQL。售后单会持续更新，所以增量同步以源系统更新时间查找变更，用售后业务主键做幂等写入，并把上一次成功处理的位置记入 `etl_sync_checkpoint`。同一时间戳可能有多笔记录，按 `(updated_at, aftersales_id)` 排序的复合游标可以稳定分页。源端与目标端分别记录批次或版本，历史状态变化也能进入后续统计。

假设每批 1,000 条，前两批已提交，第三批失败。恢复程序读取最后成功提交的检查点，从第三批继续。目标写入与检查点推进需处于同一个目标库事务里。事务失败时，两者同时撤销，重跑仍靠幂等写入防止重复。如果已经提交但任务在确认成功前断开，也必须能安全处理重复投递。Celery Worker 执行任务，Celery Beat 触发周期调度，Redis 可以承担消息代理。对可重试的临时错误做退避，持续失败和数据规则错误进入排查流程，并避免同一同步任务并发推进游标。

收官题进一步区分了记录的更新时间和事务提交可见时间。某笔单标记在 10:00 更新，数据库到 10:05 才提交，期间游标可能已越过 10:00。复合游标解决的是同一时点的排序，迟到记录还需要用**回看窗口、幂等写入和定期对账**补偿。高一致性需求可以再评估 CDC。补数既可以重跑指定时段，也可以针对单号补同步，随后重算受影响的历史汇总。

验收需要验证断点续跑、事务回滚、重复执行、迟到更新与历史补数。运行日志记录批次、起止游标、读取和写入量、异常量、耗时和失败原因。监控关注最近成功时间、数据延迟、任务失败和积压，让运营侧知道看板数据更新到了哪里。

## 第五课　把 FastAPI 做成稳定的数据契约

实战把接口称为“数据交接面”。以 `GET /api/v1/aftersales/overview` 为例，接口契约规定日期参数、可用筛选、响应字段、错误语义，以及指标适用的业务范围。用 Pydantic 校验类型和边界，用约定的时区与日期区间查询。总览、趋势和团队排名优先查匹配粒度的 ADS 汇总，明细核对按需读 DWD。平均值或比率跨日汇总时，应保存可合并的分子、分母或合计与样本数，再按查询范围重算。

权限实战把问题拆成三步。JWT 验证身份，RBAC 判断能否使用某项功能，数据范围控制决定能看哪些团队。前端传来的 `team_id` 表明查询意图，服务端按当前授权计算范围，并在数据库查询时强制应用。即使 JWT 仍有效，团队授权撤销后也应按系统约定拒绝访问。权限缓存需要与撤销的生效要求匹配，可用版本校验和主动失效，必要时回源验证。没有任何授权团队的用户应得到空范围，服务端只有确认用户具备全量权限时才查询全部团队。

项目划分为 Router、Service 和 Repository。Router 处理 HTTP 和参数，Service 负责业务规则和授权，Repository 执行已限定范围的查询。遇到慢接口，先确认 ADS 可覆盖查询口径，再检查组合索引和执行计划，最后评估缓存价值。接口验收覆盖合法与非法日期、越权团队、权限撤销、空结果、图表与明细复核，以及典型数据量下的响应时间。

## 第六课　从 React 总览下钻到可核对的明细

看板按“先看总览，再看细节”组织。顶部日期、团队等筛选器提供统一查询上下文。KPI 卡片让人判断整体状况，趋势和分布定位异常时段与类型，团队排行帮助继续缩小范围。点击柱形或趋势点时，将选中的日期或团队带到明细；用户可清空筛选，也能看见当前查看的是哪个范围。

React 页面需要处理加载、成功、空数据和错误状态。请求发出后显示加载状态，返回空集时说明当前筛选下没有结果，失败时给出清晰提示和重试入口。若用户快速切换日期或团队，较早发出的请求有可能最后才返回。可以用 `AbortController` 取消旧请求，并检查响应是否仍属于当前请求，再更新页面。

图表和明细必须遵守同一口径。例如，团队图表若统计某天解决的订单，下钻也应按解决时间筛选，并传递相同的团队归属、状态、时间区间和数据版本。用固定样本联调，从 KPI 或趋势点一路核对到单号，验证图表聚合和明细能够对上，再测试快速切换、空结果、错误重试和越权等状态。

## 第七课　发现质量问题后，控制哪些指标可以发布

源系统有 10,000 笔、目标系统有 9,850 笔，课程用这组模拟数字说明了对账的第一步。先应用相同业务口径，再检查源和目标的业务主键是否重复，双向比对缺失与多余记录，抽查状态、归属和关键时间。若 150 笔是按规则排除的测试单，差异有业务解释。若是游标遗漏、过滤错误、去重错误或维度关联失败，则需要暂停相关结果的发布并修复。也要核对 DWD 明细聚合到 ADS 后有没有漏算或重算。

质量规则覆盖完整性、唯一性、准确性、一致性、合法性和时效性。每一条规则记录检查口径、阈值和严重程度，运行结果保留批次与异常数量。团队映射失败的记录应保留原始值和错误原因，进入隔离区。修正映射后按批次复检，避免把本来无法归属的订单记到一个默认团队。

不同指标有不同依赖。负的解决时长会影响平均解决时长，团队关联失败会影响团队排行。其他指标是否受影响，要检查它们各自使用的输入和规则。生成候选 ADS 版本后，先执行质量校验，再按指标或需要一致性的指标组原子切换当前版本指针。通过的指标发布新版本，失败的指标保留上一个可信版本，并显示数据截至时间和状态。共享分子分母、需要对应下钻或必须相互对账的指标应绑定同一发布版本。

告警带上日期、批次、规则和影响指标，并按事件去重。负责人定位根因，完成修复、补算和重新校验，恢复发布后记录处理经过。质量看板可以追踪数据延迟、规则通过率、异常批次、阻断指标、恢复耗时和发布成功率。

## 第八课　部署、自动发布和生产回滚

生产方案用 Docker Compose 组织 Web、FastAPI、MySQL、Redis 和后台任务。MySQL 使用命名卷存储数据。常规删除或重建容器时，可以重新挂载同一卷；显式删除卷则会移除其中数据。备份要单独保留，并用恢复演练验证可用性。

React 构建为静态文件，由 Nginx 提供。同一 HTTPS 域名下，浏览器用相对路径 `/api` 访问后端，Nginx 将请求转发到内部 FastAPI 服务。这避免了 HTTPS 页面调用 HTTP API 的混合内容问题，也统一了浏览器访问入口。配置时要核对 `/api` 前缀是否保留、React 路由刷新时的回退规则、证书申请和续期。MySQL、Redis 与应用内部端口留在相应网络内，生产配置和凭据通过部署环境管理。

发布流程由 GitHub Actions 运行前后端检查和测试，构建镜像并推送到 GHCR。镜像用提交 SHA 标识，也可记录 digest，以便复现某次部署。服务器通过受控的 SSH 部署流程拉取镜像，用 Alembic 执行数据库迁移，更新 Compose 服务，再检查前端、API 和关键业务指标。发布记录应保留当前和上一稳定版本、迁移版本以及健康检查结果。部署要避免并发，并区分迁移失败、应用启动失败和业务指标异常。

回滚练习里，V42 发布后页面能打开，售后总量也正常，但平均解决时长算错了。先暂停继续发布，检查数据库迁移后 V41 能否运行。兼容时，可切回 V41 应用镜像，保留生产数据库，重新核对指标和服务状态。若 V42 已经错误写入历史数据，则进一步确定受影响批次，按需做补偿、重算或数据恢复。数据库可以用 Expand/Contract 做兼容迁移：先增加新结构，维持新旧应用兼容，切换并观察稳定后，再删除废弃结构。

上线验收覆盖五个方面。**功能**检查登录、筛选、联动和下钻；**数据**以独立复算核对核心指标；**安全**验证 HTTPS、权限和网络边界；**稳定性**检查负载、容器重启和任务恢复；**可恢复性**实测应用回滚和数据库恢复。Runbook 应明确 API 不可用、MySQL 连接失败、ETL 中断、指标错误、磁盘不足和发布失败时的排查与恢复路径。监控关注 API 延迟与错误率、资源使用、任务状态、数据新鲜度和备份恢复能力。课上出现的 99.5% 可用性、24 小时 RPO 和 4 小时 RTO 是用于讨论的目标示例，实际目标按业务可容忍的停机与数据损失确定。

## 第九课　初始化 Aftersales Analytics V1

第九课把设计转成一个可从头开发的项目。V1 服务于售后主管和管理层，回答业务整体怎么样、哪些团队或客服的处理效率有问题、问题集中在哪里，以及哪些问题应优先改善。MVP 包含 Excel 或 CSV 导入、Python 清洗去重和增量处理、MySQL 存储、FastAPI 查询、React 与 ECharts 看板、质量检查，以及 Docker Compose、Nginx 和 GitHub Actions 部署。复杂 AI 分析、实时同步和多租户留到后续迭代。

GitHub 仓库采用 Monorepo。课程给出了使用 `uv` 初始化 Python 后端和用 Vite 初始化 React + TypeScript 前端的步骤。后端先装 FastAPI、Uvicorn、SQLAlchemy、PyMySQL、Alembic 与配置依赖，开发检查使用 Pytest、HTTPX 和 Ruff。前端使用 Axios 与 ECharts。Celery 和 Redis 随异步任务阶段引入。Git 忽略环境文件、私钥、构建产物和本地依赖目录，提交示例配置即可。

```text
aftersales-analytics/
├── frontend/           React、TypeScript、ECharts
├── backend/            FastAPI、数据处理、质量检查、Alembic、测试
├── deploy/             Docker Compose、Nginx、生产部署配置
├── docs/               PRD、架构、数据库设计、Runbook
└── .github/workflows/  自动检查与发布
```

第一个业务闭环是 **CSV → Python ETL → MySQL → FastAPI → React 售后总览**。最小数据集包含售后单号、订单编号、申请时间、首次响应时间、解决时间、团队、状态和 SLA 截止时间。后续有团队工作量分析需求时，再用转交事件或团队归属历史回溯。正式模型还需要约定时区、状态流转、部分解决与重新打开的处理方式。

第一版总览示意包含申请量、解决量、解决率和 SLA 超时率，MVP 的指标范围还包含平均解决时长。验收这条链路时，可以用一份能手工复算的样本，逐项核对 CSV、数据库、API 和页面，并测试重复导入。解决率要明确分子和分母属于哪个订单集合，避免将某天完成的历史积压直接除以当天新增单量。

原对话停在第一轮迭代选择题。题目比较先做完整前端、先打通一条端到端链路、先铺完整后端和先做全量数据库建模四种安排。按照课程设定的首个业务闭环，端到端方案能优先验收一组可追溯的 KPI。实际仓库的创建、编码、部署和验收都是这个设计之后的工程工作。
