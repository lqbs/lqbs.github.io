## Java 后端 {#javabe}

本章收录 35 篇面经（Java 面经 01–27，其中 5 篇正文为图片无法提取；计算机基础面经 28–35），涉及阿里灵犀、阿里 ICBU、小红书、CVTE、用友、字节跳动、宜信、快手、众安保险、蚂蚁集团、美团、七牛云、百度、京东、虾皮及若干中小公司。高频考点集中在：Java 并发（线程池、synchronized 与 ReentrantLock、CAS、volatile、ThreadLocal）、JVM（内存区域、GC 算法与 CMS、类加载与双亲委派、Full GC 排查）、MySQL（B+ 树索引、事务与 MVCC、三大日志、分库分表）、Redis（持久化、缓存一致性、三大问题、分布式锁）、消息队列（RabbitMQ、Kafka）、Spring（IOC、AOP、事务、注解）、操作系统与网络（进程线程、握手挥手、拥塞控制）；手撕题以 LRU、链表、二叉树类为主。

### 阿里灵犀 · Java 后端 {#javabe-01-alilingxi}

作者：Bao；原文未注明轮次，只记了有特点的题，普通八股未记。

- B 树、B- 树、B+ 树的优劣及各自使用场景

- 消息丢失全链路：发送 confirm → broker 持久化 → 消费者 ack → 未收到 ack 重发如何保证幂等 → 唯一 ID 生成方式（要点：uuid、雪花、数据库自增、美团 Leaf）
- AQS 用了什么设计模式；获取互斥量对应操作系统的什么（PV 原语）；AQS 互斥量如何表示（volatile 的 state）
- 大 key 怎么解决（要点：监测调用耗时、scan 扫描 bigkey、拆分大 string 为 hash、大链表做散列）
- 慢查询怎么解决（要点：慢查询日志、explain 分析、上缓存、换 ES、优化索引、分库分表）
- JDK 最高版本和新特性（当时稳定版为 17）
- 分库分表分片键不同时怎么保证事务（实际考察分布式事务方案）
- MAC 地址在交换机还是路由器，工作在哪一层
- Docker 的优点和缺点
- 手撕：大于等于目标的二分、小于目标的二分、阻塞队列

原文总结：一面难度不高，面试官对着简历的技术和项目逐行提问。

- 锁：乐观锁与悲观锁（要点：乐观锁不加锁、更新时判断是否被改，实现为 CAS 或版本号机制；悲观锁直接锁数据；竞争不激烈用乐观锁，激烈用悲观锁）
- CAS 的问题（要点：ABA 问题可用版本号解决，如 AtomicStampedReference；高竞争下自旋开销大；只能保证单变量原子性）
- 典型锁（要点：互斥锁属 sleep-waiting、涉及上下文切换；条件变量用于等待、常与互斥锁配合；自旋锁属 busy-waiting、适用短临界区但占 CPU；读写锁允许多读、写互斥）
- 死锁相关问题（要点：四个必要条件为互斥、不剥夺、占有并等待、循环等待；解决可统一上锁顺序；处理方法有鸵鸟策略、检测与恢复、预防破坏四条件、避免（安全状态））
- 拥塞控制：四种拥塞算法（要点：慢开始指数增长、拥塞避免加法增长、快重传收到 3 个重复 ACK 立即重传、快恢复 cwnd 设为 ssthresh 后继续；判断拥塞的依据是超时重传）

### 面经 32 · 计算机基础 {#javabe-32}

作者：壮；问题汇总加分类答案。

- union 和 join 的区别（要点：union 操作两个或多个记录集、对应列需相同、合并去重；join 操作两个或多个表、是集合叉积的子集）
- 三次握手的流程（要点：B 处于 LISTEN，A 发 SYN=1、seq=x，B 回 SYN=1、ACK=1、ack=x+1、seq=y，A 再回 ack=y+1；SYN 不携带数据但消耗一个序号；socket 编程中客户端 connect() 触发三次握手）
- 三次握手的原因（要点：防止失效连接请求浪费服务端资源；三次是双方确认收发正常的最小值；本质是同步双方初始序列号）
- 三次握手是否可携带数据（要点：第三次可以，此时客户端已确认服务端收发能力正常；前两次不可以，否则易被 SYN 攻击利用）

### 面经 33 · 计算机基础 {#javabe-33}

作者：壮；主题为分库与分表，附答案。

- 分库（要点：解决单机资源限制下的高并发访问，一般按业务划分；带来的事务问题需分布式事务，跨库无法 JOIN，可通过业务代码关联或冗余字段解决）
- 分表（要点：解决单表数据量过大查询慢，大致三四千万行需拆分）
- 垂直分表（要点：按列拆分，把大字段、不常用字段拆到附表，一页存放更多行、减少磁盘访问）
- 水平分表（要点：按行拆分，数据越多 B+ 树越高、性能越差）
- 分表带来的问题（要点：排序、count、分页需业务代码或中间件汇总，count 结果可缓存；路由问题；全局主键可用自增步长、UUID（不连续导致页分裂）、雪花算法或 Redis 递增）

- 异步（要点：调用后可继续执行后续操作，通过状态轮询、通知、回调告知调用者）
- 同步与异步的区别：请求发出后是否需要等待结果才能继续执行其他操作

### 面经 36 · C++ 后端（公司未注明） {#cppbe-36-summary}
作者「壮」，按知识分类整理的八股汇总。

**计算机网络**
- 三次握手最后一次 ACK 丢失会怎样。要点：服务端停在 SYN_RECV，按 3s/6s/12s 超时重传 SYN+ACK，重发指定次数后自动关闭连接；客户端认为连接已建立，发数据会收到 RST。
- 四次挥手流程。要点：A 发 FIN 停止发送、B 回 ACK 进入半关闭、B 发 FIN、A 回 ACK 并进入 TIME-WAIT 等待 2MSL 后释放。
- 为什么需要四次握手。要点：服务器收到 FIN 后可能还有数据要传，ACK 和 FIN 一般分开发送，因此多一次。

**数据库（MySQL 三大日志）**
- 重做日志（redo log）。要点：物理格式日志、记录数据页修改，保证持久性与崩溃恢复；事务执行过程中即开始写入；checkpoint 与 write_pos 循环推进，写满时触发刷盘腾空间。
- 二进制日志（binlog）。要点：逻辑格式、服务层日志，记录所有更新操作的 SQL；事务提交时一次性写入；用于主从同步和基于时间点的还原。
- 回滚日志（undo log）。要点：逻辑格式，保存事务前的数据版本，用于回滚与 MVCC 的非锁定读；事务提交后由 purge 线程判断能否清理。
