而且，这次你已经开始关注软件系统中非常重要的一类问题：**业务流程中的状态变化和资源一致性。**

订单和库存不是两个独立模块。

它们之间存在强业务依赖：

- 创建订单可能占用库存。
- 审核失败可能释放库存。
- 取消订单可能释放库存。
- 发货可能实际扣减库存。
- 并发创建订单可能造成超卖。

如果这些规则没有调研清楚，后面即使数据库设计得很好，也可能出现业务错误。

### 一、评价你的访谈思路

优秀的提问方向

你的问题有三个优点：

1. **关注完整流程**：不是只问审核功能，而是调查审核前后发生了什么。
2. **关注异常情况**：主动询问库存不足和审核失败。
3. **关注业务结果**：库存预留和释放直接关系到库存准确性。

这里我特别想强调：

很多开发人员拿到订单系统需求后，会直接设计一个 `stock` 字段，然后在订单创建时执行：

```sql
UPDATE inventory
SET stock = stock - 1
WHERE product_id = 1001;
```

但这还远远不够。

必须先明确：

- 什么时间占用库存？
- 什么时间扣减实际库存？
- 什么时间释放库存？
- 多个订单同时购买时怎么办？
- 同一订单重复审核怎么办？

这就是本轮要解决的问题。

### 三、确定订单审核规则

首先要明确：不是所有订单都应该自动通过审核。

我们先把审核规则分成三类。

#### 1. 自动审核条件

建议候选规则：

- 订单信息完整。
- 商品已经成功匹配。
- 商品数量合法。
- 金额信息通过校验。
- 没有重复订单。
- 库存满足预留要求。
- 不存在需要人工处理的业务异常。

符合规则的订单可以自动审核，但是否启用自动审核，需要运营主管确认。

#### 2. 人工审核条件

例如：

- 商品匹配存在疑问。
- 订单金额不一致。
- 商品数量异常。
- 收货信息异常。
- 订单存在特殊备注。
- 库存需要人工确认。
- 命中企业内部风险规则。

#### 3. 审核结果

| **审核结果** | **后续处理** |
| --- | --- |
| 审核通过 | 进入待发货流程 |
| 审核拒绝 | 记录原因，按规则取消或关闭订单 |
| 审核待补充 | 返回运营人员修改 |
| 库存不足 | 进入缺货处理流程 |

注意：审核拒绝、订单取消和订单关闭并不一定是同一个动作，需要分别定义状态和业务含义。

#### 4. 初步审核规则

#### 订单审核规则 V0.4

| **编号** | **规则** | **初步定义** |
| --- | --- | --- |
| AUD-001 | 审核资格 | 只有授权人员可以审核 |
| AUD-002 | 审核前置条件 | 关键订单信息校验通过 |
| AUD-003 | 审核通过 | 进入后续履约流程 |
| AUD-004 | 审核拒绝 | 必须记录拒绝原因 |
| AUD-005 | 审核记录 | 记录操作人和时间 |
| AUD-006 | 重复审核 | 同一订单不能重复执行相同审核动作 |
| AUD-007 | 审核异常 | 记录异常原因并允许授权处理 |

### 四、确定库存管理的核心概念

这是本轮最重要的知识点。

我们先区分三个库存数量。

#### 库存数量模型

实际库存 On-hand

### 100 件

仓库当前实际拥有的库存数量。

预留库存 Reserved

### 30 件

已经分配给订单，但尚未实际出库的数量。

可用库存 Available

### 70 件

目前还可以分配给新订单的数量。

可用库存=实际库存-预留库存可用库存=实际库存−预留库存

例如：

仓库实际有 100 件商品。

其中 30 件已经预留给待发货订单。

那么新订单最多只能再预留 70 件。

不能因为实际库存还有 100 件，就允许新订单再购买 100 件。

这就是库存预留机制的意义。

### 五、确定库存检查和库存预留规则

#### 1. 库存检查应该发生在什么时候？

结合运营主管的回答，我们提出一个候选方案：

**订单通过必要信息校验后，在审核通过或进入履约流程之前，执行库存预留。**

但这里存在一个需要业务确认的设计选择：

- 方案 A：订单导入后立即预留库存。
- 方案 B：订单审核通过时预留库存。
- 方案 C：仓库接单时才预留库存。

三种方案各有利弊。

| **方案** | **优点** | **风险** |
| --- | --- | --- |
| 导入后预留 | 提前锁定库存 | 未审核订单长期占用库存 |
| 审核通过时预留 | 兼顾审核和库存控制 | 审核前库存可能变化 |
| 仓库接单时预留 | 库存占用时间较短 | 订单审核后可能缺货 |

对于当前模拟业务，我建议先采用方案 B：

**审核通过时原子性地检查并预留库存，库存预留成功后才能进入待发货状态。**

这样能够避免订单尚未审核就长期占用库存。

不过，如果企业要求导入后立即保证库存，那么就需要调整预留时机，并增加预留超时机制。

#### 2. 库存预留流程

#### 库存预留业务流程

**订单审核通过请求**

**读取商品可用库存**

**判断库存是否充足**

库存充足

**预留库存**

**进入待发货**

库存不足

**预留失败**

**进入缺货处理**

#### 3. 库存预留计算

假设：

- 实际库存：100 件。
- 已预留库存：30 件。
- 新订单需要：20 件。

那么：

可用库存=100-30=70可用库存=100−30=70

因为 70 大于 20，所以可以预留。

预留之后：

| **库存项目** | **预留前** | **预留后** |
| --- | --- | --- |
| 实际库存 | 100 | 100 |
| 预留库存 | 30 | 50 |
| 可用库存 | 70 | 50 |

注意：

**预留库存不等于实际出库。**

此时商品还在仓库里，只是已经分配给订单，不能再分配给其他订单。

### 六、确定超卖防护规则

这是订单系统最重要的技术与业务结合点之一。

#### 1. 什么情况下会超卖？

假设商品只剩 10 件。

两个运营人员几乎同时处理订单：

#### 并发库存争抢场景

**当前可用库存：10 件**

**订单 A**

### 8 件

运营人员 1

**订单 B**

### 8 件

运营人员 2

潜在超卖

**两笔订单同时读取到库存 10 件**

如果都通过普通读取和更新，可能错误地预留 16 件。

所以，库存检查和库存扣减不能分成两个互不关联的操作。

#### 2. 推荐使用数据库原子更新

例如 MySQL 可以使用条件更新：

```sql
UPDATE inventory
SET reserved_quantity = reserved_quantity + 8
WHERE sku_id = 1001
  AND warehouse_id = 1
  AND (
    total_quantity - reserved_quantity
  ) >= 8;
```

然后检查受影响行数：

- 影响 1 行：库存预留成功。
- 影响 0 行：库存不足或记录不存在，需要进一步判断。

这条 SQL 的关键是：

**判断库存是否充足和增加预留库存，在同一个原子操作中完成。**

如果一次订单包含多个 SKU，还需要在同一个数据库事务中完成所有 SKU 的预留。

如果任何一个商品预留失败，就回滚整个事务，避免只预留一部分商品。

#### 3. 完整超卖防护要求

| **编号** | **规则** | **处理方式** |
| --- | --- | --- |
| INV-006 | 可用库存检查 | 实际库存减去预留库存 |
| INV-007 | 原子预留 | 条件更新，不允许先查后改 |
| INV-008 | 多商品预留 | 使用数据库事务 |
| INV-009 | 并发处理 | 保证库存不会被重复占用 |
| INV-010 | 重复审核 | 同一订单只能成功预留一次 |
| INV-011 | 库存不足 | 拒绝预留，记录失败原因 |
| INV-012 | 库存流水 | 每次库存变化都记录来源和数量 |

还要考虑数据库事务隔离、锁等待和死锁处理。对于多 SKU 订单，建议按固定 SKU 顺序获取锁，减少死锁风险。

#### 4. 库存不变量

以后你设计任何库存系统，都应该检查这几个条件：

可用库存=实际库存-预留库存可用库存=实际库存−预留库存

实际库存 ≥ 0实际库存≥0

预留库存 ≥ 0预留库存≥0

预留库存 ≤ 实际库存预留库存≤实际库存

这些是系统必须持续满足的业务约束。

### 七、确定库存释放和发货扣减规则

现在我们处理另一个核心问题。

订单预留库存后，如果订单取消了，库存怎么办？

#### 1. 订单取消

例如：

- 订单 A 预留 8 件。
- 客户要求取消。
- 订单尚未发货。

那么：

- 预留库存减少 8 件。
- 可用库存增加 8 件。
- 实际库存不变。

| **库存项目** | **取消前** | **取消后** |
| --- | --- | --- |
| 实际库存 | 100 | 100 |
| 预留库存 | 50 | 42 |
| 可用库存 | 50 | 58 |

#### 2. 订单发货

订单真正出库时：

- 实际库存减少。
- 预留库存减少。
- 可用库存保持不变。

例如发货 8 件：

| **库存项目** | **发货前** | **发货后** |
| --- | --- | --- |
| 实际库存 | 100 | 92 |
| 预留库存 | 50 | 42 |
| 可用库存 | 50 | 50 |

这意味着：

预留阶段只占用库存，发货阶段才真正减少实际库存。

#### 3. 库存变化规则总表

| **业务事件** | **实际库存** | **预留库存** | **可用库存** |
| --- | --- | --- | --- |
| 新增库存 20 | +20 | 0 | +20 |
| 预留库存 8 | 0 | +8 | -8 |
| 取消订单释放 8 | 0 | -8 | +8 |
| 发货出库 8 | -8 | -8 | 0 |
| 退货验收入库 8 | +8 | 0 | +8 |

这里有一个特别容易犯的错误：

**发货时不能只减少实际库存，而忘记减少预留库存。**

否则库存数量就会出现不一致。

#### 4. 库存操作必须有流水

每次库存变化都需要记录：

| **字段** | **示例** |
| --- | --- |
| SKU | SKU1001 |
| 业务类型 | ORDER\_RESERVE |
| 业务编号 | ORDER001 |
| 数量变化 | +8 预留 |
| 操作人 | SYSTEM |
| 操作时间 | 2026-11-20 |
| 操作原因 | 订单审核通过 |

建议库存流水记录实际库存和预留库存各自的变化量，而不只是记录一个模糊的数量。

### 八、形成正式库存与订单审核业务规则 V0.4

我们把本轮访谈整理成项目文档。

**订单管理系统 · 库存与审核规则**

V0.4

**一、订单审核**

- 订单审核前必须通过必要的信息校验。
- 只有授权用户可以执行人工审核。
- 审核通过后进入库存预留流程。
- 审核拒绝必须记录原因。
- 审核操作必须支持幂等控制。

**二、库存模型**

- 实际库存：仓库当前持有数量。
- 预留库存：已经分配给订单的数量。
- 可用库存：实际库存减去预留库存。

**三、库存预留**

- 暂定在订单审核通过时执行。
- 库存检查与预留必须原子执行。
- 多商品订单必须在一个事务内完成预留。
- 库存不足时禁止进入正常待发货流程。

**四、超卖防护**

- 使用数据库原子条件更新。
- 使用事务保证多 SKU 预留一致性。
- 同一订单不得重复预留。
- 并发操作不得突破可用库存。
- 所有库存变化必须记录流水。

**五、库存释放**

- 未发货订单取消时释放预留库存。
- 审核拒绝时，根据是否已预留库存决定是否释放。
- 释放操作必须具备幂等性。
- 已发货订单不能通过普通取消操作释放库存。

**六、发货扣减**

- 发货确认时扣减实际库存。
- 同时减少对应预留库存。
- 发货失败时根据实际出库情况处理库存。
- 同一订单不能重复扣减库存。

| FR-020 | 订单审核 |
| FR-021 | 自动审核规则 |
| FR-022 | 库存查询 |
| FR-023 | 库存预留 |
| FR-024 | 库存不足处理 |
| FR-025 | 超卖防护 |
| FR-026 | 订单取消库存释放 |
| FR-027 | 发货库存扣减 |
| FR-028 | 库存流水查询 |
| FR-029 | 库存异常预警 |

**七、尚待业务确认**

1. 审核通过时预留库存是否符合实际业务。
2. 库存不足是否允许部分发货。
3. 库存预留是否设置超时时间。
4. 取消订单是否需要主管审批。
5. 已发货订单发生退货时的入库规则。

### 十、本轮学习总结

你今天学到的最重要的东西，不只是库存计算，而是一个完整的业务思维：

**业务动作 → 状态变化 → 数据变化 → 异常处理 → 操作记录。**

例如订单取消：

1. 业务动作：客户申请取消。
2. 状态变化：订单从待发货变成已取消。
3. 数据变化：预留库存减少。
4. 异常处理：如果库存释放失败，需要重试或人工处理。
5. 操作记录：记录取消人、取消时间和库存释放结果。

这套思维后面可以直接用于：

- 数据库设计。
- FastAPI 业务服务设计。
