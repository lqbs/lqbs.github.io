你选择 A：

> 能不能结合你日常经营决策，告诉我最需要关注哪些指标？每个指标如何计算、多久查看一次、发现异常后需要采取什么行动？

这是本轮最合适的访谈问题。

而且，你已经开始从操作层面的需求调研，转向管理层面的需求调研。

前六轮主要回答：

- 订单如何进入系统？
- 订单如何创建？
- 如何审核？
- 如何管理库存？
- 如何发货？
- 出现异常如何处理？

第七轮要回答：

**系统上线以后，老板如何知道业务运行得好不好？**

### 一、评价你的访谈思路

优秀

你的问题包含四个重要维度。

| **维度** | **你提出的问题** | **对应设计成果** |
| --- | --- | --- |
| 指标 | 关注哪些数据？ | KPI 指标体系 |
| 计算 | 指标如何计算？ | 指标口径 |
| 周期 | 多久查看一次？ | 日报、周报、月报 |
| 行动 | 发现异常怎么办？ | 预警与运营流程 |

这比单纯问「老板想看什么报表」专业得多。

因为老板真正需要的不是一张漂亮的大屏，而是通过数据发现问题、判断原因、采取行动。

这里引入一个产品设计的重要原则：

**指标必须能够支持业务决策。**

例如：

老板看到今天有 1,000 笔订单，这个数字本身不一定有价值。

但如果发现：

- 订单量比昨天增加 30%。
- 发货及时率下降 15%。
- 库存异常增加 20%。

这些信息就可以帮助老板判断是否需要增加仓库人手、调整采购计划或者处理积压订单。

### 二、模拟老板回答

现在进入模拟访谈。

**老板 · 经营决策者**

模拟回答

「我每天最关心几件事情：

第一，今天有多少订单？销售额是多少？跟昨天相比怎么样？

第二，订单处理得快不快？有多少订单还没有审核？有多少订单积压在仓库？

第三，发货及时不及时？有没有漏发、错发？

第四，库存准不准确？有没有商品库存不足或者库存异常？

第五，售后退款和订单异常多不多？哪些问题一直没有解决？

第六，我想知道每个运营人员每天处理了多少订单，平均处理时间是多少。

我希望每天早上能看到一份经营日报，每周能看到一次运营分析。

如果订单积压、发货延迟或者库存不足，希望系统能够及时提醒。」

这段回答可以提炼出六个经营管理方向：

1. 订单规模。
2. 订单处理效率。
3. 发货履约质量。
4. 库存健康度。
5. 售后与异常管理。
6. 人员工作效率。

现在我们逐个确定指标。

### 三、设计订单运营 KPI 指标体系

首先需要理解：

KPI 不应该只是指标名称，还必须明确计算方式、统计范围和使用场景。

我建议把指标分成六个主题。

#### 1. 订单规模指标

| **指标** | **计算口径** | **统计周期** |
| --- | --- | --- |
| 订单总数 | 统计周期内创建的有效订单数 | 日/周/月 |
| 销售商品金额 | 订单商品金额合计 | 日/周/月 |
| 买家实付金额 | 订单买家实际支付金额合计 | 日/周/月 |
| 取消订单数 | 统计周期内取消的订单数 | 日/周/月 |
| 订单取消率 | 取消订单数 ÷ 订单数 | 日/周/月 |

这里要注意：

订单总数应该明确统计创建时间还是支付时间。

销售额也要明确是商品原价、优惠后金额还是买家实付金额。

否则不同报表之间可能出现数字不一致。

#### 2. 订单处理效率指标

| **指标** | **计算口径** | **业务意义** |
| --- | --- | --- |
| 平均审核时长 | 审核完成时间 - 订单进入审核时间 | 衡量审核效率 |
| 待审核订单数 | 当前待审核订单数量 | 发现审核积压 |
| 平均拣货时长 | 拣货完成时间 - 拣货开始时间 | 衡量仓库效率 |
| 待发货订单数 | 当前尚未完成发货的订单数量 | 发现仓库积压 |
| 订单处理完成率 | 完成处理订单数 ÷ 进入处理订单数 | 衡量处理能力 |

建议特别关注 P95 处理时长。

因为平均值可能掩盖少数订单长时间积压的问题。

例如：

平均审核时间是 10 分钟，但仍然可能有一部分订单等待了 3 小时。

#### 3. 发货履约指标

| **指标** | **计算口径** | **业务意义** |
| --- | --- | --- |
| 发货订单数 | 统计周期内实际发货订单数 | 观察履约规模 |
| 及时发货率 | SLA 内发货订单数 ÷ 到期应发货订单数 | 衡量发货及时性 |
| 发货失败率 | 发货失败次数 ÷ 发货尝试次数 | 衡量发货稳定性 |
| 错发率 | 错发订单数 ÷ 已发货订单数 | 衡量仓库准确性 |
| 漏发率 | 漏发订单数 ÷ 已发货订单数 | 衡量履约质量 |

注意：及时发货率的分母应该是已经到达发货期限的订单，而不是所有创建订单。

否则新创建、还没到发货时间的订单会干扰统计。

#### 4. 库存健康指标

| **指标** | **计算口径** | **业务意义** |
| --- | --- | --- |
| 可用库存 | 实际库存 - 预留库存 | 判断还能接多少订单 |
| 库存不足 SKU 数 | 可用库存低于安全库存的 SKU 数 | 识别缺货风险 |
| 库存准确率 | 盘点一致 SKU 数 ÷ 已盘点 SKU 数 | 衡量账实一致性 |
| 库存预留失败率 | 预留失败订单数 ÷ 库存预留请求数 | 衡量库存供给能力 |
| 库存释放失败数 | 释放失败记录数 | 识别库存异常 |

其中库存准确率不能通过系统账面数据自行计算，必须结合实际盘点数据。

#### 5. 售后与异常指标

| **指标** | **计算口径** | **业务意义** |
| --- | --- | --- |
| 退款订单数 | 发生退款的订单数 | 观察退款规模 |
| 退款金额 | 成功退款金额合计 | 观察退款影响 |
| 异常订单数 | 当前未关闭的异常订单数 | 观察异常积压 |
| 异常解决时长 | 异常解决时间 - 异常创建时间 | 衡量处理效率 |
| 异常超时率 | 超过 SLA 未解决异常数 ÷ 到期异常数 | 识别管理风险 |

#### 6. 人员工作效率指标

| **指标** | **计算口径** |
| --- | --- |
| 人均审核订单数 | 审核订单数 ÷ 审核人员数 |
| 人均处理订单数 | 完成处理订单数 ÷ 处理人员数 |
| 人均异常处理数 | 已解决异常数 ÷ 处理人员数 |
| 个人平均审核时长 | 个人审核总耗时 ÷ 完成审核订单数 |

这里特别提醒：

人员效率指标必须结合订单复杂度、工作时段、岗位职责进行解释。

不能简单地认为处理订单最多的人就是效率最高的人。

### 四、建立指标口径管理规范

现在你已经有了一批 KPI，但还需要解决一个问题：

不同人使用同一个指标时，能否得到相同的结果？

这需要建立指标口径管理规范。

例如：

#### 指标定义卡片：订单及时发货率

核心运营指标

**指标名称**

订单及时发货率

**业务定义**

在规定发货时限内完成实际出库的订单占到期应发货订单的比例。

**计算公式**

(SLA内实际出库订单数) ÷ (到期应发货订单数) × 100%到期应发货订单数SLA内实际出库订单数​×100%

**统计周期**

每日、每周、每月。

**数据来源**

订单表、发货记录表、订单状态历史表。

**责任部门**

仓库运营部门。

**异常处理**

低于目标值时，分析待拣货、缺货、复核失败和快递交接等原因。

这就是数据分析系统中的指标口径管理。

建议所有核心指标都使用这种结构进行定义。

### 五、设置运营目标值与预警规则

有了指标，还需要明确什么情况算正常，什么情况需要处理。

注意：下面是项目初始建议目标，不是企业已经确认的经营承诺。

| **指标** | **建议初始目标** | **预警条件** |
| --- | --- | --- |
| 订单及时发货率 | ≥95% | 低于95% |
| 订单审核 P95 时长 | ≤30分钟 | 超过30分钟 |
| 库存准确率 | ≥98% | 低于98% |
| 发货错误率 | ≤0.5% | 高于0.5% |
| 异常订单超时率 | ≤5% | 高于5% |
| 库存释放失败数 | 0 | 大于0 |

建议将预警分成三个级别：

P0

**严重异常**

例如：库存负数、重复扣减库存、批量发货失败。需要立即通知负责人。

P1

**重要异常**

例如：订单大量积压、及时发货率持续下降。需要主管及时处理。

P2

**一般提醒**

例如：库存接近安全库存、少量订单处理超时。进入日常运营处理。

这里要区分业务预警和系统故障告警。

例如：

- 库存不足属于业务预警。
- MySQL 无法连接属于技术告警。
- 库存释放失败可能同时触发业务异常和技术告警。

两者需要不同的处理责任人。

### 七、确定数据权限

这部分非常容易被忽略。

老板希望查看所有经营情况，但不代表所有员工都应该看到所有数据。

建议采用 RBAC（基于角色的访问控制）。

#### 1. 数据权限矩阵

| **数据类型** | **老板** | **主管** | **运营** | **仓库** |
| --- | --- | --- | --- | --- |
| 订单列表 | 全部 | 管辖范围 | 授权订单 | 履约相关 |
| 订单金额 | 全部 | 全部或授权范围 | 按岗位授权 | 默认隐藏 |
| 客户电话 | 授权查看 | 授权查看 | 业务需要时查看 | 默认脱敏 |
| 收货地址 | 全部 | 管辖范围 | 业务需要时查看 | 履约需要时查看 |
| 库存数据 | 全部 | 全部 | 可查看 | 可查看 |
| 退款金额 | 全部 | 全部 | 按权限查看 | 默认隐藏 |
| 经营报表 | 全部 | 部门范围 | 默认不开放 | 默认不开放 |
| 操作日志 | 全部 | 授权查看 | 本人相关 | 本人相关 |

#### 2. 权限设计的三个层次

建议区分：

1. **功能权限**：能否创建订单、审核订单、取消订单。
2. **数据权限**：能看到哪些订单、哪些部门的数据。
3. **字段权限**：能否看到客户电话、金额等敏感字段。

例如：

运营人员可以处理订单，但不一定可以查看全部订单的利润数据。

仓库人员需要查看收货地址，但不一定需要看到订单的完整财务信息。

### 八、确定系统管理需求

最后还需要明确系统管理功能。

建议包括：

| **模块** | **功能** |
| --- | --- |
| 用户管理 | 用户创建、禁用、重置密码 |
| 角色管理 | 角色配置 |
| 权限管理 | 菜单、接口和数据权限 |
| 商品管理 | 商品、SKU、规格 |
| 仓库管理 | 仓库与库位 |
| 渠道管理 | 电商平台、内部系统 |
| 字典管理 | 订单状态、异常类型 |
| 操作日志 | 业务操作审计 |
| 导入管理 | 导入批次和失败记录 |
| 系统配置 | 业务参数和预警阈值 |

特别需要强调：

订单状态、异常类型等关键业务字典不能让普通用户随意修改，否则可能破坏业务规则。

- 验收标准需要证明问题是否真正解决。

这四件事不能混为一谈。

### 十一、需求调研第 8 轮：需求范围确认与 MVP 评审

现在我们进入需求调研最后一轮。

前七轮已经形成了 66 项候选功能需求。

但如果全部放进第一版，项目可能会非常庞大。

假设老板现在提出：

> 「我希望系统尽快上线，先解决订单导入、订单处理、库存管理和发货问题。经营看板、复杂的自动化和其他高级功能可以后续再做。你帮我确定第一期究竟做哪些功能。」

现在你作为项目负责人，需要进行需求范围管理。

#### 实战问题：你应该怎么做？

#### 正式需求调研第 8 轮

需求范围与 MVP

- A. 根据核心业务目标、用户痛点、业务依赖和实施成本，对需求进行优先级排序，明确第一期 MVP 范围，并与老板确认。
- B. 66 项功能全部放入第一期，保证系统功能完整。
- C. 优先开发老板最喜欢的数据大屏。
- D. 先开发技术上最容易实现的功能。

提交项目决策

### 十二、下一阶段交付目标

第八轮完成后，我们将正式结束需求调研，交付：

目标：形成可以进入系统设计阶段的需求基线

**给你一个特别重要的提醒：**

不要为了让需求文档看起来完整，就把没有经过业务确认的假设写成既定事实。

目前我们所有的运营主管、老板和仓库人员回答都是模拟业务案例。正式项目中，还需要用真实访谈、订单样本、平台字段和企业制度验证这些规则。

接下来我们要训练的，是能够区分「已经确认的需求」「合理的设计建议」和「尚待验证的假设」。

这才是从会做功能开发，成长为能够独立负责软件项目的关键一步。
