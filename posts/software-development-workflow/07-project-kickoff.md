### 一、逐题批改

#### 问题 1：项目最核心的目标是什么？

你的选择：A。

正确

提高订单处理效率、减少订单错误、实现业务流程数字化，并帮助管理者掌握运营情况。

这是正确的，因为你关注的是业务价值，而不是技术实现。

例如：

| **老板提出的问题** | **对应业务目标** |
| --- | --- |
| 人工处理订单麻烦 | 提高订单处理效率 |
| 经常出现库存错误 | 提高库存准确性 |
| 订单容易遗漏 | 提高订单处理完整性 |
| 管理者不了解业务情况 | 建立运营分析能力 |

需要进一步注意：这些是初步目标，还需要调研后确定优先级和量化目标。

#### 问题 2：项目启动后首先做什么？

你的选择：A。

正确

确认目标用户、当前业务流程、核心痛点和业务目标。

原因是：如果业务流程没有搞清楚，直接设计数据库，很可能出现数据模型与实际业务不匹配的问题。

正确顺序：

**了解业务背景**

**识别目标用户**

**调研当前流程**

**发现业务问题**

**形成需求方案**

#### 问题 3：谁是核心目标用户？

你的选择：A。

正确

订单运营人员是核心操作用户，管理者是经营决策用户。

这道题还涉及一个重要概念：用户角色（User Role）。

| **用户角色** | **主要工作** | **系统需要提供什么** |
| --- | --- | --- |
| 老板 | 查看经营情况 | 经营总览、趋势、异常 |
| 运营主管 | 管理订单处理 | 订单监控、人员管理、统计 |
| 订单运营人员 | 日常处理订单 | 查询、审核、取消、发货 |
| 仓库人员 | 处理库存与出库 | 库存查询、出库、库存流水 |
| 系统管理员 | 管理系统 | 用户、角色、权限 |

这意味着不同角色不应该拥有完全相同的操作权限和页面。

#### 2. 需求调研需要完成什么？

我们把调研拆成五项工作：

| **调研任务** | **需要得到的结果** |
| --- | --- |
| 用户调研 | 谁使用系统、各自负责什么 |

### 四、第一步：用户调研与角色分析

我们假设企业目前有以下人员：

#### 订单管理系统用户角色图

**老板**

经营决策、查看经营结果

**运营主管**

订单管理、任务分配、异常监控

**订单运营人员**

审核、处理、取消订单

**仓库人员**

库存、出库、发货

这只是初始角色假设，实际调研要确认是否有客服、财务、采购人员参与订单流程。

##### 用户调研访谈表

| **访谈对象** | **核心问题** |
| --- | --- |
| 老板 | 最希望通过系统解决什么经营问题？ |
| 运营主管 | 如何分配和监督订单任务？ |
| 订单运营 | 每天如何处理订单？最困难的是什么？ |
| 仓库人员 | 如何确认库存、出库和发货？ |

特别提醒：访谈时不要只问用户想要什么功能，还要让用户演示最近一次真实操作。

### 五、第二步：分析完整订单业务流程

现在进入本次最重要的实战内容。

一个典型的订单业务流程可能是：

#### 订单业务主流程 V0.1

**订单创建**

**订单信息校验**

**库存检查**

**库存预留**

**订单审核**

**仓库拣货与发货**

**订单完成**

但是，这只是正常业务主流程。

真实系统必须考虑异常情况。

#### 1. 订单取消

例如：

- 订单创建后，客户要求取消。
- 订单审核不通过。
- 库存不足。
- 仓库尚未发货。

这些情况可能触发不同的订单状态变化和库存释放规则。

#### 2. 库存不足

例如：

- 创建订单时库存不足。
- 库存预留失败。
- 多个订单同时抢购同一商品。
- 订单取消后库存没有正确释放。

这些都是需要明确业务规则的地方。

#### 3. 发货异常

例如：

- 仓库拣货失败。
- 发货接口调用失败。
- 物流单号重复。
- 订单已经发货，却再次提交发货操作。

这涉及状态管理、幂等性和异常处理。

#### 4. 订单流程图

上图只作为流程表达参考。真正项目的流程图必须根据访谈确认的业务规则绘制，不能直接把示意图当成需求事实。

### 六、第三步：把业务流程拆解成可分析的步骤

我们不能只画一张流程图，还需要明确每一步具体做什么。

建议采用下面的业务流程分析表。

#### 1. 订单业务流程分析表

| **步骤** | **业务活动** | **责任角色** | **关键输出** |
| --- | --- | --- | --- |
| 1 | 接收订单 | 订单运营 | 待处理订单 |
| 2 | 校验订单信息 | 订单运营 | 合法订单 |
| 3 | 检查库存 | 系统/运营 | 库存检查结果 |
| 4 | 预留库存 | 系统 | 库存预留记录 |
| 5 | 审核订单 | 运营主管 | 审核结果 |
| 6 | 仓库拣货 | 仓库人员 | 拣货结果 |
| 7 | 确认发货 | 仓库人员 | 发货记录 |
| 8 | 完成订单 | 系统 | 已完成订单 |

这是一个初步模型，实际流程需要通过用户访谈确认。

#### 2. 每个业务步骤需要分析什么？

以库存检查为例：

| **分析维度** | **需要确认的问题** |
| --- | --- |
| 触发条件 | 什么情况下检查库存？ |
| 输入数据 | 商品 ID、购买数量、可用库存 |
| 处理规则 | 可用库存是否足够？ |
| 正常结果 | 库存足够，允许继续 |
| 异常结果 | 库存不足，阻止订单继续 |
| 责任角色 | 系统还是运营人员？ |
| 数据记录 | 是否记录库存检查结果？ |

特别需要确认库存的概念：

- 实际库存：仓库实际拥有的数量。
- 已预留库存：已经分配给订单的数量。
- 可用库存：可以继续分配的数量。

这些概念会直接影响后续数据库设计。

#### 3. 建立订单状态流转规则

订单状态不能随意修改，需要定义合法流转。

#### 订单状态流转 V0.1

待审核

审核通过

待发货

已发货

已完成

审核不通过

已取消

示意状态机。实际还需定义客户取消、库存不足、退款、发货失败等分支。

这里需要明确一个关键问题：

订单取消后，什么时候释放库存？发货后是否允许取消？审核不通过是否需要自动释放库存？

这些都属于业务规则，不应该由开发人员自行决定。

### 七、第四步：形成正式需求调研记录

现在我们把前面的工作转化成可以交付的文档。

建议正式项目至少形成四份核心资料：

**01 用户调研记录**

用户角色、工作职责、访谈内容、真实痛点。

**02 业务流程说明**

正常流程、异常流程、责任角色、业务规则。

**03 业务问题清单**

问题描述、发生频率、影响范围、业务损失、证据。

**04 需求说明书 PRD**

业务目标、功能需求、业务规则、验收标准。

建议将项目目录设计为：

```text
order-management/
├── docs/
│   ├── 01-research/
│   │   ├── user-interviews.md
│   │   ├── business-process.md
│   │   └── problem-list.md
│   ├── 02-requirements/
│   │   ├── prd.md
│   │   └── acceptance-criteria.md
│   ├── 03-design/
│   ├── 04-development/
│   ├── 05-testing/
│   └── 06-operations/
├── frontend/
├── backend/
├── database/
└── docker-compose.yml
```

这套结构可以贯穿整个项目生命周期。

### 八、现在开始真正的需求调研实战

接下来我不直接替你编写完整需求，而是模拟老板、运营主管和仓库人员，带你逐步完成调研。

我们先从订单来源开始，因为订单来源会影响后续的数据接入、订单创建、字段设计和业务流程。

#### 模拟访谈 · 运营主管

访谈第 1 轮

**我（运营主管）：**

「我们每天需要处理很多订单，目前订单主要来自不同的业务渠道。运营人员需要把订单整理好，再交给仓库处理。」

**你作为项目负责人，首先需要确认订单从哪里进入系统。**

你会怎么提问？

- A. 目前订单分别来自哪些渠道？是自动同步，还是人工导入？
- B. 我们先设计订单列表页面吧。
- C. 我建议所有订单统一使用一个数据库表。
- D. 订单状态应该设计成哪些枚举值？

提交访谈问题

**这次项目有一个要求：**

每完成一轮调研，我们都要沉淀一份正式的项目资料，而不是只完成一道选择题。

最终我们将得到一份完整的订单管理系统 PRD、业务流程图、功能清单、验收标准，然后再进入架构设计。

我们的目标是让你真正能够独立承担一个软件项目的需求分析工作。
