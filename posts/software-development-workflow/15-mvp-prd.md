## 对话 51　第 8 轮　MVP 需求追踪矩阵与 PRD {#turn-51}

> **用户**
>
> 订单管理系统正式需求调研第8轮，我选择：A。请评价我的需求范围管理思路，模拟老板回答，并带我完成 MVP 范围划分、MoSCoW 优先级、需求追踪矩阵和正式 PRD 编写。

**ChatGPT**

回答正确 · 正式需求调研第 8 轮通过

恭喜你！你已经完成订单管理系统的八轮正式需求调研。

你选择 A：

> 根据核心业务目标、用户痛点、业务依赖和实施成本，对需求进行优先级排序，明确第一期 MVP 范围，并与老板确认。

这是正确的项目管理思路。

而且，第八轮是整个需求分析阶段非常关键的一步：**从尽可能收集需求，转变为决定哪些需求值得优先开发。**

今天我们不再继续无限增加功能，而是完成需求分析阶段的正式收尾，产出可以交给开发人员使用的 PRD。

### 一、评价你的需求范围管理思路

优秀

你选择的方案有四个重要优点。

| **思考维度** | **你的做法** | **评价** |
| --- | --- | --- |
| 业务价值 | 解决核心业务问题 | 正确 |
| 用户痛点 | 根据真实问题排序 | 正确 |
| 业务依赖 | 考虑功能之间的关系 | 非常重要 |
| 实施成本 | 考虑开发资源和周期 | 正确 |

我特别强调一个原则：

**MVP 不是功能最少的系统，而是能够独立解决一个核心业务问题的最小可用系统。**

例如：

如果第一期只有订单列表、订单详情和订单搜索，却不能导入订单、审核订单、预留库存和完成发货，那么它可能只是一个订单查询工具，还不能真正解决订单管理问题。

所以我们需要围绕完整业务闭环确定 MVP。

### 二、模拟老板回答

现在进行最后一轮模拟项目评审。

**老板 · 项目决策者**

模拟评审

「我希望第一期尽快上线，但不能只是一个展示数据的系统。

我最希望解决的是订单管理混乱、人工整理订单耗时、库存不准确、仓库发货容易出错这些问题。

第一阶段我认为应该做到：

1. 能够从 Excel 导入订单。
2. 能够统一管理不同来源的订单。
3. 能够检查重复订单和异常数据。
4. 能够管理商品和 SKU。
5. 能够审核订单和预留库存。
6. 仓库能够拣货、复核和发货。
7. 能够处理取消订单和库存释放。
8. 能够查询订单状态和操作记录。

至于复杂的自动化、平台 API 对接、智能经营分析，可以后续再做。

我希望第一期上线后，至少能够让运营和仓库不再依赖 Excel 和人工沟通来管理订单。」

#### 1. 从老板回答中提炼项目目标

我们可以形成三个核心目标：

- **订单统一化**：将不同来源的订单统一接入和管理。
- **履约流程化**：将审核、库存、拣货、发货形成闭环。
- **业务可追溯**：订单、库存、异常和操作记录能够追踪。

这三个目标应该成为第一期 MVP 的决策依据。

### 三、确定 MVP 范围

先把候选功能分成三个版本。

#### 订单管理系统版本规划

**V1.0 · 核心订单闭环**

MVP

目标：让订单从导入到发货能够完整运行。

- Excel 订单导入
- 订单解析与校验
- 商品及 SKU 管理
- 重复订单识别
- 订单列表和详情
- 订单审核
- 库存查询与预留
- 库存释放和出库扣减
- 拣货、复核和发货
- 订单取消
- 操作日志和异常记录

**V1.1 · 运营效率提升**

第二阶段

目标：减少人工操作，提高运营效率。

- 多渠道 API 对接
- 自动商品匹配
- 部分发货
- 物流轨迹自动同步
- 退款与售后管理
- 经营日报和运营周报
- 指标预警

**V2.0 · 智能经营管理**

长期规划

目标：从订单工具升级为经营管理系统。

- 智能经营分析
- 采购与补货建议
- 多仓库管理
- 高级财务对账
- 自动化业务规则
- AI 经营助手
- 人员绩效分析

这里有一个关键决定：

第一期暂不做复杂的 AI 自动化和全渠道 API，但必须把订单来源、商品映射、订单明细和库存流水设计好。

这样以后增加新渠道时，不需要推翻核心架构。

另外，部分退款、复杂优惠分摊和多仓库调拨可以延后，但第一期仍应保留基础金额字段、取消规则和库存审计能力。

### 四、使用 MoSCoW 方法确定需求优先级

MoSCoW 是一种常用的需求优先级管理方法。

它把需求分成四类：

| **分类** | **含义** | **判断标准** |
| --- | --- | --- |
| Must | 必须有 | 缺少它，核心业务无法运行 |
| Should | 应该有 | 非常重要，但可以有临时替代方案 |
| Could | 可以有 | 有价值，但不影响核心闭环 |
| Won't | 暂不做 | 当前版本明确不实现 |

#### 1. 订单系统需求优先级

| **功能模块** | **需求** | **优先级** |
| --- | --- | --- |
| 订单接入 | Excel 导入 | Must |
| 订单接入 | 导入数据校验 | Must |
| 订单管理 | 订单列表与详情 | Must |
| 订单管理 | 重复订单识别 | Must |
| 商品管理 | 商品与 SKU 管理 | Must |
| 商品管理 | 渠道商品映射 | Must |
| 订单审核 | 人工审核 | Must |
| 库存管理 | 库存查询 | Must |
| 库存管理 | 库存预留 | Must |
| 库存管理 | 库存释放 | Must |
| 库存管理 | 库存流水 | Must |
| 仓库管理 | 拣货与复核 | Must |
| 仓库管理 | 发货确认 | Must |
| 仓库管理 | 多包裹拆单 | Could |
| 订单管理 | 取消订单 | Must |
| 订单管理 | 部分发货 | Should |
| 物流管理 | 物流单号记录 | Must |
| 物流管理 | 自动物流轨迹 | Should |
| 退款管理 | 基础退款记录 | Should |
| 退款管理 | 复杂退款分摊 | Won't |
| 数据分析 | 经营日报 | Should |
| 数据分析 | 高级经营大屏 | Could |
| 系统管理 | 用户角色权限 | Must |
| 系统管理 | 操作审计日志 | Must |
| 智能化 | AI 经营建议 | Won't |
| 系统集成 | 多平台 API 自动对接 | Won't |

注意：这里的 Won't 代表不进入 V1.0，不代表永远不开发。

#### 2. 一个重要的需求取舍

为什么库存流水是 Must？

因为如果没有库存流水，系统虽然能显示库存数量，却无法解释：

- 为什么库存减少了？
- 哪个订单占用了库存？
- 谁释放了库存？
- 为什么实际库存和系统库存不一致？

所以库存流水虽然不一定是老板直接看到的功能，却是系统可靠运行的基础。

这就是产品经理必须具备的能力：

**不能只根据用户表面提出的功能判断优先级，还要识别功能背后的业务依赖。**

### 五、建立需求追踪矩阵 RTM

接下来进入一个非常重要的项目管理知识点。

RTM（Requirements Traceability Matrix），中文叫需求追踪矩阵。

它解决的问题是：

> 每一个业务问题，是否都已经转化成需求？每个需求是否有设计、开发和测试？最终是否通过验收？

我们用一条完整链路举例。

#### 需求追踪示例

**业务问题**

重复导入 Excel 会产生重复订单。

**功能需求 FR-006**

系统必须识别相同来源、相同外部订单标识的订单。

**技术设计**

来源渠道 + 外部订单唯一标识、数据库唯一约束、幂等导入服务。

**测试用例 TC-006**

同一个 Excel 文件重复上传两次，系统不得创建重复正式订单。

**验收结果**

订单数量不增加，重复记录可查询，原始导入记录可追溯。

这就是从业务问题到验收结果的完整追踪链路。

#### 1. 订单系统 RTM 示例

| **业务问题** | **需求 ID** | **功能** | **测试 ID** |
| --- | --- | --- | --- |
| 多渠道订单混乱 | FR-001 | Excel 订单导入 | TC-001 |
| 重复订单 | FR-006 | 重复识别 | TC-006 |
| 商品无法匹配 | FR-004 | 商品匹配 | TC-004 |
| 订单数据异常 | FR-007 | 订单校验 | TC-007 |
| 库存超卖 | FR-023 | 库存预留 | TC-023 |
| 库存释放失败 | FR-026 | 库存释放 | TC-026 |
| 拣货错误 | FR-031 | 拣货结果记录 | TC-031 |
| 发货重复扣减 | FR-040 | 出库确认 | TC-040 |
| 取消订单混乱 | FR-041 | 订单取消 | TC-041 |
| 经营数据不清楚 | FR-052 | 经营总览 | TC-052 |

#### 2. RTM 的实际用途

后续开发时，我们会在每条需求中继续增加：

- 设计文档 ID。
- 开发任务 ID。
- API 接口 ID。
- 数据库表或字段。
- 测试用例 ID。
- 测试结果。
- 验收状态。

这样项目就不会出现「需求写了，但是开发漏了」「功能开发了，但是没有测试」「测试通过了，但是不符合业务」等问题。

### 六、正式编写 PRD

现在开始将八轮调研成果转化为正式需求说明书。

这份 PRD 不是简单的功能清单，而是开发、测试、产品和业务人员共同使用的项目基线。

我会先给出 V1.0 的可评审初稿，明确哪些规则已经有模拟业务依据，哪些仍需要真实业务确认。

写作

### 订单管理系统（OMS）产品需求说明书 PRD

**文档版本：** V1.0-Draft
**项目阶段：** 需求分析
**文档状态：** 待业务评审
**产品类型：** B 端订单与仓库管理系统

#### 1. 项目概述

##### 1.1 项目背景

企业目前通过多个渠道获取订单，订单格式不统一，运营人员需要人工整理、核对和处理订单。

现有业务存在以下问题：

1. 多渠道订单数据分散，缺少统一管理。
2. Excel 导入容易产生重复订单和数据错误。
3. 外部商品与内部 SKU 匹配依赖人工。
4. 订单审核、库存预留和取消流程不规范。
5. 仓库拣货、复核和发货缺少统一记录。
6. 库存变更缺少完整的业务流水。
7. 订单异常无法及时发现和追踪。
8. 管理人员缺少统一的运营数据。

##### 1.2 项目目标

建设一个统一的订单管理系统，实现：

- 多渠道订单统一接入。
- 订单创建、审核和状态管理。
- 商品与 SKU 统一管理。
- 库存检查、预留、释放和出库。
- 仓库拣货、复核和发货。
- 订单取消与异常处理。
- 业务操作记录和数据追溯。

##### 1.3 核心业务闭环

订单导入 → 数据校验 → 商品匹配 → 订单创建 → 订单审核 → 库存预留 → 仓库拣货 → 商品复核 → 打包 → 出库 → 物流跟踪。

异常订单进入异常处理流程，不允许绕过必要的业务校验直接进入履约。

#### 2. 用户角色

| **角色** | **主要职责** |
| --- | --- |
| 老板 | 查看经营数据、业务总览 |
| 运营主管 | 订单审核、异常审批、业务管理 |
| 运营人员 | 导入订单、处理订单、提交取消申请 |
| 仓库人员 | 拣货、复核、打包、出库 |
| 系统管理员 | 用户、角色、商品和系统配置 |

权限采用 RBAC 模型，并支持数据权限和字段权限。

#### 3. MVP 功能范围

##### 3.1 V1.0 必须实现

1. 用户登录与权限管理。
2. 商品与 SKU 管理。
3. Excel 订单批量导入。
4. 导入数据解析和校验。
5. 重复订单识别。
6. 商品匹配与人工修正。
7. 订单列表、详情和搜索。
8. 订单审核。
9. 库存查询与预留。
10. 库存释放和出库扣减。
11. 仓库拣货和复核。
12. 打包与发货确认。
13. 物流单号记录。
14. 订单取消。
15. 异常订单处理。
16. 操作日志和库存流水。

##### 3.2 V1.0 暂不实现

- 多平台自动 API 接入。
- AI 自动经营建议。
- 复杂财务结算。
- 高级经营数据大屏。
- 多仓库调拨。
- 复杂退款分摊。
- 自动采购与补货。

#### 4. 功能需求

##### FR-001：订单导入

**功能描述：**

运营人员上传 Excel 文件，系统解析文件并生成订单导入批次。

**业务规则：**

- 支持规定模板的 Excel 文件。
- 校验必填字段。
- 记录导入人、导入时间和来源渠道。
- 保存原始导入数据。
- 记录每条数据的解析和校验结果。
- 支持查看失败原因。
- 重复上传不得产生重复正式订单。

**验收标准：**

- 上传合法文件后能够生成导入批次。
- 非法文件能够返回明确错误。
- 每条失败数据可以定位到具体原因。
- 同一订单重复导入不会重复创建正式订单。

##### FR-002：商品管理

**功能描述：**

维护内部商品和 SKU 信息，支持外部商品映射。

**业务规则：**

- 一个商品可以有多个 SKU。
- 一个订单可以包含多个商品明细。
- 外部 SKU 与内部 SKU 建立映射关系。
- 无法匹配时进入人工处理。
- 保存订单商品价格快照。

**验收标准：**

- 能够新增、编辑和停用商品。
- 能够维护商品规格。
- 能够建立和查询渠道商品映射。
- 无法匹配的商品不能进入正常履约流程。

##### FR-003：订单管理

**功能描述：**

提供订单列表、详情、搜索和状态查询。

**订单信息：**

- 内部订单编号。
- 外部订单编号。
- 来源渠道。
- 客户信息。
- 收货信息。
- 商品明细。
- 订单金额。
- 订单状态。
- 履约状态。
- 创建时间。

**验收标准：**

- 支持按订单编号查询。
- 支持按来源渠道筛选。
- 支持按订单状态筛选。
- 订单详情展示完整商品明细。
- 普通修改不得覆盖原始订单数据。

##### FR-004：订单审核

**功能描述：**

授权用户对订单执行审核。

**业务规则：**

- 审核前必须完成必要的信息校验。
- 审核通过时执行库存预留。
- 库存预留成功后才能进入正常待发货流程。
- 库存不足时进入缺货处理。
- 审核拒绝必须记录原因。
- 审核操作支持幂等控制。

**验收标准：**

- 未通过必要校验的订单不能正常审核通过。
- 库存不足不能进入正常待发货状态。
- 同一订单重复审核不能重复预留库存。
- 审核操作记录审核人和时间。

##### FR-005：库存管理

**功能描述：**

管理实际库存、预留库存和可用库存。

**计算规则：**

可用库存 = 实际库存 - 预留库存。

**业务规则：**

- 审核通过时预留库存。
- 未发货取消时释放预留库存。
- 实际出库时扣减实际库存。
- 出库时同步减少对应预留库存。
- 多 SKU 预留在同一事务内完成。
- 库存操作必须记录流水。
- 库存不得出现负数。

**验收标准：**

- 预留库存不得超过实际库存。
- 并发预留不得产生超卖。
- 重复预留和重复释放不得重复修改库存。
- 多商品预留失败时应回滚整个事务。
- 每次库存变化能够查询来源订单和操作记录。

##### FR-006：仓库拣货与复核

**功能描述：**

仓库人员根据订单明细执行拣货和复核。

**业务规则：**

- 只允许处理符合履约条件的订单。
- 记录订单商品、规格和实际拣货数量。
- 拣货异常需要记录原因。
- 复核不通过不能正常进入打包。
- 记录拣货人和复核人。

**验收标准：**

- 能够查看待处理拣货任务。
- 能够记录实际拣货数量。
- 数量不符时能够提交异常。
- 复核失败后能够重新处理。
- 拣货和复核过程可追溯。

##### FR-007：发货管理

**功能描述：**

管理打包、出库和物流信息。

**业务规则：**

- 复核通过后才能打包。
- 实际出库确认时扣减库存。
- 记录快递公司和物流单号。
- 物流单号创建不等于快递已经揽收。
- 发货请求超时必须先核对实际结果再重试。
- 同一出库记录不得重复扣减库存。

**验收标准：**

- 未复核通过的商品不能正常发货。
- 发货记录能够关联订单和商品明细。
- 发货确认后库存数量正确变化。
- 物流单号能够查询。
- 重复提交发货请求不能重复扣减库存。

##### FR-008：订单取消

**功能描述：**

根据订单状态处理取消申请。

**业务规则：**

- 待审核订单可以按权限取消。
- 待发货订单取消时释放预留库存。
- 拣货中订单需要停止拣货并确认商品归位。
- 已打包订单需要审批。
- 已出库订单进入物流拦截或售后处理。
- 已完成订单通过售后流程处理。
- 所有取消操作记录原因和操作人。

**验收标准：**

- 不允许执行不符合订单状态的取消操作。
- 库存释放失败时不能伪装成完整取消成功。
- 重复取消请求不能重复释放库存。
- 取消过程能够查询完整记录。

##### FR-009：异常订单管理

**功能描述：**

统一管理订单、库存和仓库异常。

**业务规则：**

- 支持异常分类。
- 支持责任人分配。
- 支持异常状态管理。
- 支持处理说明。
- 支持异常关闭和审计。

**验收标准：**

- 异常能够关联订单。
- 异常能够分配责任人。
- 异常处理过程可以追踪。
- 已关闭异常不能被普通操作直接覆盖。

##### FR-010：操作审计

**功能描述：**

记录关键业务操作。

**记录内容：**

- 操作人。
- 操作时间。
- 操作对象。
- 操作类型。
- 修改前数据。
- 修改后数据。
- 操作原因。

**验收标准：**

订单审核、取消、库存变更、发货、地址修改等重要操作均能够查询审计记录。

#### 5. 核心业务状态

##### 5.1 订单状态

初步建议：

- 待审核。
- 待处理。
- 待发货。
- 部分发货。
- 已完成。
- 已取消。
- 异常处理中。

实际订单状态需要通过合法状态转换规则管理，不能任意修改。

##### 5.2 履约状态

- 待拣货。
- 拣货中。
- 待复核。
- 待打包。
- 待出库。
- 部分发货。
- 全部发货。

##### 5.3 退款状态

退款状态独立于订单状态管理，V1.0 先保留必要的退款关联字段，完整退款流程后续实现。

#### 6. 非功能需求

##### 6.1 数据一致性

- 库存变更使用数据库事务。
- 库存操作支持幂等。
- 重要业务操作保留审计日志。
- 订单原始数据可追溯。

##### 6.2 安全性

- 登录身份认证。
- 后端接口权限校验。
- 客户隐私字段按权限展示。
- 重要操作记录审计日志。

##### 6.3 可用性

- 订单导入失败提供明确提示。
- 异常任务支持重试。
- 系统故障不能导致重复扣减库存。
- 关键业务操作提供执行结果反馈。

##### 6.4 性能

具体并发量、订单量、导入文件大小和响应时间需要在正式技术设计阶段根据真实业务规模确定，不在本稿中虚构性能承诺。

#### 你的下一道实战题

假设现在让你负责开发这个系统。

老板问你：

「我们为什么不能把所有功能都写在一个 FastAPI 文件里？为什么要拆成订单、库存、商品、仓库等模块？」

你会怎么回答？

#### 系统架构设计 · 第一题

- A. 因为不同业务模块有独立职责和业务规则，合理划分模块可以降低耦合，让系统更容易维护、测试和扩展。
- B. 因为文件越多，系统性能越好。
- C. 因为每个模块都必须独立部署成一个微服务。
- D. 因为使用更多技术组件可以体现架构设计水平。
