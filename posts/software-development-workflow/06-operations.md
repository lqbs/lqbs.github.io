### 二、正式建立订单管理系统运营指标体系

今天我们要完成一个实际成果：

**订单管理系统运营指标体系 V1.0**

首先记住一个核心方法：

业务目标 → 运营目标 → KPI → 计算口径 → 数据来源 → 改进动作。

#### 第一步：明确系统的核心业务目标

假设企业开发订单管理系统，是为了解决四个问题：

| **业务问题** | **希望实现的目标** |
| --- | --- |
| 订单处理慢 | 提高订单处理效率 |
| 订单容易出错 | 降低订单错误率 |
| 用户不愿意使用 | 提高系统使用率 |
| 管理者不了解订单情况 | 提高经营管理效率 |

这四个目标构成运营指标体系的基础。

#### 第二步：设计四大指标模块

#### 订单管理系统运营指标体系

**1. 用户使用指标**

回答：用户是否真正使用系统？

- 周活跃用户数（WAU）
- 用户激活率
- 功能使用率
- 核心任务完成率
- 用户留存率

**2. 业务效率指标**

回答：系统是否提高工作效率？

- 平均订单处理时长
- 人均订单处理量
- 订单处理自动化率
- 订单积压数量

**3. 业务质量指标**

回答：业务处理是否准确？

- 订单错误率
- 订单取消率
- 库存异常率
- 订单数据完整率

**4. 系统运行指标**

回答：系统是否稳定可靠？

- 系统可用性
- API 成功率
- API P95 响应时间
- 系统异常次数

注意：四类指标各有用途。不能用系统可用性代替用户使用率，也不能用用户登录次数代替业务价值。

### 三、第三步：为每个指标定义计算公式

指标名称只是开始，必须有明确的计算口径。

下面是订单管理系统 V1.0 的核心指标定义。

#### 1. 用户使用指标

| **指标** | **计算公式** |
| --- | --- |
| 周活跃用户 WAU | 一周内完成有效业务行为的去重用户数 |
| 用户激活率 | 完成首次核心任务的用户数 / 新注册用户数 |
| 功能使用率 | 使用某功能的活跃用户数 / 活跃用户数 |
| 任务完成率 | 成功完成任务数 / 开始任务数 |
| 用户留存率 | 本期活跃且下期仍活跃的用户数 / 本期活跃用户数 |

这里特别强调：

**登录不等于活跃。**

例如，用户登录系统后没有完成任何订单操作，只能说明他访问过系统，不能说明他真正使用了订单管理功能。

建议把有效业务行为定义为：

- 创建订单。
- 修改订单。
- 审核订单。
- 完成发货。
- 处理订单异常。

具体需要根据实际岗位职责选择。

#### 2. 业务效率指标

| **指标** | **计算公式** |
| --- | --- |
| 平均订单处理时长 | 总处理耗时 / 完成订单数 |
| 人均订单处理量 | 完成订单数 / 参与处理人数 |
| 自动化处理率 | 自动完成订单数 / 总完成订单数 |
| 订单积压量 | 当前超过规定处理时限的订单数 |

例如：

**平均订单处理时长计算示例**

### 600

总处理分钟数

### 100

完成订单数

**平均处理时长**

### 6 分钟

600 ÷ 100=6分钟600÷100=6分钟

这里有一个容易犯的错误：

订单创建时间到订单完成时间，不一定等于人工处理时间。

如果订单等待了 2 小时才被处理，直接用这两个时间相减，会把等待时间也算进去。

所以要明确区分：

- 订单总流转时长。
- 人工实际处理时长。
- 各业务环节等待时长。

#### 3. 业务质量指标

| **指标** | **计算公式** |
| --- | --- |
| 订单错误率 | 错误订单数 / 总订单数 |
| 库存异常率 | 存在库存异常的订单数 / 总订单数 |
| 订单取消率 | 取消订单数 / 已创建订单数 |
| 数据完整率 | 必填信息完整的订单数 / 总订单数 |

注意，订单取消不一定代表错误。例如客户主动取消订单，可能是正常业务行为。

所以后续需要对取消原因进行分类。

#### 4. 系统运行指标

| **指标** | **计算方式** |
| --- | --- |
| 系统可用性 | 可用时间 / 总服务时间 |
| API 成功率 | 成功请求数 / 有效请求数 |
| API P95 | 请求耗时的第 95 百分位数 |
| 异常次数 | 统计周期内符合定义的系统异常数量 |

这些指标可以与第五课学过的 Prometheus、Grafana 结合。

### 四、第四步：建立指标优先级

初学者容易犯的一个错误：

把所有指标都放进大屏，最后不知道应该重点关注什么。

我们应该区分三类指标。

核心指标

**北极星指标：每周有效完成订单数**

衡量系统是否持续帮助用户完成核心业务任务。

过程指标

**周活跃用户、任务完成率、平均处理时长、功能使用率**

解释核心指标为什么变化。

质量护栏指标

**订单错误率、库存异常率、API 失败率**

防止为了追求效率而牺牲数据准确性和系统稳定性。

为什么把每周有效完成订单数作为北极星指标？

因为订单管理系统的核心价值是帮助用户完成订单管理工作。

但是不能为了增加订单完成量，就忽略错误订单、重复订单或异常库存。

所以需要设置质量护栏。

### 五、第五步：设计指标数据来源

指标不能凭空产生，需要明确数据从哪里来。

以我们之前的 React + FastAPI + MySQL 项目为例：

| **指标** | **数据来源** | **技术实现** |
| --- | --- | --- |
| 周活跃用户 | 用户行为记录 | FastAPI 埋点 |
| 功能使用率 | 功能操作记录 | 行为事件表 |
| 订单处理时长 | 订单状态变化记录 | MySQL 时间字段 |
| 订单错误率 | 订单异常记录 | 业务异常表 |
| 库存异常率 | 库存流水和库存快照 | MySQL |
| API 成功率 | HTTP 请求日志和指标 | Prometheus |
| API P95 | 请求耗时指标 | Prometheus |

这里引入一个重要概念：

**数据埋点（Event Tracking）。**

例如用户创建订单：

```json
{
  "event_name": "order_created",
  "user_id": 1001,
  "order_id": 20001,
  "timestamp": "2026-11-20T10:30:00+08:00",
  "source": "web"
}
```

用户完成订单：

```json
{
  "event_name": "order_completed",
  "user_id": 1001,
  "order_id": 20001,
  "timestamp": "2026-11-20T10:36:00+08:00"
}
```

通过两个事件，可以计算订单的流转时长。

但要注意：

- 事件必须有统一命名规范。
- 同一个业务动作可能重复上报，需要去重。
- 时间戳要统一时区。
- 用户和订单标识要能够关联。
- 不能只依靠前端埋点判断订单是否真正完成，应以服务端业务状态为准。

对于订单、库存这类重要数据，建议服务端记录业务事件，前端埋点主要补充页面访问、按钮点击和操作流程信息。

### 第六课 · 1.2 指标计算口径、目标值与运营看板

#### 一、第一步：建立指标定义表

先明确一个原则：

**一个指标必须具备名称、业务定义、计算公式、统计范围和数据来源。**

否则不同人可能使用不同的计算方式，最后得到完全不同的结果。

我们以订单管理系统为例。

#### 核心运营指标定义 V1.0

统计周期：自然周 · 统计对象：正常业务订单

**指标 1：每周有效完成订单数**

- 定义：一周内成功完成业务流程的有效订单数量。
- 公式：有效完成订单去重计数。
- 数据来源：订单主表。
- 统计粒度：周。

**指标 2：平均订单处理时长**

- 定义：订单从开始处理到完成处理的平均耗时。
- 公式：总有效处理时长 / 完成订单数。
- 数据来源：订单状态流转记录。
- 统计粒度：订单、周。

**指标 3：订单错误率**

- 定义：完成后被确认存在业务错误的订单占比。
- 公式：错误订单数 / 完成订单数 × 100%。
- 数据来源：订单异常记录、人工复核结果。
- 统计粒度：周。

**指标 4：核心任务完成率**

- 定义：用户成功完成核心订单任务的比例。
- 公式：成功完成任务数 / 已开始任务数 × 100%。
- 数据来源：服务端业务事件。
- 统计粒度：用户、周。

##### 一个容易忽略的问题：什么叫有效完成订单？

例如订单状态：

```text
待处理 → 处理中 → 已完成
```

如果用户创建订单后马上取消，是否计入完成订单数？

不应该。

建议将有效完成订单定义为：

- 订单真实存在。
- 已经完成规定的业务流程。
- 不属于测试订单。
- 不属于重复订单。
- 不属于已撤销或作废的订单。

另外，如果同一笔订单发生重复状态变更，只能计数一次。

这就是指标口径的重要性。

#### 二、第二步：设计指标计算公式

现在我们进一步细化计算方法。

##### 1. 每周有效完成订单数

订单数 = COUNT(DISTINCT order\_id)订单数=COUNT(DISTINCT order\_id)

SQL 示例：

```sql
SELECT
    COUNT(DISTINCT id) AS completed_orders
FROM orders
WHERE status = 'completed'
  AND completed_at >= '2026-11-16 00:00:00'
  AND completed_at <  '2026-11-23 00:00:00'
  AND is_test = 0;
```

这里使用左闭右开的时间范围，避免时间边界重复统计。

注意：这是示例 SQL，真实系统需要根据订单状态模型和作废规则确定统计口径。

##### 2. 平均订单处理时长

平均时长 = (Σ(完成时间-开始处理时间)) ÷ (完成订单数)平均时长=完成订单数∑(完成时间−开始处理时间)​

SQL 示例：

```sql
SELECT
    AVG(
        TIMESTAMPDIFF(
            SECOND,
            process_started_at,
            completed_at
        )
    ) / 60 AS avg_minutes
FROM orders
WHERE status = 'completed'
  AND process_started_at IS NOT NULL
  AND completed_at IS NOT NULL;
```

这里有一个设计细节：

如果一笔订单中途暂停，应该扣除暂停时间吗？

如果业务目标是衡量员工实际操作效率，可能需要扣除等待时间；如果目标是衡量客户从下单到完成的整体体验，则不应该扣除。

不同业务目标需要不同的时间口径。

##### 3. 订单错误率

错误率 = (错误订单数) ÷ (有效完成订单数) × 100%错误率=有效完成订单数错误订单数​×100%

例如：

- 完成订单：1000 笔。
- 确认错误订单：20 笔。

那么：

20/1000 × 100%=2%20/1000×100%=2%

##### 4. 核心任务完成率

任务完成率 = (成功完成任务数) ÷ (开始任务数) × 100%任务完成率=开始任务数成功完成任务数​×100%

例如：

- 用户开始创建订单 100 次。
- 成功完成 95 次。

任务完成率为 95%。

注意：必须用统一的任务 ID 或业务流程 ID 关联开始和完成事件，避免重复点击造成分母膨胀。

### 三、第三步：为指标设定目标值

现在我们知道如何计算指标了。

接下来要解决一个更重要的问题：

**指标达到多少，才算做得好？**

例如：

- 订单错误率 2%，算高还是低？
- 平均处理时长 6 分钟，是否合理？
- 每周完成 1000 笔订单，是否达标？

不能随意设定目标值。

建议使用三个步骤。

#### 1. 确定当前基准值

先统计系统上线前或最近 4 周的数据。

假设目前数据如下：

| **指标** | **当前基准值** |
| --- | --- |
| 每周有效完成订单数 | 1000 笔 |
| 平均订单处理时长 | 6 分钟 |
| 订单错误率 | 2% |
| 核心任务完成率 | 95% |

#### 2. 根据业务目标设定目标值

例如，企业希望在未来 3 个月提高订单处理效率。

我们可以初步制定：

| **指标** | **当前值** | **3 个月目标** | **方向** |
| --- | --- | --- | --- |
| 每周有效完成订单数 | 1000 | 1200 | 越高越好 |
| 平均处理时长 | 6 分钟 | 4.5 分钟 | 越低越好 |
| 订单错误率 | 2% | 1% | 越低越好 |
| 核心任务完成率 | 95% | 98% | 越高越好 |

这些是教学示例目标，真正的目标要根据业务量、人员配置、订单复杂度和实际基准来验证。

#### 3. 明确目标值的依据

建议从三个角度设定目标：

- 历史数据：过去表现如何？
- 业务要求：老板希望改善什么？
- 实际能力：团队和系统能否实现？

不要为了让报表好看而设置不合理的 KPI。

例如，如果订单量受季节影响明显，不能简单要求每周订单量固定增长 20%，否则可能把市场变化误认为产品效果。

#### 3. 看板设计原则

记住四个原则：

**第一，先看结果，再看原因。**

- 哪个部门错误最多？
- 哪个员工错误最多？
- 哪类订单错误最多？
- 哪个业务环节出现问题？

**第四，看板必须能够引导行动。**

### 五、第五步：建立指标异常分析机制

现在看板已经建好了。

不能只在看板上标红。

需要建立一套分析流程：

#### 指标异常分析流程

**发现异常**

订单错误率超过目标

**拆解维度**

部门、员工、订单类型、时间段

**定位原因**

流程问题、系统问题、人员操作问题

**制定改善方案**

优化流程、调整功能、加强培训

**验证改善效果**

对比改善前后的指标

举个例子：

进一步分析：

| **订单类型** | **错误率** |
| --- | --- |
| 普通订单 | 0.5% |
| 批量订单 | 5% |
| 退货订单 | 0.8% |

发现批量订单错误率明显偏高。

下一步就应该重点调查批量订单的操作流程，而不是盲目修改整个系统。

这就是指标驱动的运营分析。

你没有因为订单数量距离目标最近，就优先追求数量，而是先关注业务质量。

#### 一、评价你的判断

先看四项指标：

| **指标** | **当前值** | **目标值** | **差距** |
| --- | --- | --- | --- |
| 每周完成订单数 | 1080 | 1200 | 少 10% |
| 平均处理时长 | 5.2 分钟 | 4.5 分钟 | 高 15.6% |
| 订单错误率 | 1.6% | 1% | 高 60% |

但要补充一个管理上的判断：

**指标差距大，不一定代表业务影响最大。**

例如：

- 订单错误率上升，可能导致库存不准确、客户投诉。
- 订单处理时间增加，可能造成大量订单积压。
- 完成订单数下降，可能意味着业务需求减少，也可能是系统使用率下降。

因此，真正的优先级应该同时考虑：

1. 影响范围。
2. 业务损失。
3. 风险严重程度。
4. 解决成本。
5. 是否存在紧急性。

你的选择 A 是一个合理的第一步：先调查质量风险，再根据证据确定改善方案，而不是直接修改功能。

### 第六课 · 1.3 用户反馈收集、用户访谈与需求发现

本节目标：从用户表达中发现真实业务问题

今天我们要解决一个非常重要的问题：

**用户说想要一个功能，我们应该直接开发吗？**

答案通常是：不要急着开发。

例如，订单系统上线后，运营主管提出：

> 我希望增加一个批量修改订单状态的功能。

如果你马上开发，可能会遇到：

- 开发完没人使用。
- 实际问题没有解决。
- 业务流程反而更复杂。
- 后续不断追加需求。

所以我们需要先理解用户真正想解决的问题。

这就是需求发现（Discovery）。

### 二、第一步：理解用户反馈和真实需求的区别

先理解三个概念。

用户表达

**用户想要什么？**

例如：我想增加批量修改订单状态的功能。

真实问题

**用户为什么需要？**

例如：每天需要逐条修改 200 笔订单，重复操作非常耗时。

业务价值

**解决后有什么改善？**

例如：减少重复操作，将订单批量处理时间从 30 分钟缩短到 5 分钟。

这三个层次不能混淆。

用户提出的功能，只是他对解决方案的一种设想，不一定是最佳方案。

#### 一个实际案例

运营主管说：

「希望增加批量修改订单状态。」

我们进一步询问：

- 为什么需要批量修改？
- 每天有多少订单需要修改？
- 现在怎么操作？
- 每次需要多长时间？
- 哪些订单可以批量修改？
- 修改错误会有什么影响？

经过沟通，发现真实情况是：

每天有 200 笔订单需要人工逐条审核，平均每笔需要 10 秒。

那么每天耗时：

200 × 10=2000秒200×10=2000秒

约为 33 分钟。

这时候我们才知道，真正的问题可能是：

**订单审核流程存在大量重复人工操作。**

解决方案不一定只是批量修改状态，还可能包括批量审核、审核规则自动化或异常订单自动筛选。

### 三、第二步：建立用户反馈收集渠道

用户反馈不能只依靠老板或运营主管转述。

我们需要建立多渠道反馈机制。

#### 1. 五种常见反馈渠道

| **渠道** | **收集什么** | **适用场景** |
| --- | --- | --- |
| 用户访谈 | 深层原因、工作流程 | 发现真实问题 |
| 问卷调查 | 满意度、普遍意见 | 大范围收集反馈 |
| 用户工单 | 具体问题、故障 | 处理使用障碍 |
| 产品行为数据 | 实际使用行为 | 发现用户行为异常 |
| 业务人员反馈 | 一线业务痛点 | 发现流程问题 |

我建议建立一个统一的反馈入口，而不是让需求散落在微信群、口头沟通和 Excel 中。

#### 2. 设计反馈记录表

每一条反馈都应该保留原始信息和后续分析结果。

#### 用户反馈记录模板

| **字段** | **示例** |
| --- | --- |
| 反馈编号 | FB-001 |
| 反馈用户 | 订单运营主管 |
| 反馈时间 | 2026-11-20 |
| 反馈内容 | 希望批量修改订单状态 |
| 所属模块 | 订单管理 |
| 问题类型 | 效率问题 |
| 影响范围 | 每天约 200 笔订单 |
| 当前处理方式 | 逐条手动修改 |
| 业务影响 | 每天耗时约 33 分钟 |
| 当前状态 | 待分析 |

注意：不要在收集反馈时就直接把「批量修改订单状态」认定为需求。

它目前只是用户提出的解决方案。

我们还需要通过访谈确认问题。

### 四、第三步：学习用户访谈方法

用户访谈是需求发现中非常重要的能力。

它不是简单地问用户：

「你还需要什么功能？」

而是通过提问，了解用户的实际工作、遇到的困难和行为习惯。

#### 1. 用户访谈的五个步骤

1. **了解用户角色**

他负责什么工作？每天需要处理哪些任务？

2. **了解实际流程**

从接收订单到完成订单，具体经过哪些步骤？

3. **发现困难**

哪个环节最耗时？最容易出错？

4. **量化业务影响**

每天发生多少次？浪费多少时间？影响多少订单？

5. **确认改善目标**

如果问题解决，希望发生什么变化？

#### 2. 设计一套用户访谈问题

假设我们采访一名订单运营主管。

我建议使用以下问题。

**第一组：了解工作**

- 你每天主要负责哪些订单工作？
- 每天大概处理多少笔订单？
- 哪些工作最耗费时间？

**第二组：了解流程**

- 你能不能带我完整走一遍订单处理流程？
- 哪些环节需要人工操作？
- 哪些环节需要在多个系统之间切换？

**第三组：发现问题**

- 最近一次订单处理出错是什么时候？
- 当时发生了什么？
- 你是怎么解决的？
- 哪个问题出现得最频繁？

**第四组：量化影响**

- 这个问题每天发生多少次？
- 每次需要处理多久？
- 会影响多少笔订单？
- 会不会造成客户投诉或经济损失？

**第五组：确认目标**

- 如果这个问题得到解决，你最希望改善什么？
- 你如何判断改善有效？
- 有没有其他方式可以解决？

#### 3. 特别重要：避免诱导性提问

这是很多技术人员容易忽略的地方。

| **不好的提问** | **更好的提问** |
| --- | --- |
| 你是不是觉得批量操作很重要？ | 你目前如何处理大量订单？ |
| 要不要增加批量审核？ | 哪个审核环节最耗时？ |
| 如果增加这个功能，你会使用吗？ | 最近一次处理这类订单时，你具体怎么操作？ |
| 你觉得系统好不好用？ | 哪些操作让你感到困难？ |

为什么？

因为用户可能为了配合你而回答「是」，但这不代表他真的有这个需求。

**尽量询问用户过去真实发生的行为，而不是让用户预测未来会怎么做。**

### 五、第四步：从用户反馈提炼真实需求

这是今天最重要的能力。

我们通过一个案例来学习。

#### 订单运营主管访谈记录

模拟访谈

**访谈对象：** 订单运营主管

**用户原话：**

「每天有很多订单需要审核，我要逐条打开订单、检查信息、修改状态。忙的时候需要半小时以上。我希望增加批量修改功能。」

**进一步访谈发现：**

- 每天约 200 笔订单需要审核。
- 每笔订单需要打开详情、检查信息、修改状态。
- 大约 20% 的订单存在信息不完整问题。
- 运营人员需要逐条识别异常订单。
- 普通订单和异常订单需要不同的处理流程。

现在我们进行需求分析。

#### 1. 拆解用户真正的问题

| **维度** | **分析结果** |
| --- | --- |
| 用户角色 | 订单运营主管 |
| 工作任务 | 审核订单 |
| 当前流程 | 逐条打开、检查、修改 |
| 主要困难 | 重复操作、异常订单难以识别 |
| 影响范围 | 每天约 200 笔 |
| 业务影响 | 审核耗时长、容易遗漏 |

#### 2. 提炼问题陈述

问题陈述（Problem Statement）应该清晰描述：

- 谁遇到了问题？
- 在什么场景下？
- 遇到了什么困难？
- 造成什么影响？

例如：

> 订单运营人员在每天处理约 200 笔订单时，需要逐条打开订单并人工审核。由于普通订单和异常订单混在一起，导致审核操作重复、异常订单识别效率低，每天需要花费大量时间。

这才是一个可以进一步分析和解决的问题。

#### 3. 从问题提炼功能需求

| **业务问题** | **候选功能需求** |
| --- | --- |
| 逐条打开订单 | 订单批量审核 |
| 普通订单和异常订单混杂 | 异常订单自动识别 |
| 难以快速找到待处理订单 | 待审核订单筛选 |
| 容易遗漏异常订单 | 异常订单提醒 |

注意：这些是候选解决方案，还需要进一步评估技术可行性、业务规则和用户价值。

#### 4. 将需求写成标准格式

可以使用下面这个模板：

#### 用户故事模板

作为一名 \[用户角色\]，

我希望 \[完成某项操作\]，

以便 \[获得某种业务价值\]。

**示例：**

作为一名订单运营人员，

我希望能够批量审核符合规则的普通订单，

以便减少重复操作，提高订单审核效率。

再为需求增加验收标准：

- 可以选择多笔符合条件的订单。
- 可以查看批量操作影响的订单数量。
- 不符合审核条件的订单不能被批量通过。
- 批量操作失败时能够明确显示失败原因。
- 重复提交不能造成重复业务处理。
- 能够记录操作人、操作时间和操作结果。

这样就从一句用户反馈，逐渐形成了可开发、可测试的需求。

### 六、第五步：建立需求发现的证据链

真正成熟的需求管理，不是记录「用户说了什么」，而是记录为什么认为这个问题值得解决。

我建议使用下面这条证据链：

#### 需求发现证据链

**用户反馈**

希望增加批量审核

**访谈证据**

每天处理约 200 笔订单

**数据证据**

人工审核耗时约 33 分钟/天

**问题定义**

订单审核存在重复人工操作

**候选需求**

### 第六课 · 1.4 用户反馈分类与需求优先级

本节目标：建立需求池，并判断先做什么

#### 三、第一步：为什么要对用户反馈分类？

假设你负责订单管理系统。

一个星期内，收到了 20 条用户反馈：

- 订单列表加载慢。
- 希望增加批量审核。
- 导出 Excel 失败。
- 库存数量不准确。
- 页面颜色不好看。
- 订单搜索不方便。
- 希望增加自动审核。
- 系统偶尔登录失败。

如果不分类，会发生什么？

很可能：

- 重要问题被普通建议淹没。
- 开发人员不断被临时需求打断。
- 同类问题重复出现。
- 团队不知道应该先解决什么。

因此，我们首先建立一个统一的需求池（Backlog）。

#### 四、第二步：建立用户反馈分类体系

我建议先采用五种分类。

Bug / 故障

**系统功能异常**

例如：订单导出失败、库存扣减错误、登录异常。

功能需求

**希望增加新能力**

例如：批量审核、自动识别异常订单。

体验优化

**已有功能使用不顺畅**

例如：订单搜索不方便、操作步骤过多。

性能问题

**系统响应速度或处理能力不足**

例如：订单列表加载缓慢、大批量导出超时。

业务规则调整

**业务流程或规则发生变化**

例如：订单审核条件调整、取消订单规则变化。

这里有一个细节：

同一条反馈可能涉及多个分类。

例如：

「订单批量导出时经常超时，希望增加异步导出。」

它可能同时涉及性能问题和功能需求。

建议给每条反馈设置一个主分类和若干辅助标签，而不是强行把复杂问题归入唯一类别。

#### 五、第三步：建立统一需求池

需求池是保存所有待分析、待开发、待验证需求的地方。

建议每条需求至少包含以下字段：

| **字段** | **作用** |
| --- | --- |
| 需求编号 | 唯一标识 |
| 需求名称 | 简短描述 |
| 反馈来源 | 谁提出的 |
| 所属模块 | 订单、库存、售后等 |
| 需求分类 | Bug、功能、体验等 |
| 问题描述 | 用户真正遇到什么问题 |
| 业务影响 | 造成什么损失 |
| 证据 | 访谈、数据、日志 |
| 优先级 | P0、P1、P2、P3 |
| 状态 | 待分析、待评审、待开发等 |

### 六、第四步：学习需求优先级 P0～P3

这是软件项目管理中非常重要的能力。

| **优先级** | **定义** | **处理方式** |
| --- | --- | --- |
| P0 | 核心业务中断、严重数据安全问题 | 立即处理 |
| P1 | 重要业务受损、影响较大 | 尽快安排 |
| P2 | 有价值的功能或体验优化 | 纳入迭代计划 |
| P3 | 低影响、非紧急的优化建议 | 暂缓或观察 |

例如：

- 库存扣减错误导致超卖：可能是 P0。
- 订单列表持续加载缓慢：通常是 P1。
- 增加批量审核：根据业务收益评估，可能是 P1 或 P2。
- 修改按钮颜色：通常是 P3。

注意，P0～P3 是团队的管理约定，不是行业统一标准。严重故障要依据影响范围、数据风险和业务损失确定等级。

#### 1. Bug 优先级和功能优先级要分开考虑

这里是一个重要知识点。

Bug 优先级主要看：

- 影响范围。
- 严重程度。
- 是否阻断核心业务。
- 是否造成数据损坏。
- 是否有临时替代方案。

功能需求优先级主要看：

- 能覆盖多少用户。
- 能产生多大业务价值。
- 用户问题有多严重。
- 实现需要多少成本。

不能因为某个用户提出了很多次，就自动将它排到最高优先级。

### 七、第五步：使用 RICE 模型排序需求

当多个功能都值得开发时，怎么判断先做哪个？

可以使用 RICE 模型。

RICE 是一种需求优先级评估方法，包含四个维度：

| **维度** | **英文** | **含义** |
| --- | --- | --- |
| 覆盖人数 | Reach | 在一个统计周期内影响多少用户 |
| 影响程度 | Impact | 对每个用户的影响有多大 |
| 信心程度 | Confidence | 我们对判断有多大把握 |
| 实现成本 | Effort | 需要多少人月投入 |

计算公式：

RICE=(Reach × Impact × Confidence) ÷ (Effort)RICE=EffortReach×Impact×Confidence​

其中 Confidence 使用 0～1 的数值。

##### 1. 影响程度评分

可以采用如下教学评分：

| **分值** | **影响程度** |
| --- | --- |
| 3 | 极大影响 |
| 2 | 高影响 |
| 1 | 中等影响 |
| 0.5 | 较小影响 |
| 0.25 | 极小影响 |

##### 2. 订单系统需求评分

假设有三个候选需求：

- A：批量审核订单。
- B：异常订单自动识别。
- C：优化订单页面颜色。

我们进行模拟评估：

| **需求** | **Reach** | **Impact** | **Confidence** | **Effort** |
| --- | --- | --- | --- | --- |
| 批量审核 | 80 | 2 | 0.8 | 4 |
| 异常识别 | 40 | 3 | 0.9 | 3 |
| 页面优化 | 100 | 0.25 | 0.9 | 2 |

计算结果：

#### RICE 需求优先级排名

**1. 异常订单自动识别**

### 36

**2. 批量审核订单**

### 32

**3. 页面颜色优化**

### 11.25

分数仅用于模拟。Reach 代表同一统计周期内的用户数，Effort 使用人月。

计算过程：

A=(40 × 3 × 0.9) ÷ (3)=36A=340×3×0.9​=36

B=(80 × 2 × 0.8) ÷ (4)=32B=480×2×0.8​=32

但要特别注意：

**RICE 不能覆盖紧急故障和强制性业务要求。**

例如，库存超卖问题即使 RICE 分数很低，也应该因为数据风险被优先处理。

### 八、第六步：结合 MoSCoW 制定迭代计划

RICE 适合比较需求价值与成本。

MoSCoW 则适合确定一个版本必须做什么、可以做什么。

它将需求分成四类：

| **分类** | **含义** | **订单系统示例** |
| --- | --- | --- |
| Must Have | 必须实现 | 修复库存扣减错误 |
| Should Have | 应该实现 | 异常订单识别 |
| Could Have | 可以实现 | 批量审核 |
| Won't Have | 本次不做 | 页面颜色调整 |

两种方法可以结合使用：

- 先用 Must Have 识别不可推迟的需求。
- 再用 RICE 比较其他候选需求。
- 最后根据团队资源制定版本计划。

### 第六课 · 1.5 数据分析与问题诊断

本节目标：从业务数据发现问题，定位根因

#### 三、第一步：理解数据分析的真正目的

假设你负责的订单管理系统已经运行一个月。

老板告诉你：

> 最近订单处理效率下降了，你分析一下是什么原因。

你会怎么做？

不应该马上打开数据库，随便写几条 SQL。

而是先明确：

1. 具体哪个指标下降？
2. 从什么时候开始下降？
3. 下降了多少？
4. 影响哪些用户或业务环节？
5. 有什么证据能够解释变化？

数据分析不是单纯统计数字，而是利用数据回答业务问题。

#### 四、建立数据分析的六步法

#### 业务问题分析六步法

1. **明确分析目标**

这次分析究竟想解决什么业务问题？

2. **定义核心指标**

用什么指标衡量问题？计算口径是什么？

3. **收集业务数据**

需要哪些表、字段、时间范围？

4. **分析指标变化**

按时间、用户、部门、业务类型拆解。

5. **定位问题根因**

通过数据和业务流程验证原因。

6. **提出改善方案**

制定动作，并通过后续指标验证效果。

这六步以后可以直接用于你的售后分析看板、反爬分析看板和商小智经营分析项目。

#### 五、第二步：学会定义分析指标

我们继续使用订单管理系统。

老板说「订单处理效率下降」，这句话还不够具体。

我们需要将它转换为可分析的指标。

例如：

| **业务问题** | **分析指标** |
| --- | --- |
| 订单处理变慢 | 平均订单处理时长 |
| 订单积压 | 待处理订单数量 |
| 订单处理失败 | 订单处理失败率 |
| 员工效率下降 | 人均完成订单数 |
| 订单质量下降 | 订单错误率 |

##### 1. 确定指标口径

以平均订单处理时长为例：

平均处理时长 = (所有订单有效处理时长之和) ÷ (完成订单数)平均处理时长=完成订单数所有订单有效处理时长之和​

这里要明确：

- 统计对象：正常业务订单。
- 统计周期：自然周。
- 开始时间：订单进入处理中。
- 结束时间：订单处理完成。
- 排除范围：测试订单、无效订单。

##### 2. 区分结果指标和过程指标

例如：

**结果指标**

### 平均处理时长：6 分钟

最终结果：订单处理变慢了。

**过程指标**

| **环节** | **平均耗时** |
| --- | --- |
| 订单创建 | 1 分钟 |
| 订单审核 | 3 分钟 |
| 库存确认 | 1 分钟 |
| 订单完成 | 1 分钟 |

模拟数据。通过拆解过程，寻找结果指标变化的来源。

这是一个非常重要的分析思维：

**结果指标告诉你问题发生了，过程指标帮助你找到问题发生在哪里。**

### 六、第三步：学会数据拆解与下钻分析

这是数据分析中最重要的技能之一。

假设订单处理时长从 4 分钟上升到 6 分钟。

你不能马上认为所有员工效率都下降了。

应该从不同维度拆解。

#### 1. 按时间拆解

观察每天的变化：

每日平均订单处理时长

模拟数据，单位：分钟

你发现周五开始明显上升。

接下来就要调查：

- 周五是否发布了新版本？
- 是否调整了订单审核规则？
- 是否出现订单量激增？
- 是否有人员排班变化？

#### 2. 按部门拆解

假设不同部门的数据如下：

| **部门** | **上周** | **本周** |
| --- | --- | --- |
| A 部门 | 4 分钟 | 4.2 分钟 |
| B 部门 | 4 分钟 | 4.5 分钟 |
| C 部门 | 4 分钟 | 9 分钟 |

重点异常：C 部门

我们发现整体处理时长上升，可能主要由 C 部门贡献。

接下来应该重点调查 C 部门的工作流程，而不是要求所有部门提高效率。

#### 3. 按业务类型拆解

假设：

| **订单类型** | **上周耗时** | **本周耗时** |
| --- | --- | --- |
| 普通订单 | 4 分钟 | 4.2 分钟 |
| 批量订单 | 5 分钟 | 9 分钟 |
| 异常订单 | 8 分钟 | 8.5 分钟 |

这里可能发现批量订单处理耗时明显增加。

下一步可以继续调查：

- 批量订单审核规则是否发生变化？
- 是否需要逐条检查？
- 是否存在批量导入数据质量问题？
- 是否出现系统性能问题？

#### 4. 三种常用下钻维度

#### 业务数据下钻分析

**订单处理时长上升**

**时间**

哪天开始？

**组织**

哪个部门？

**业务**

哪类订单？

**定位具体异常环节**

进一步查看订单、操作记录和系统日志

这种方法叫维度下钻分析。

它可以帮助你从整体指标逐渐定位到具体业务场景。

### 七、第四步：学会使用 MySQL 分析业务数据

既然我们之前一直使用 React + FastAPI + MySQL 开发订单系统，现在就把数据分析落到 SQL 上。

假设订单表结构如下：

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    order_no VARCHAR(64),
    department_id BIGINT,
    order_type VARCHAR(32),
    status VARCHAR(32),
    process_started_at DATETIME,
    completed_at DATETIME,
    is_test TINYINT DEFAULT 0
);
```

##### 1. 统计每周订单处理时长

```sql
SELECT
    COUNT(*) AS completed_orders,
    ROUND(
        AVG(
            TIMESTAMPDIFF(
                SECOND,
                process_started_at,
                completed_at
            )
        ) / 60,
        2
    ) AS avg_minutes
FROM orders
WHERE status = 'completed'
  AND is_test = 0
  AND process_started_at IS NOT NULL
  AND completed_at IS NOT NULL
  AND completed_at >= '2026-11-16'
  AND completed_at < '2026-11-23';
```

##### 2. 按部门分析

```sql
SELECT
    department_id,
    COUNT(*) AS order_count,
    ROUND(
        AVG(
            TIMESTAMPDIFF(
                SECOND,
                process_started_at,
                completed_at
            )
        ) / 60,
        2
    ) AS avg_minutes
FROM orders
WHERE status = 'completed'
  AND is_test = 0
GROUP BY department_id
ORDER BY avg_minutes DESC;
```

##### 3. 按订单类型分析

```sql
SELECT
    order_type,
    COUNT(*) AS order_count,
    ROUND(
        AVG(
            TIMESTAMPDIFF(
                SECOND,
                process_started_at,
                completed_at
            )
        ) / 60,
        2
    ) AS avg_minutes
FROM orders
WHERE status = 'completed'
  AND is_test = 0
GROUP BY order_type
ORDER BY avg_minutes DESC;
```

这些 SQL 可以帮助你快速发现不同部门和订单类型之间的差异。

但要注意一个分析陷阱：

**平均值可能掩盖问题。**

例如：

- 90 笔订单处理时间是 2 分钟。
- 10 笔订单处理时间是 20 分钟。

平均处理时间是 3.8 分钟，但有 10% 的订单处理得非常慢。

因此，建议同时观察：

- 平均值（AVG）。
- 中位数（P50）。
- P90。
- P95。
- 最大值。

对于售后解决时长分析，也应该使用类似方法，避免少数超长案例被平均值掩盖。

### 八、第五步：从数据异常定位真正根因

现在假设我们分析出：

- 整体订单处理时间从 4 分钟增加到 6 分钟。
- C 部门从 4 分钟增加到 9 分钟。
- C 部门主要处理批量订单。
- 批量订单需要人工逐条审核。

我们现在有了一个初步假设：

> 批量订单审核流程可能是订单处理时长上升的主要原因。

但是，注意：

**发现相关性，不代表证明了因果关系。**

我们还需要进一步验证。

#### 1. 使用 5 Whys 分析

#### 订单处理效率下降的根因分析

1. **为什么处理时长增加？**

C 部门处理时间明显增加。

2. **为什么 C 部门处理时间增加？**

批量订单审核耗时增加。

3. **为什么批量订单审核耗时增加？**

需要逐条核对订单信息。

4. **为什么需要逐条核对？**

系统没有自动筛选异常订单。

5. **为什么没有自动筛选？**

之前没有识别和验证批量订单审核的业务需求。

这里得到一个候选根因：

系统缺少批量订单异常识别能力。

#### 2. 设计验证方案

不能直接开始开发，需要验证：

| **验证内容** | **验证方法** |
| --- | --- |
| 批量订单是否更耗时 | 对比不同订单类型耗时 |
| 是否存在大量异常订单 | 统计异常订单占比 |
| 人工审核是否造成延迟 | 观察各审核环节耗时 |
| 自动识别是否可行 | 使用历史订单回放测试 |
| 自动识别是否有价值 | 估算节省时间和误报成本 |

例如，历史数据回放发现：

- 每天 200 笔批量订单。
- 40 笔存在异常。
- 人工筛查平均需要 30 分钟。
- 自动识别预计能减少 20 分钟人工工作。

这时，才有比较充分的证据支持开发异常订单识别功能。

### 九、第六步：从分析结论转化为产品需求

数据分析最终不是为了写一份漂亮的报告，而是为了推动业务改善。

我们把刚才的案例整理成一个完整分析报告。

#### 订单处理效率下降分析报告

模拟分析案例

**1. 分析目标**

找出订单平均处理时长从 4 分钟上升到 6 分钟的原因。

**2. 数据发现**

- C 部门处理时长从 4 分钟增加到 9 分钟。
- C 部门主要处理批量订单。
- 批量订单需要人工逐条审核。

**3. 初步根因**

系统缺少批量订单异常识别能力，导致人工审核工作量较大。

**4. 改善方案**

- 增加异常订单自动识别。
- 增加异常订单筛选。
- 支持符合规则的普通订单批量审核。

**5. 验收指标**

| **指标** | **改善目标** |
| --- | --- |
| 批量订单审核耗时 | 降低 40% |
| 异常订单识别准确率 | ≥ 95% |
| 人工审核工作量 | 降低 30% |
| 订单错误率 | 不高于改善前 |

**6. 效果验证**

上线后观察 2～4 周，对比上线前后的数据，并结合用户访谈确认改善效果。

这里还有一个重要的分析原则：

如果上线后订单处理时间下降，不能马上认定完全是新功能带来的。

还需要排除订单结构变化、人员调整、业务量变化等因素。条件允许时，可以通过分组对比或 A/B 测试增强因果判断。

2. 误报率。
3. 漏报率。
4. 人工复核成本。
5. 自动化带来的时间收益。

### 第六课 · 1.6 需求优先级、迭代规划与版本管理

本节目标：把业务问题变成可执行的版本计划

#### 三、第一步：理解为什么需要迭代规划

假设经过前面的分析，我们已经收集到以下需求：

| **编号** | **需求** | **业务价值** |
| --- | --- | --- |
| REQ-001 | 修复库存扣减错误 | 防止库存超卖 |
| REQ-002 | 优化订单列表性能 | 提升查询效率 |
| REQ-003 | 异常订单自动识别 | 减少人工筛查 |
| REQ-004 | 批量审核订单 | 减少重复操作 |
| REQ-005 | 优化页面视觉 | 改善使用体验 |

现在团队只有：

- 2 名开发人员。
- 1 名测试人员。
- 1 名产品负责人。
- 每个迭代周期 2 周。

问题来了：

**这五项需求应该全部放进下一个版本吗？**

显然不应该。

因为团队资源有限，而且不同需求之间可能存在依赖关系。

迭代规划就是：

在有限的人力和时间内，选择最值得做的事情，安排合理的开发顺序，并明确每个版本要实现的业务目标。

#### 四、第二步：确定版本目标，而不是简单堆功能

这是产品迭代最重要的思维。

不推荐这样制定版本：

```text
V1.2.0
- 增加批量审核
- 增加订单筛选
- 增加异常识别
- 优化页面颜色
- 修改订单列表
```

因为这些只是功能清单，没有说明版本解决了什么问题。

更推荐这样制定：

#### 版本 V1.2.0

版本目标

**降低批量订单审核耗时，提升订单处理效率。**

**核心需求：**

- 异常订单自动识别。
- 异常订单筛选。
- 符合规则的普通订单批量审核。

**验收目标：**

- 批量订单平均审核耗时降低 30%。
- 异常订单识别准确率达到约定标准。
- 不出现严重漏报。
- 不影响原有订单审核流程。

这样团队知道：

- 为什么开发。
- 开发什么。
- 什么情况下算完成。
- 上线后如何判断成功。

#### 五、第三步：确定需求优先级

我们把前面学过的 P0～P3、RICE 和 MoSCoW 结合起来。

##### 1. 先判断紧急程度

| **需求** | **优先级** | **原因** |
| --- | --- | --- |
| 库存扣减错误 | P0 | 已造成超卖 |
| 订单列表性能优化 | P1 | 影响大量用户 |
| 异常订单自动识别 | P1 | 明显影响业务效率 |
| 批量审核 | P2 | 效率优化 |
| 页面视觉优化 | P3 | 非核心需求 |

这里有个重要区别：

P0 是需要立即控制和处理的生产风险，不应该等到下一个常规迭代。

因此，REQ-001 应该作为紧急修复（Hotfix）处理，修复后再进入正常迭代规划。

##### 2. 使用 RICE 比较普通需求

假设库存问题已经修复，我们再比较其他需求。

#### 需求价值评估表

| **需求** | **Reach** | **Impact** | **Confidence** | **Effort** |
| --- | --- | --- | --- | --- |
| 订单性能优化 | 80 | 2 | 0.9 | 3 |
| 异常订单识别 | 40 | 3 | 0.9 | 3 |
| 批量审核 | 80 | 2 | 0.8 | 4 |
| 页面视觉优化 | 100 | 0.25 | 0.9 | 2 |

**RICE 计算结果**

| **需求** | **分数** | **排名** |
| --- | --- | --- |
| 异常订单识别 | 36 | 1 |
| 订单性能优化 | 48 | 2 |
| 批量审核 | 32 | 3 |
| 页面视觉优化 | 11.25 | 4 |

注：分数公式为 Reach × Impact × Confidence ÷ Effort。表中排序按分数从高到低；数据为模拟值。

注意，这里的订单性能优化分数是 48，高于异常订单识别的 36。

所以如果没有其他约束，性能优化应该排在前面。

这也说明：不要凭感觉排序，要根据评分结果和业务风险共同决策。

| **角色** | **人数** |

| 后端开发 | 1 |
| 前端开发 | 1 |
| 测试人员 | 1 |

可以使用人日（Person-Day）作为初步估算单位。

| --- | --- | --- | --- | --- |
| 订单列表性能优化 | 1 | 3 | 1 | 5 |

因此不能把所有理论工作时间都排满。

- 异常订单规则梳理
- 异常识别后端开发

- 回归测试与用户验收
- 灰度发布与上线观察

实际项目中还要考虑任务依赖。例如异常识别规则未确认之前，后端不应该直接开始完整开发。

#### 七、第五步：管理版本号

软件迭代不仅要管理需求，还需要管理版本。

我们使用比较常见的语义化版本管理方式（Semantic Versioning）。

版本格式：

MAJOR.MINOR.PATCHMAJOR.MINOR.PATCH

例如：

### V1.2.3

### 1

**MAJOR**

不兼容的重大变更

### 2

**MINOR**

新增向后兼容功能

### 3

**PATCH**

向后兼容的问题修复

举例：

| **版本** | **变更** |
| --- | --- |
| V1.0.0 | 订单系统首次正式发布 |
| V1.0.1 | 修复订单查询 Bug |
| V1.1.0 | 增加订单批量审核 |
| V1.2.0 | 增加异常订单识别 |
| V2.0.0 | 对外 API 出现不兼容变更 |

注意：版本号规则是项目管理约定，数据库迁移和应用回滚还需要单独管理。

##### 1. Git 如何管理版本？

每个正式发布版本都应该有一个 Git Tag。

例如：

```bash
# 查看所有版本标签
git tag

# 创建版本标签
git tag -a v1.2.0 -m "Release v1.2.0"

# 推送标签
git push origin v1.2.0
```

后续可以通过标签追踪：

- 哪个 Git Commit 对应哪个版本。
- 哪些需求进入了这个版本。
- 哪些 Bug 在这个版本修复。
- 哪个版本是当前生产版本。

##### 2. 建立 CHANGELOG

每次发布都记录变更。

```md
# Changelog

## [1.2.0] - 2026-11-20

### Added
- 增加异常订单自动识别
- 增加异常订单筛选

### Improved
- 优化订单列表查询性能

### Fixed
- 修复订单库存扣减异常

### Database
- 增加异常订单识别记录表
```

这份文件不仅方便开发人员，也方便测试人员、运营人员和管理者了解每次版本变更。

### 八、第六步：建立版本发布与迭代管理流程

一个版本从需求确定到正式上线，应该经过完整的流程。

#### 版本迭代生命周期

1. **需求评审**

确认业务价值、优先级和验收标准。

2. **迭代规划**

确定版本范围、工作量和负责人。

3. **开发实现**

开发功能、代码评审、持续集成。

4. **测试验证**

功能、接口、回归、性能测试。

5. **版本发布**

构建镜像、灰度发布、生产部署。

6. **运营观察**

监控错误率、性能、业务指标。

7. **迭代复盘**

检查目标达成情况，进入下一轮规划。

#### 1. 定义版本发布条件

不是开发完成就能发布。

建议制定以下发布门槛：

| **检查项** | **发布条件** |
| --- | --- |
| 功能开发 | 所有计划功能完成 |
| 自动化测试 | 核心测试通过 |
| Bug | 无未解决的阻断级缺陷 |
| 数据库迁移 | 已验证兼容性和恢复方案 |
| 性能 | 满足约定的性能标准 |
| 业务验收 | 运营人员确认符合需求 |
| 回滚 | 已准备并验证恢复方案 |

#### 2. 什么是灰度发布？

灰度发布是让新版本先服务一小部分用户，再逐步扩大范围。

例如：

#### V1.2.0 灰度发布计划

1. **第一阶段：5% 用户**

小范围验证

验证核心功能、错误率和业务数据。

2. **第二阶段：20% 用户**

观察更多真实业务场景。

3. **第三阶段：50% 用户**

评估性能、稳定性和用户反馈。

4. **第四阶段：100% 用户**

全量发布

确认没有重大异常后扩大到全部用户。

灰度比例只是示例，实际需要根据用户规模、流量、业务风险和系统架构确定。

如果出现以下情况，应暂停扩大范围：

- API 错误率明显上升。
- 订单处理时间明显变长。
- 库存异常增加。
- 自动识别漏报率超出容忍范围。

特别是订单和库存系统，灰度期间还要考虑不同版本同时操作同一业务数据时的兼容性。

### 第六课 · 1.7 版本迭代复盘与持续改进

本节最后一课

进入软件持续改进阶段

今天我们解决一个非常重要的问题：

**一个软件版本发布以后，如何判断它是否成功？如果效果不理想，下一轮应该怎么改进？**

很多团队有一个误区：

开发完成 → 测试通过 → 发布上线 → 关闭任务。

但这只完成了技术交付，没有完成业务闭环。

真正完整的软件迭代应该是：

需求提出 → 开发实现 → 测试验证 → 发布上线 → 运营观察 → 效果复盘 → 下一轮迭代。

### 三、第一步：理解什么是版本复盘

假设订单管理系统发布了 V1.2.0。

这个版本主要完成两个功能：

1. 优化订单列表查询性能。
2. 增加异常订单自动识别。

发布之前，我们设定了目标：

| **指标** | **上线前** | **目标** |
| --- | --- | --- |
| 订单列表加载时间 | 5 秒 | 2 秒以内 |
| 异常订单识别准确率 | 无自动识别 | ≥95% |
| 人工筛查时间 | 30 分钟/天 | 15 分钟/天 |
| 订单错误率 | 2% | 不高于 2% |

现在版本已经上线两周。

我们需要回答四个问题：

- 版本目标是否完成？
- 哪些功能真正产生了价值？
- 哪些问题没有解决？
- 下一版本应该做什么？

这就是版本复盘（Release Retrospective）。

#### 1. 版本复盘与开发验收有什么区别？

| **开发验收** | **版本复盘** |
| --- | --- |
| 功能是否实现 | 业务目标是否达成 |
| 接口是否正常 | 用户是否真正使用 |
| 测试是否通过 | 业务效率是否改善 |
| Bug 是否修复 | 是否产生预期价值 |
| 是否可以发布 | 下一版本如何改进 |

记住：

**验收关注交付质量，复盘关注业务结果和改进机会。**

### 五、第三步：如何判断一个版本是否成功？

我们可以把版本成果分为三个层次。

第一层：交付成功

**功能是否按计划开发完成？**

代码、接口、页面、数据库变更是否符合要求。

第二层：使用成功

**用户是否真正使用新功能？**

功能使用率、任务完成率、用户反馈。

第三层：业务成功

**是否产生预期业务价值？**

效率提升、成本降低、错误减少。

例如：

异常订单识别功能：

- 交付成功：功能已经开发完成。
- 使用成功：运营人员每天都在使用。
- 业务成功：人工筛查时间减少 60%，且业务风险没有增加。

这三个层次需要分别验证。

**一个功能可以交付成功，但使用失败；也可以使用率很高，却没有产生预期业务价值。**

### 六、第四步：学习 PDCA 持续改进

PDCA 是一种持续改进方法。

它可以应用于软件版本迭代、业务流程优化、运营管理和质量管理。

#### PDCA 持续改进循环

### P

**Plan · 计划**

发现问题、设定目标、制定方案。

### D

**Do · 执行**

开发功能、实施优化。

### C

**Check · 检查**

比较实际数据和预期目标。

### A

**Act · 改进**

总结经验、修正问题、进入下一轮。

四个阶段循环执行，不是一次性的项目流程。

##### 用订单系统理解 PDCA

| **阶段** | **实际工作** |
| --- | --- |
| P | 发现批量订单审核耗时长，设定减少 30% 的目标 |
| D | 开发异常订单自动识别 |
| C | 对比上线前后审核耗时、识别效果 |
| A | 优化识别规则，安排下一版本 |

这里最关键的是 A 阶段。

如果发现某个方案有效，就把它沉淀为标准流程；如果没有效果，就调整方案，而不是重复做同样的事情。

### 七、第五步：如何组织一次版本复盘会议？

一个有效的复盘会议，不是大家轮流汇报「我做了什么」，而是围绕目标、结果、问题和改进展开。

建议控制在 45～60 分钟。

#### V1.2.0 版本复盘会议

1. **10 分钟：回顾版本目标**

为什么做这个版本？原定目标是什么？

2. **15 分钟：分析指标结果**

哪些指标达标？哪些指标没有达标？

3. **10 分钟：收集用户反馈**

用户是否满意？还有哪些问题？

4. **10 分钟：分析问题原因**

哪些判断正确？哪些方案需要调整？

5. **10 分钟：确定改进任务**

下一版本具体要改什么？由谁负责？

#### 复盘时可以使用三个问题

**1. 哪些事情做得好？**

例如：

- SQL 优化明显改善查询速度。
- 异常识别减少了人工工作量。
- 灰度发布及时发现了部分误报问题。

**2. 哪些事情做得不好？**

例如：

- 部分异常订单类型识别效果不稳定。
- 用户反馈入口不够明显。
- 测试数据覆盖不足。

**3. 下一次应该如何改进？**

例如：

- 增加异常订单分类训练和回放测试。
- 增加用户反馈入口。
- 补充极端订单场景测试。

复盘应该关注系统、流程和决策的改进，而不是简单追究个人责任。

### 八、第六步：把复盘结果转化为 V1.3.0

假设 V1.2.0 已经上线。

复盘发现了三个新问题：

| **编号** | **问题** | **改进方向** |
| --- | --- | --- |
| R-001 | 特殊异常订单漏报 | 优化识别规则 |
| R-002 | 用户无法方便地反馈误报 | 增加反馈入口 |
| R-003 | 批量审核仍然需要重复操作 | 增加批量审核 |

现在我们规划 V1.3.0。

#### V1.3.0 迭代目标

**目标：提升异常订单识别质量，进一步减少人工审核工作量。**

**计划需求：**

1. 优化异常识别规则。
2. 增加误报、漏报反馈机制。
3. 增加符合规则的订单批量审核。

**验收标准：**

- 高风险异常订单漏报率达到约定阈值。
- 用户反馈可以关联具体订单。
- 批量审核操作成功率达到目标。
- 订单错误率不高于现有基准。

这就是持续迭代：

V1.2.0 解决了一批问题，同时暴露出新的改进机会，最终推动 V1.3.0。

这个判断非常准确。

| **指标** | **目标** | **实际** | **结果** |
| --- | --- | --- | --- |

这说明：

- 技术交付成功。

**你的判断体现了多指标综合评价能力。**

#### 问题 2：如何处理误报反馈？

你的选择：A。

正确

正确流程是：

1. 收集具体误报订单。
2. 分析误报类型。
3. 统计误报发生频率。
4. 找到识别规则的问题。
5. 评估改善方案。
6. 纳入下一版本计划。

这里最重要的是：用户反馈必须转化成可分析的证据。

例如：

用户说「系统经常误判」。

我们应该进一步调查：

- 哪种订单容易误判？
- 每天误判多少笔？
- 哪条识别规则触发了误报？
- 哪些业务人员受到影响？

这才是有效的需求发现。
