这是本轮最合适的访谈问题。

你已经开始具备一个项目负责人的重要能力：**不仅关注订单如何创建，还关注订单如何真正交付给客户。**

这轮我们重点解决订单管理系统的最后一段核心业务链路：

订单审核 → 仓库接单 → 拣货 → 复核 → 打包 → 发货 → 物流跟踪。

### 一、评价你的访谈思路

优秀

你的问题有三个值得肯定的地方。

1. **覆盖完整业务流程**：不是只关注发货按钮，而是调查仓库从接单到发货的全部动作。
2. **关注实际执行角色**：仓库人员才是真正执行拣货和出库的人。
3. **主动调查异常场景**：缺货、错发、物流异常往往比正常流程更容易暴露系统问题。

我特别强调一点：

订单状态变成「已发货」，不应该仅仅因为运营人员点击了一个按钮。

系统需要有明确的业务证据，例如实际出库确认、发货数量和物流信息。

### 二、模拟仓库人员回答

现在我们进入模拟访谈。

**仓库人员**

模拟回答

「我们每天会收到运营人员审核通过的订单。

目前大概这样操作：

1. 先查看待发货订单，根据商品和数量准备货物。
2. 仓库人员按照订单拣货。
3. 拣货完成后，另一个人检查商品、规格和数量。
4. 检查没问题就打包。
5. 联系快递发货，获取物流单号。
6. 把物流单号填写到订单里面。

现在有几个问题：

- 有时候仓库实际库存和系统库存不一致。
- 有时候拣货数量不正确。
- 有时候一个订单的部分商品缺货。
- 有时候物流单号填错。
- 有些订单已经打包，但快递还没有真正揽收。
- 如果发货操作失败，运营人员不知道应该怎么处理。

我们希望系统可以记录每一步操作，减少错发和漏发。」

这段回答揭示了六个业务问题：

| **编号** | **业务问题** | **潜在影响** |
| --- | --- | --- |
| WH-001 | 实物库存与系统库存不一致 | 拣货失败 |
| WH-002 | 拣货数量错误 | 错发、漏发 |
| WH-003 | 部分商品缺货 | 无法完整履约 |
| WH-004 | 物流单号错误 | 物流无法追踪 |
| WH-005 | 打包与实际揽收混淆 | 订单状态不准确 |
| WH-006 | 发货失败处理不明确 | 库存和订单状态不一致 |

其中 WH-005 特别重要。

**打包完成不等于已发货，填写物流单号也不等于快递已经揽收。**

我们必须把这些业务动作区分开。

### 三、设计仓库拣货规则

#### 1. 什么是拣货？

拣货是仓库人员按照订单明细，从仓库中找到对应商品并准备出库的过程。

例如：

#### 订单拣货任务示例

订单编号：ORD-20261120001

| **商品** | **规格** | **订单数量** | **拣货数量** |
| --- | --- | --- | --- |
| 芝士猪排 | 大份 | 2 | 2 |
| 芝士猪排 | 小份 | 1 | 1 |
| 赠品酱料 | 50g | 1 | 1 |

**拣货完成率**

### 100%

#### 2. 推荐拣货流程

**生成拣货任务**

**仓库人员领取任务**

**根据 SKU 和数量拣货**

**记录实际拣货数量**

**提交拣货结果**

#### 3. 初步拣货业务规则

| **编号** | **规则** | **定义** |
| --- | --- | --- |
| PICK-001 | 任务来源 | 从已审核且库存预留成功的订单生成 |
| PICK-002 | 商品识别 | 按内部 SKU 识别商品 |
| PICK-003 | 数量记录 | 记录订单数量与实际拣货数量 |
| PICK-004 | 任务归属 | 记录领取任务的仓库人员 |
| PICK-005 | 拣货异常 | 缺货、破损、规格不符必须记录 |
| PICK-006 | 拣货完成 | 所有要求的商品均已拣货，或异常已按规则处理 |

这里还需要区分订单与拣货任务。

一笔订单可以对应一个或多个拣货任务，尤其是多仓库发货时。

不能简单假设一笔订单永远只有一个拣货任务。

### 四、设计拣货复核规则

拣货完成后，需要复核。

建议采用双人操作：

- 仓库人员 A：负责拣货。
- 仓库人员 B：负责复核。

这样能够减少一个人既拣货又确认造成的错误。

#### 1. 复核内容

| **检查项** | **检查内容** |
| --- | --- |
| 商品 | 是否为订单指定商品 |
| SKU | 商品规格是否正确 |
| 数量 | 实际数量是否与订单一致 |
| 包装 | 是否满足包装要求 |
| 赠品 | 是否遗漏赠品 |
| 备注 | 是否存在特殊发货要求 |

#### 2. 复核结果

| **结果** | **处理** |
| --- | --- |
| 复核通过 | 进入打包环节 |
| 数量不一致 | 退回拣货处理 |
| 商品错误 | 重新拣货 |
| 商品破损 | 记录异常并更换 |
| 无法处理 | 提交仓库主管 |

#### 3. 复核业务规则

- 必须记录复核人。
- 复核人和拣货人原则上分离。
- 复核不通过不能进入正常打包流程。
- 复核结果必须保留。
- 修改拣货数量必须记录原因和修改人员。

注意：双人复核是否适用于所有订单，需要根据业务风险和仓库工作量确定。可以先对高价值、高风险或特殊商品启用强制复核。

### 五、确定部分发货规则

这是本轮最需要仔细讨论的业务问题。

假设订单购买了 3 件商品：

- 商品 A：2 件。
- 商品 B：1 件。

但是仓库发现商品 B 暂时缺货。

这时系统应该怎么办？

#### 1. 部分发货的三种方案

| **方案** | **处理方式** | **适用情况** |
| --- | --- | --- |
| A | 所有商品齐全后统一发货 | 不允许拆单的业务 |
| B | 有货商品先发，缺货商品后发 | 允许分批履约 |
| C | 有货商品先发，缺货商品取消或退款 | 不支持等待补货 |

对于我们的模拟电商业务，我建议 V1.0 优先支持方案 B，但需要运营确认。

#### 2. 部分发货示例

#### 订单 ORD-001

订单商品总数

**3 件**

| **商品** | **订单数量** | **本次发货** |
| --- | --- | --- |
| 商品 A | 2 | 2 |
| 商品 B | 1 | 0 |

累计已发货

**2 件**

剩余待发货

**1 件**

部分发货

这里必须注意：

订单整体状态不能简单地设置为「已发货」。

建议增加履约状态：

- 待发货。
- 部分发货。
- 全部发货。
- 履约异常。

订单状态和履约状态可以分别管理。

#### 3. 部分发货业务规则

| **编号** | **规则** | **定义** |
| --- | --- | --- |
| SHIP-001 | 部分发货 | 允许订单商品分批发出 |
| SHIP-002 | 发货数量 | 不得超过订单剩余待发数量 |
| SHIP-003 | 库存扣减 | 按实际发货数量扣减 |
| SHIP-004 | 剩余数量 | 继续保留未发货商品的库存预留 |
| SHIP-005 | 完成条件 | 所有订单商品完成发货或经批准取消 |
| SHIP-006 | 发货记录 | 每次发货必须生成独立发货记录 |

这意味着：

一笔订单可能对应多次发货，每次发货也可能有独立物流单号。

所以数据库设计时不能只在订单表里放一个物流单号字段。

这是一个非常重要的系统设计结论。

### 六、确定物流单号与物流跟踪规则

#### 1. 物流业务流程

#### 物流履约流程

**拣货完成**

**复核通过**

**打包完成**

**创建物流发货记录**

**快递实际揽收**

**物流运输与签收**

注意这几个状态的区别：

| **状态** | **真实含义** |
| --- | --- |
| 已拣货 | 商品已经从货架拣出 |
| 已复核 | 商品和数量已经检查 |
| 已打包 | 商品已装箱 |
| 待揽收 | 已创建物流信息，快递尚未确认接收 |
| 已揽收 | 快递已经实际接收包裹 |
| 运输中 | 快递正在运输 |
| 已签收 | 收件人或指定收货方已签收 |

**不能将创建物流单号等同于快递已经揽收。**

#### 2. 物流信息管理规则

建议每次发货至少记录：

| **字段** | **说明** |
| --- | --- |
| shipment\_id | 发货记录 ID |
| order\_id | 关联订单 |
| carrier\_code | 快递公司编码 |
| tracking\_number | 物流单号 |
| shipped\_quantity | 本次发货数量 |
| shipped\_at | 仓库实际出库时间 |
| accepted\_at | 快递揽收时间 |
| shipping\_status | 物流状态 |

同时需要保存物流轨迹：

- 物流单创建。
- 快递揽收。
- 运输中转。
- 派送中。
- 已签收。
- 运输异常。

#### 3. 物流单号校验规则

- 物流公司必须明确。
- 物流单号不能为空。
- 同一发货记录不能重复绑定多个冲突的物流单号。
- 同一物流单号不能被错误地重复绑定到无关发货记录。
- 修改物流单号必须记录修改原因。
- 物流状态更新需要进行状态和事件校验。

注意：同一个物流单号是否允许关联多个订单，要结合平台合单、包裹合并业务确认，不能简单地设置全局唯一约束。

### 七、确定发货失败与异常处理规则

现在模拟仓库人员继续补充：

> 「有时候拣货完成后，发现商品破损；有时候快递没有揽收；有时候物流单号填错了；还有时候系统显示发货失败，但实际上货物已经交给快递了。」

这句话非常关键。

因为系统的发货操作可能失败，但现实世界的货物可能已经移动。

这涉及一个重要原则：

**数据库操作失败，不代表现实世界的业务动作没有发生。**

#### 1. 发货异常分类

| **异常类型** | **示例** | **建议处理** |
| --- | --- | --- |
| 拣货异常 | 商品破损 | 重新拣货或缺货处理 |
| 复核异常 | 数量不符 | 退回重新拣货 |
| 打包异常 | 包装损坏 | 重新打包 |
| 物流异常 | 快递未揽收 | 联系快递并跟踪 |
| 单号异常 | 物流单号错误 | 授权修正并留痕 |
| 系统异常 | 发货请求超时 | 查询真实发货结果后再重试 |

#### 2. 发货失败的处理流程

#### 发货失败处理流程

**提交发货请求**

**系统发生异常或请求超时**

**核对仓库出库与快递揽收证据**

**确认已经出库**

补记结果，禁止重复扣库存

**确认尚未出库**

修复问题后重新执行

这里还要注意：

如果只是物流接口超时，不能立即重新创建物流单或重复扣减库存。

应该先查询原请求结果，再决定是否重试。

这也是我们前面学过的幂等机制在真实业务中的应用。

### 八、确定发货时的库存扣减规则

我们之前已经定义：

- 订单审核通过时预留库存。
- 订单取消时释放库存。
- 发货时扣减实际库存。

现在结合仓库流程进一步细化。

#### 1. 推荐扣减时机

我建议以仓库实际确认出库作为库存扣减的业务时点。

也就是说：

- 拣货完成：不扣减实际库存。
- 复核通过：不扣减实际库存。
- 打包完成：不扣减实际库存。
- 实际确认出库：扣减实际库存并减少预留库存。
- 快递揽收：更新物流状态，不再次扣减库存。

如果仓库已经实际将货物交给快递，但系统记录失败，需要根据出库凭证补偿记录，不能重复扣减。

#### 2. 库存扣减示例

订单预留了 10 件商品。

本次发货 6 件，剩余 4 件等待后续发货。

| **库存项目** | **发货前** | **发货后** |
| --- | --- | --- |
| 实际库存 | 100 | 94 |
| 预留库存 | 10 | 4 |
| 可用库存 | 90 | 90 |

注意，剩余 4 件仍然被订单占用，不能释放给其他订单。

#### 3. 发货扣减规则

| **编号** | **规则** | **定义** |
| --- | --- | --- |
| INV-013 | 扣减时机 | 实际出库确认时扣减 |
| INV-014 | 扣减数量 | 按本次实际出库数量 |
| INV-015 | 预留转换 | 同时减少对应预留库存 |
| INV-016 | 重复出库 | 同一出库记录不得重复扣减 |
| INV-017 | 部分发货 | 保留未发货部分的预留库存 |
| INV-018 | 出库异常 | 必须核对实际货物状态后处理 |

### 九、正式需求调研记录 V0.5

现在将第五轮访谈成果整理成正式项目资料。

**订单管理系统 · 仓库履约需求**

V0.5

**一、业务背景**

仓库目前通过人工接收订单、拣货、复核、打包和发货。存在库存不一致、错发漏发、部分缺货和物流信息错误等问题。

**二、拣货管理**

- 从已审核且预留成功的订单生成拣货任务。
- 按 SKU、规格和数量执行拣货。
- 记录拣货人员、实际数量和异常原因。
- 支持缺货、破损和数量不符处理。

**三、复核管理**

- 拣货完成后进入复核。
- 根据商品、规格、数量进行检查。
- 复核失败需要重新处理。
- 记录复核人员和复核结果。
- 高风险订单考虑强制双人复核。

**四、部分发货**

- 支持一笔订单多次发货。
- 每次发货生成独立发货记录。
- 记录本次发货商品及数量。
- 保留未发货商品对应的库存预留。
- 所有商品完成履约后更新整体履约状态。

**五、物流管理**

- 记录快递公司和物流单号。
- 区分已打包、待揽收、已揽收、运输中和已签收。
- 支持物流轨迹查询。
- 物流单号修改需要授权和审计记录。

**六、发货异常**

- 支持拣货、复核、打包和物流异常记录。
- 发货请求超时后先核对真实出库结果。
- 防止重复创建物流记录和重复扣减库存。
- 物流异常需要有处理责任人和处理结果。

**七、库存扣减**

- 实际出库确认时扣减实际库存。
- 同时减少对应预留库存。
- 部分发货按实际出库数量扣减。
- 未发货部分继续保留预留库存。
- 所有库存操作记录业务流水。

接下来需要重点训练的是：从用户描述中发现隐含规则，并追问边界条件。

例如：

「仓库已经打包，但是客户突然取消订单，怎么办？」

这个问题就涉及订单状态、库存、物流和权限多个模块。

### 十一、需求调研第 6 轮：取消订单与异常订单处理

现在进入下一轮。

模拟运营主管补充：

> 「订单处理过程中经常会遇到客户要求取消订单、商品缺货、客户修改地址、订单重复、发货失败等情况。不同状态下处理方式不一样。有时候运营人员不知道订单是否还能取消，需要找主管确认。」

这里有一个很重要的需求：

**订单取消不能只看用户有没有点击取消按钮，还要看订单当前处于什么状态。**

例如：

| **当前状态** | **可能的取消处理** |
| --- | --- |
| 待审核 | 可以申请取消 |
| 待发货 | 检查库存预留后取消 |
| 拣货中 | 需要停止拣货并处理已拣商品 |
| 已打包 | 需要仓库确认是否可以撤回 |
| 已出库 | 不能直接释放库存 |
| 已揽收 | 需要进入物流拦截或售后流程 |
| 已完成 | 通过退款或售后处理 |
