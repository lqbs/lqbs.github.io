### 一、评价你的访谈思路

优秀

你的问题有四个优点：

1. **使用真实案例**：通过实际取消订单和异常订单发现隐藏规则。
2. **关注订单状态**：不同状态下，同一个操作可能产生完全不同的结果。
3. **关注审批流程**：不是所有操作都应该由普通运营人员决定。
4. **关注处理闭环**：从发现问题到最终解决，必须能够追踪。

这里引入一个重要的软件设计概念：

**状态驱动的业务规则（State-driven Business Rules）。**

例如：

同样是修改收货地址：

- 待审核：可能允许直接修改。
- 待发货：可能需要重新确认仓库任务。
- 已打包：可能需要撤销打包。
- 已出库：不能直接修改原发货记录。
- 已签收：应该进入售后处理。

因此，不能只定义「修改订单」功能，还必须定义每种状态下允许执行什么操作。

### 二、模拟运营主管回答

现在开始模拟真实访谈。

**运营主管**

「我举几个最近发生的情况。

**案例一：待审核订单取消**

客户刚下单，订单还没有审核，客户就要求取消。这种订单我们通常直接取消，不需要找主管。

**案例二：已经审核、库存已经预留**

客户要求取消，运营人员需要取消订单，同时通知系统释放预留库存。有时候库存释放失败，需要人工处理。

**案例三：仓库已经拣货**

客户要求取消时，仓库可能已经把商品拣出来了，需要通知仓库停止处理，把商品放回原来的货位。

**案例四：已经打包但尚未交给快递**

这种情况需要仓库主管确认能不能拦截，不能直接由运营人员取消。

**案例五：已经发货**

不能直接取消，需要联系快递或者进入售后退款流程。

**案例六：修改收货地址**

订单还没拣货时一般可以修改。如果已经打包，需要找仓库确认。如果已经交给快递，就要联系快递处理。

另外，订单金额、商品数量和已经发货的订单信息不能随便修改。」

### 三、确定不同订单状态下的取消规则

#### 1. 首先区分两个概念

- 取消申请：客户或运营人员提出取消请求。
- 取消完成：系统和相关业务模块已经成功处理取消操作。

这两者不能混为一谈。

例如，一笔订单已经预留库存，取消时库存释放失败。

此时不能简单地把订单标记为已取消，然后忽略库存异常。

#### 2. 订单状态与取消规则矩阵

#### 订单取消状态规则 V0.6

| **当前状态** | **取消规则** | **库存处理** |
| --- | --- | --- |
| 待审核 | 允许取消 | 无预留则无需释放 |
| 待发货 | 检查后允许取消 | 释放全部未出库预留 |
| 拣货中 | 申请取消，停止拣货 | 确认商品归位后释放 |
| 已打包 | 主管审批 | 确认撤销打包后释放 |
| 已出库 | 不允许普通取消 | 进入物流拦截或售后 |
| 已揽收 | 不允许普通取消 | 进入物流拦截或退款 |
| 部分发货 | 不能直接整单取消 | 分别处理已发货与未发货部分 |
| 已完成 | 不允许普通取消 | 进入售后退款流程 |

注意：表中的规则是我们建议的 V0.6 业务方案，最终需要业务负责人确认。

#### 3. 取消业务流程

#### 订单取消流程

**提交取消申请**

**检查订单当前状态**

允许直接取消

**执行取消**

需要审批

**提交主管审批**

**检查仓库任务与库存预留**

**执行库存释放或履约撤销**

**取消完成并记录操作日志**

这里有一个工程上的关键点：

订单取消、仓库任务撤销、库存释放可能涉及多个模块。

建议使用可重试的业务处理机制，记录每一步执行结果。只有必要的业务动作全部完成后，才将取消流程标记为完成。

不能简单地用一次数据库 UPDATE 假装整个业务流程都成功了。

### 四、确定订单地址修改规则

地址修改和普通订单字段修改不同，因为它可能影响仓库拣货、物流面单和实际配送。

#### 1. 地址修改规则

| **订单状态** | **是否允许** | **建议处理** |
| --- | --- | --- |
| 待审核 | 允许 | 运营人员修改并留痕 |
| 待发货 | 允许 | 修改后重新确认履约信息 |
| 拣货中 | 有条件允许 | 通知仓库暂停并确认 |
| 已打包 | 需要审批 | 撤销旧面单，重新打包或打印面单 |
| 已出库 | 不允许直接修改 | 联系快递处理 |
| 已揽收 | 不允许直接修改 | 物流改址或拦截 |
| 已签收 | 不允许修改原订单 | 进入售后流程 |

#### 2. 地址修改需要记录什么？

建议记录：

| **字段** | **示例** |
| --- | --- |
| order\_id | ORD001 |
| old\_address | 杭州市地址 A |
| new\_address | 杭州市地址 B |
| change\_reason | 客户要求修改 |
| operator\_id | 1001 |
| approval\_user\_id | 2001 |
| change\_time | 修改时间 |
| fulfillment\_impact | 是否影响仓库和物流 |

还需要注意：

地址修改可能影响物流面单。

如果原面单已经生成，需要确认是否可以取消原面单、重新生成面单，避免一个包裹出现两个有效物流信息。

#### 3. 地址修改的业务规则

建议形成以下规则：

- 只能修改授权范围内的地址字段。
- 每次修改必须记录原因。
- 已打包订单修改需要仓库确认。
- 已出库订单不能直接覆盖原地址。
- 修改地址后必须同步更新后续履约任务。
- 修改失败时保留原地址和操作结果。

### 五、确定异常订单处理规则

现在我们把之前六轮访谈发现的问题进行统一管理。

#### 1. 异常类型分类

#### 订单异常分类体系

**订单数据异常**

重复订单、金额不一致、商品无法匹配、收货信息缺失。

**库存异常**

库存不足、预留失败、库存释放失败、实际库存不一致。

**仓库异常**

缺货、错发、漏发、破损、拣货失败。

**物流异常**

物流单号错误、未揽收、运输异常、配送失败。

**售后异常**

退款失败、部分退款异常、退货未入库。

#### 2. 异常处理生命周期

我建议每一条异常都具有自己的处理状态：

待处理

处理中

待验证

**已解决**

如果验证失败，可以重新进入处理中；无法解决的异常需要升级主管处理。

每条异常记录至少需要：

| **字段** | **说明** |
| --- | --- |
| exception\_id | 异常编号 |
| order\_id | 关联订单 |
| exception\_type | 异常类型 |
| description | 异常描述 |
| severity | 严重程度 |
| assignee | 处理责任人 |
| status | 处理状态 |
| solution | 解决方案 |
| created\_at | 发现时间 |
| resolved\_at | 解决时间 |

#### 3. 异常处理示例

例如：库存释放失败。

1. 订单取消请求提交。
2. 系统发现库存释放失败。
3. 创建库存异常记录。
4. 通知运营主管。
5. 相关人员核查库存预留记录。
6. 修复后重新执行释放操作。
7. 校验库存数量。
8. 关闭异常记录。

这里需要强调：异常重试必须具有幂等保护，不能因为重复执行释放操作而把库存增加两次。

### 六、确定审批权限规则

前面我们已经识别了老板、运营主管、订单运营人员和仓库人员。

现在需要明确每个角色能做什么。

#### 1. 角色权限矩阵

#### 订单管理系统权限矩阵 V0.6

| **操作** | **老板** | **主管** | **运营** | **仓库** |
| --- | --- | --- | --- | --- |
| 查看订单 | ✓ | ✓ | ✓ | ✓ |
| 创建订单 | — | ✓ | ✓ | — |
| 审核订单 | — | ✓ | — | — |
| 申请取消 | — | ✓ | ✓ | — |
| 审批特殊取消 | — | ✓ | — | — |
| 修改地址 | — | ✓ | ✓ | — |
| 拣货 | — | — | — | ✓ |
| 商品复核 | — | — | — | ✓ |
| 确认出库 | — | — | — | ✓ |
| 查看经营报表 | ✓ | ✓ | — | — |
| 查看操作日志 | ✓ | ✓ | — | — |

初始建议矩阵。最终还需根据岗位职责、数据敏感程度和公司授权制度确认。

#### 2. 特殊操作审批规则

并不是所有操作都需要主管审批。

建议采用以下原则：

| **操作** | **建议权限** |
| --- | --- |
| 待审核订单取消 | 运营人员可直接处理 |
| 待发货订单取消 | 授权运营人员可处理，异常时升级 |
| 已拣货订单取消 | 需要仓库确认 |
| 已打包订单取消 | 需要主管审批 |
| 已出库订单取消 | 不允许普通取消，转物流或售后处理 |
| 已发货地址修改 | 需要物流处理，不允许直接覆盖 |
| 金额人工调整 | 需要主管审批 |
| 库存人工调整 | 需要授权审批并记录原因 |

#### 3. 权限设计中的一个关键问题

建议把「申请权限」和「审批权限」分开。

例如：

运营人员可以申请取消订单，但不能审批自己提交的特殊取消申请。

这有助于形成职责分离。

同时，权限应该在后端接口执行，而不是只隐藏前端按钮。

### 七、确定库存释放规则

现在将取消规则和库存模块重新连接起来。

这是一个很容易出现数据不一致的地方。

#### 1. 不同订单状态下的库存处理

| **业务场景** | **库存操作** |
| --- | --- |
| 待审核订单取消 | 通常无需释放 |
| 待发货订单取消 | 释放全部未出库预留 |
| 拣货中取消 | 确认商品归位后释放 |
| 已打包取消 | 撤销打包、确认商品归位后释放 |
| 部分发货取消 | 仅处理未发货的预留数量 |
| 已出库订单 | 不允许直接释放已扣减库存 |
| 已签收后退货 | 退货验收合格后执行入库 |

#### 2. 部分发货的库存处理

例如：

订单原本预留 10 件。

已经实际发货 6 件，还剩 4 件预留。

客户要求取消剩余部分。

那么：

| **库存项目** | **取消前** | **取消后** |
| --- | --- | --- |
| 实际库存 | 94 | 94 |
| 预留库存 | 4 | 0 |
| 可用库存 | 90 | 94 |

已经发货的 6 件不应该因为取消剩余商品而恢复库存。

#### 3. 库存释放必须满足的规则

- 只能释放该订单实际预留的数量。
- 不能释放已经出库的数量。
- 同一笔库存预留只能释放一次。
- 释放操作必须关联订单和原预留记录。
- 释放失败必须创建异常记录。
- 人工调整库存不能替代正常的库存释放流程。

**订单管理系统 · 取消与异常处理**

V0.6

**一、订单取消**

- 根据订单状态控制修改权限。
- 已打包订单需要仓库确认。
- 已出库订单不允许直接覆盖地址。

**三、异常处理**

- 统一管理订单、库存、仓库、物流和售后异常。

- 异常处理过程必须保留记录。

- 区分申请人、执行人和审批人。
- 特殊取消、金额修改和库存调整需要授权。
- 普通运营人员不能越权修改已发货订单。
- 后端必须执行权限校验。

**五、库存释放**

- 只释放尚未实际出库的预留库存。
- 拣货和打包阶段需要确认商品归位。
- 部分发货只释放剩余预留数量。
- 已出库商品不能通过取消订单直接恢复库存。
- 所有释放操作必须支持幂等和审计。

### 十、需求调研第 7 轮：运营指标与系统管理要求

我们已经知道系统如何运行，但还需要回答一个问题：

**系统上线后，老板如何判断它是否真正改善了业务？**

模拟老板提出：

> 「我希望系统上线后，不仅能处理订单，还能让我知道每天有多少订单、处理效率怎么样、库存是否准确、发货是否及时、异常订单有没有及时解决。我也希望能够看到每个运营人员的工作情况。」

这轮我们需要调研运营指标、报表、系统管理和数据权限。

#### 实战问题：你会如何继续访谈老板？

#### 正式需求调研第 7 轮

运营指标与管理需求

- A. 能不能结合你日常经营决策，告诉我最需要关注哪些指标？每个指标如何计算、多久查看一次、发现异常后需要采取什么行动？
- B. 我们直接开发一个 ECharts 数据大屏。
- C. 我们先增加订单总数、销售额两个指标。
- D. 我建议所有员工都可以查看全部订单和经营数据。
