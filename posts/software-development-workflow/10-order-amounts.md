**不要让用户抽象地解释业务规则，而是让用户拿一笔真实业务数据，演示完整的计算过程。**

订单金额尤其适合这样调研，因为用户经常会把商品金额、买家实付金额、平台补贴和商家结算金额混为一谈。

### 一、评价你的访谈思路

优秀的提问方向

你的问题有三个优点：

1. 有具体对象：一笔真实发生金额不一致的订单。
2. 有明确范围：商品、优惠、补贴、运费。
3. 有验证目标：还原金额从产生到核对的完整过程。

不过，还可以进一步追问：

- 这些金额分别由哪个系统提供？
- 哪些优惠由商家承担，哪些由平台承担？
- 买家实际支付了多少钱？
- 平台最终向商家结算多少钱？
- 发生退款后，原订单金额如何变化？

这里要建立一个重要认知：

**买家实付金额 ≠ 商家结算金额 ≠ 商品原始金额。**

这三个金额必须分别管理。

### 二、模拟运营主管回答

现在进行真实场景模拟。

**运营主管**

模拟访谈

「我拿昨天的一笔拼多多订单举例。

这个订单有两件商品：

- 商品 A：50 元 × 2 件。
- 商品 B：30 元 × 1 件。

商品原价合计 130 元。

这笔订单有商家优惠 10 元，平台优惠券 5 元，运费 8 元。

用户最后实际支付了 123 元。

但是我们财务核对时，发现平台账单显示的结算金额和用户实付金额不一样。

有时候还会发生退款，例如客户只退其中一件商品。

目前我们主要依靠平台订单详情和财务账单人工核对，系统没有完整记录这些金额的来源和变化。」

#### 1. 先还原这笔订单

#### 模拟订单金额明细

订单编号：PDD20261120001

| **项目** | **金额** |
| --- | --- |
| 商品 A：50 × 2 | ¥100 |
| 商品 B：30 × 1 | ¥30 |
| 商品原价合计 | ¥130 |
| 商家优惠 | -¥10 |
| 平台优惠券 | -¥5 |
| 运费 | +¥8 |
| **用户实际支付** | **¥123** |

**计算结果**

### ¥123.00

以上是根据模拟访谈给出的示例计算，实际应以平台订单明细中的支付口径为准。

计算：

130-10-5+8=123130−10−5+8=123

目前算术关系是成立的。

但我们还没有确认平台优惠券是否全部由平台承担，以及商家是否需要承担其他费用。

因此，不能直接用 123 元作为商家收入。

#### 2. 必须区分三种金额

**商品原始金额**

### ¥130.00

商品售价 × 商品数量之和。

**买家实际支付金额**

### ¥123.00

买家实际支付给交易平台的金额。

**商家结算金额**

### 待核对

根据平台补贴、商家优惠、平台费用、退款和结算规则计算或读取。

这里是本轮最重要的发现：

如果订单系统未来还需要做利润分析，那么仅保存订单总金额是不够的。

必须保留金额构成和来源。

### 三、确定订单金额计算规则

我们把金额分为六个类别。

#### 1. 商品金额

计算规则：

商品原价金额=Σ(商品单价 × 购买数量)商品原价金额=∑(商品单价×购买数量)

需要明确：

- 商品单价使用哪个渠道的价格？
- 多件商品是否分别记录价格？
- 商品价格发生变化后，历史订单是否保持原价？

建议：正式订单创建时保存商品价格快照，不能因为商品主数据价格变化而修改历史订单金额。

#### 2. 商家优惠

例如：

- 店铺优惠券。
- 商家满减。
- 商家折扣。
- 商家承担的促销优惠。

建议记录：

- 优惠金额。
- 优惠类型。
- 优惠承担方。
- 优惠来源。
- 对应订单或商品明细。

#### 3. 平台优惠

例如平台发放的优惠券。

需要区分：

- 平台承担。
- 商家承担。
- 平台与商家共同承担。

不能把所有优惠都简单归入商家优惠。

#### 4. 运费

需要确认：

- 买家支付的运费。
- 商家承担的运费。
- 平台补贴的运费。
- 物流实际成本。

这几个金额可能不同。

#### 5. 买家实付金额

建议优先读取平台提供的订单实付金额，而不是仅凭商品价格自行推算。

因为不同平台可能存在不同的优惠分摊、运费规则和支付调整规则。

#### 6. 商家结算金额

建议优先从平台结算账单获取。

将结算金额与订单金额建立关联，支持后续财务对账。

初步数据关系：

#### 订单金额数据关系

**商品金额**

**优惠明细**

**运费与其他调整**

**买家支付金额**

**商家结算金额**

实际金额之间的计算关系必须根据平台账单口径确认，不能将两个结果简单等同。

### 四、确定退款业务规则

现在我们继续模拟运营主管回答。

**运营主管：**

「退款比较麻烦。

有时候客户购买两件商品，只申请退其中一件；有时候整笔订单取消；还有时候商品已经发货，客户收到以后才申请退款。

目前退款金额和订单金额需要人工核对，退款完成以后，订单状态也容易出现混乱。」

这里我们发现一个关键问题：

**退款不是简单地把订单状态改成已退款。**

必须区分退款申请、退款处理、退款成功，以及是否发生退货。

#### 1. 退款类型

| **退款类型** | **业务场景** | **处理方式** |
| --- | --- | --- |
| 整单退款 | 整笔订单退款 | 关联原订单 |
| 部分退款 | 只退部分商品 | 关联订单商品明细 |
| 未发货退款 | 发货前取消 | 处理库存释放 |
| 已发货退款 | 发货后申请 | 需要判断是否退货 |
| 退款失败 | 平台退款失败 | 保留失败记录，支持重试或人工处理 |

#### 2. 退款状态设计

建议退款单独建立状态机：

#### 退款状态流转

**待审核**

**退款处理中**

成功

**退款完成**

失败

**退款失败**

订单状态和退款状态应该分开管理。

例如：

一笔订单已经发货，客户申请部分退款。

这时订单仍然可能处于已发货状态，同时退款单处于退款处理中。

不能因为部分退款就把整笔订单改成已退款。

#### 3. 退款金额规则

建议建立以下计算逻辑：

剩余可退款金额 = 原订单可退款金额-累计成功退款金额剩余可退款金额=原订单可退款金额−累计成功退款金额

例如：

| **项目** | **金额** |
| --- | --- |
| 原订单实付 | ¥123 |
| 第一次成功退款 | ¥30 |
| 第二次成功退款 | ¥20 |
| 累计退款 | ¥50 |
| 剩余可退款金额 | ¥73 |

注意：

实际可退金额还要考虑退款分摊、已退款商品、运费、优惠券和平台规则。不能简单允许运营人员任意填写退款金额。

#### 4. 退款库存规则

这里要区分两个动作：

- 退款：资金退还。
- 退货入库：商品重新回到库存。

两者不一定同时发生。

例如：

- 未发货取消：通常需要释放预留库存。
- 已发货但未退货：不能直接增加库存。
- 退货验收合格：才允许按实际数量重新入库。

这将影响后面的库存模块设计。

### 五、确定订单数据修正规则

运营主管还提出：

「如果 Excel 导入错了，或者平台订单信息更新了，我们需要修改订单。有些订单已经审核或者发货，不能随便修改。」

这是一个非常重要的需求。

我们需要建立订单数据修正规则。

#### 1. 数据修正分类

| **数据类型** | **是否允许修改** | **建议规则** |
| --- | --- | --- |
| 原始平台订单数据 | 不直接覆盖 | 永久保留原始记录 |
| 商品匹配关系 | 允许 | 记录修改前后结果 |
| 收货信息 | 有条件允许 | 根据订单状态控制 |
| 商品数量 | 有条件允许 | 审核库存影响后处理 |
| 商品价格 | 有条件允许 | 保留金额调整记录 |
| 已发货订单 | 严格限制 | 不允许普通修改 |
| 退款记录 | 不允许直接覆盖 | 通过退款业务处理 |

#### 2. 建立操作审计日志

每次修改都应该记录：

| **字段** | **示例** |
| --- | --- |
| 操作对象 | 订单 PDD001 |
| 修改字段 | 收货地址 |
| 修改前 | 杭州地址 A |
| 修改后 | 杭州地址 B |
| 操作人员 | 用户 1001 |
| 修改原因 | 客户要求修改 |
| 操作时间 | 2026-11-20 14:30 |

这样以后出现业务争议，就能追溯是谁修改了什么。

#### 3. 数据修正原则

我建议确立四条原则：

1. 原始订单数据不可被普通业务操作覆盖。
2. 重要修改必须记录修改前后内容。
3. 已发货、已退款等订单必须执行状态权限校验。
4. 涉及金额、库存的修改必须产生对应的业务记录。

这里还有一个工程设计原则：

**重要业务变更应该通过业务操作完成，而不是直接修改数据库字段。**

例如，修改商品数量不仅仅是 UPDATE 订单明细，还要检查库存、订单金额、退款和履约影响。

### 八、第四轮访谈：订单审核与库存预留

接下来，我们要调查订单从创建成功到真正进入仓库处理的过程。

模拟运营主管补充：

> 「订单导入成功后，我们会先检查订单。部分订单需要主管审核，审核通过后才能交给仓库。有时候库存不足，或者多个订单同时购买同一商品，会导致库存不够。」

现在你作为项目负责人，需要继续调查。

**你首先应该问什么？**

#### 需求调研第 4 轮

订单审核与库存管理

- A. 能不能带我走一遍订单审核和库存处理的完整过程？包括审核条件、库存不足处理、库存预留，以及审核失败后怎么处理？
- B. 我们先设计订单状态枚举和库存数据库表。
- C. 我建议所有订单创建后自动审核通过。
- D. 直接开发库存预警页面。

提交访谈问题

**下一轮的学习重点：**

我们要把订单管理系统最核心的业务闭环弄清楚：

订单创建 → 订单审核 → 库存预留 → 仓库拣货 → 发货 → 完成。

尤其是库存预留、超卖防护、取消订单释放库存，这些业务规则将直接决定后面的数据库设计、事务设计和并发控制。

继续保持现在的习惯：先调查真实业务，再确定规则，最后才设计功能和代码。
