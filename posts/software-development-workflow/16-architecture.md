### 一、评价你的答案

你的思路有三个正确之处：

| **你的判断** | **架构意义** |
| --- | --- |
| 独立职责 | 高内聚 |
| 降低耦合 | 低耦合 |
| 方便维护和扩展 | 可演进性 |

举个例子。

如果所有订单、库存、商品、发货代码都写在一个 `main.py` 文件里：

```python
@app.post("/orders")
def create_order():
    # 创建订单
    # 检查库存
    # 修改库存
    # 匹配商品
    # 生成发货记录
    # 发送物流请求
    pass
```

短期可能很方便，但随着需求增加，会出现：

- 修改订单功能影响库存功能。
- 库存逻辑被多个接口重复实现。
- 单元测试困难。
- 不同开发人员容易互相修改代码。
- 业务规则越来越难以维护。

更合理的做法是按业务职责组织代码。

```text
app/
├── orders/
├── products/
├── inventory/
├── warehouse/
├── shipping/
└── users/
```

但注意：仅仅拆目录还不够，还需要明确模块之间允许调用什么、不能直接修改什么。

### 二、模块化单体架构是什么？

先理解第一个架构方案：模块化单体（Modular Monolith）。

它有两个关键词：

- 单体：整个系统作为一个应用部署。
- 模块化：内部按照业务边界划分独立模块。

#### 模块化单体架构

**一个 FastAPI 应用**

**订单模块**

创建、审核、取消

**商品模块**

商品、SKU、映射

**库存模块**

查询、预留、释放

**仓库模块**

拣货、复核、出库

**物流模块**

发货、物流单号

**权限模块**

用户、角色、授权

**共享数据库 MySQL**

各模块在同一个应用进程中运行，但通过明确的业务接口协作。

例如，运营人员审核订单时：

1. 订单模块接收审核请求。
2. 订单模块调用库存模块的预留服务。
3. 库存模块检查可用库存。
4. 库存模块执行库存预留。
5. 订单模块完成审核状态更新。

整个过程可以通过一个数据库事务保证一致性。

#### 模块化单体的优点

- 开发和部署简单。
- 数据库事务容易管理。
- 本地调试方便。
- 适合小团队。
- 不需要复杂的服务间通信。
- 运营成本相对较低。

#### 缺点

- 整个应用通常一起发布。
- 模块边界如果管理不好，容易重新变成大杂烩。
- 单体应用扩容时通常以整个应用为单位。
- 不同模块无法独立选择部署技术和发布节奏。

### 三、微服务架构是什么？

微服务（Microservices）则是另一种架构方式。

它把系统拆成多个可以独立运行、部署和扩展的服务。

#### 微服务架构

**React 前端**

**API Gateway**

统一入口、路由、认证

**订单服务**

订单生命周期

**商品服务**

商品与 SKU

**库存服务**

库存预留与扣减

**仓库服务**

拣货与复核

**物流服务**

物流与发货

**用户服务**

身份与权限

**服务间通信**

HTTP / 消息队列 / 事件

**订单数据库**

**库存数据库**

这里最重要的变化是：

不同服务有独立的运行进程，通常也拥有自己的数据存储边界。

例如订单服务需要库存时，不能直接访问库存服务的数据库，而是通过库存服务提供的 API 或消息机制完成协作。

#### 微服务的优点

- 可以独立部署。
- 可以针对热点服务单独扩容。
- 不同团队可以独立开发。
- 服务故障可以在一定程度上隔离。
- 不同服务可以独立演进。

#### 微服务的缺点

- 部署和运维复杂。
- 服务之间存在网络延迟。
- 分布式事务处理困难。
- 日志、监控和链路追踪要求更高。
- 需要处理消息重复、消息丢失和最终一致性。
- 测试和故障排查成本更高。

### 四、模块化单体与微服务的区别

| **比较维度** | **模块化单体** | **微服务** |
| --- | --- | --- |
| 部署方式 | 一个应用 | 多个服务 |
| 运行进程 | 通常一个 | 多个 |
| 数据库 | 通常共享数据库 | 服务独立拥有数据 |
| 模块通信 | 函数或服务接口 | HTTP、消息等 |
| 事务管理 | 本地数据库事务 | 通常需要最终一致性 |
| 开发成本 | 较低 | 较高 |
| 运维复杂度 | 较低 | 较高 |
| 独立扩容 | 较有限 | 更灵活 |
| 适用团队 | 小团队 | 多团队或复杂组织 |

这里有一个很重要的认知：

**微服务不是模块化单体的升级版，而是为了解决不同规模下不同的组织和工程问题。**

不要因为系统有订单、库存、商品六个模块，就认为必须建立六个微服务。

模块数量和微服务数量没有必然关系。

### 五、为订单管理系统选择架构

现在结合我们的实际项目做决策。

目前系统具有以下特点：

- 前端：React + TypeScript。
- 后端：Python + FastAPI。
- 数据库：MySQL。
- 主要业务：订单、商品、库存、仓库、物流。
- 项目团队：个人或小团队开发。
- 开发方式：AI 辅助开发，快速交付 MVP。

我建议：

**推荐方案：模块化单体**

V1.0 推荐

### Modular Monolith

**技术组合**

- React + TypeScript：前端。
- FastAPI：后端应用。
- SQLAlchemy：ORM。
- MySQL：业务数据库。
- Alembic：数据库迁移。
- Redis：根据异步任务和缓存需求决定是否引入。
- Celery：后续需要后台任务时引入。

**架构策略**

一个后端应用、一个核心数据库、清晰的业务模块边界。

为什么不直接使用微服务？

因为目前订单、库存、审核和仓库之间有大量强一致性业务。

例如一笔订单审核时，需要：

1. 检查订单状态。
2. 检查商品 SKU。
3. 预留多个 SKU 的库存。
4. 更新订单审核状态。
5. 写入库存流水。

使用模块化单体，可以在一个 MySQL 事务中处理这些操作。

如果拆成微服务，就可能需要分布式事务、补偿机制、消息可靠投递等额外设计。

对当前 MVP 来说，这些复杂度没有足够的收益。

**未来演进原则：先模块化，后服务化。**

如果将来库存模块需要独立扩容，或者团队需要独立维护库存服务，再考虑把库存模块拆出去。

### 六、设计订单管理系统整体架构

现在进入真正的架构设计。

我们不只是选择技术，还要明确系统由哪些层组成、每一层负责什么。

#### 1. 整体分层架构

#### 订单管理系统整体架构 V1.0

**表现层 Presentation**

#### React + TypeScript

订单页面 · 商品页面 · 库存页面 · 仓库工作台 · 运营看板

**接口层 API**

#### FastAPI Routers

HTTP 请求 · 参数验证 · 身份认证 · 权限校验

**业务应用层 Application**

订单应用服务

库存应用服务

商品应用服务

仓库应用服务

物流应用服务

用户应用服务

**领域业务层 Domain**

订单规则 · 库存规则 · 状态流转 · 业务约束

**基础设施层 Infrastructure**

SQLAlchemy · MySQL · Redis（可选）· 文件存储 · 外部平台接口

我们逐层理解。

##### 第一层：表现层

负责用户看到的界面。

例如：

- 订单列表。
- 订单详情。
- Excel 导入页面。
- 商品管理页面。
- 库存管理页面。
- 仓库拣货工作台。
- 经营总览。

这一层不应该直接实现库存扣减、订单取消等核心业务规则。

##### 第二层：接口层

负责接收前端请求。

例如：

```http
POST /api/v1/orders
POST /api/v1/orders/{id}/approve
POST /api/v1/orders/{id}/cancel

GET /api/v1/inventory
POST /api/v1/inventory/reservations
POST /api/v1/shipments
```

接口层主要负责：

- 请求参数校验。
- 身份认证。
- 权限检查。
- 调用应用服务。
- 返回统一响应。

##### 第三层：业务应用层

负责组织一次完整业务操作。

例如订单审核服务：

```python
def approve_order(order_id, operator_id):
    # 1. 获取订单
    # 2. 检查订单状态
    # 3. 校验订单商品
    # 4. 调用库存服务预留库存
    # 5. 更新订单状态
    # 6. 记录审核日志
    pass
```

这里的示例只是业务流程示意，真正实现时需要加入事务、并发控制和幂等机制。

##### 第四层：领域业务层

负责最核心的业务规则。

例如：

- 待审核订单能否取消？
- 预留库存能否超过实际库存？
- 已出库订单能否直接取消？
- 部分发货后剩余库存如何处理？

这些规则不能分散在多个 API 路由中。

##### 第五层：基础设施层

负责具体技术实现：

- 数据库连接。
- ORM 映射。
- 数据库事务。
- 缓存。
- 文件上传。
- 第三方物流接口。

这样以后更换数据库或物流接口，不需要重写所有业务逻辑。

### 七、确定系统业务模块边界

接下来是本课最重要的部分。

我们不能只按页面划分模块，而要按业务职责划分。

我建议第一期划分为八个模块。

#### 订单管理系统业务模块

**01. 订单模块 Orders**

核心模块

订单创建、导入、审核、取消、订单状态管理。

**02. 商品模块 Products**

核心模块

商品、SKU、规格、渠道商品映射。

**03. 库存模块 Inventory**

核心模块

库存查询、预留、释放、扣减、库存流水。

**04. 仓库模块 Warehouse**

核心模块

拣货任务、复核、打包、出库确认。

**05. 物流模块 Shipping**

核心模块

发货记录、物流单号、物流状态。

**06. 用户与权限模块 Users**

用户、角色、功能权限、数据权限。

**07. 异常管理模块 Exceptions**

异常创建、任务分派、处理记录、关闭。

**08. 经营分析模块 Analytics**

订单统计、履约指标、库存指标、运营报表。

#### 模块之间如何协作？

以订单审核为例：

```text
订单模块
   │
   ├── 查询商品模块：确认 SKU 有效
   │
   ├── 调用库存模块：预留库存
   │
   └── 更新订单状态：审核通过
```

这里有一个重要的架构约束：

**订单模块可以调用库存模块提供的业务接口，但不能直接修改库存模块的数据表。**

反过来也一样。

库存模块不应该直接修改订单表中的订单状态。

这就是模块边界。

### 八、设计模块依赖关系

模块划分完成后，还要决定谁可以调用谁。

建议采用以下依赖关系：

这张图表达了几个重要原则：

1. API 层负责接收请求，不直接操作业务表。
2. 订单模块负责订单生命周期。
3. 库存模块负责库存数量和库存流水。
4. 仓库模块负责实际履约过程。
5. 物流模块负责发货和物流信息。
6. 分析模块读取业务数据，不直接修改订单或库存。

#### 1. 禁止跨模块直接修改数据

错误做法：

```python
# orders/service.py
def approve_order(order_id, db):
    order = db.query(Order).get(order_id)
    # 直接修改库存模块的数据
    inventory = db.query(Inventory).get(1001)
    inventory.reserved_quantity += 5
```

问题在于：

订单模块直接知道了库存表结构和库存更新细节。

如果以后库存预留规则发生变化，订单模块也可能需要修改。

推荐做法：

```python
# orders/service.py
def approve_order(order_id, db):
    order = get_order(order_id, db)
    inventory_service.reserve(
        db=db,
        order_id=order.id,
        items=order.items
    )
    order.status = "pending_shipment"
```

这里的 `inventory_service.reserve()` 是库存模块公开的业务接口。

真实实现还需要确保订单状态检查、库存预留和订单状态更新处于正确的事务边界中。

#### 2. 事务应该由谁管理？

对于模块化单体，这是一个非常重要的设计问题。

建议：

**由一次完整业务操作的应用服务统一管理事务，底层模块服务参与事务，但不要随意自行提交。**

例如：

```python
def approve_order(order_id, db):
    try:
        # 检查订单状态
        order = order_service.get_for_update(db, order_id)
        # 库存预留
        inventory_service.reserve(
            db=db,
            order_id=order_id,
            items=order.items
        )
        # 更新订单状态
        order_service.mark_approved(db, order)
        # 统一提交
        db.commit()
    except Exception:
        db.rollback()
        raise
```

这样才能避免：

- 库存已经预留，订单却没有审核成功。
- 订单审核成功，库存却没有预留。
- 订单中有多个 SKU，只成功预留了一部分。

注意：上面的代码是事务设计示意，实际代码还需要处理重复审核、并发状态竞争、异常分类和库存流水幂等。

### 十、设计系统部署架构

软件架构不仅包括代码，还包括运行环境。

第一期可以采用这样的部署方案：

#### 生产环境部署架构 V1.0

**用户浏览器**

React 前端

**Nginx**

HTTPS · 静态资源 · API 反向代理

**FastAPI 应用容器**

模块化单体后端

**MySQL**

核心业务数据

**Redis（可选）**

缓存、任务协调

**备份、日志和监控**

第一期建议：

- Nginx 负责 HTTPS 和反向代理。
- FastAPI 作为一个应用部署。
- MySQL 存储核心业务数据。
- Redis 根据实际需要引入。

### 十二、本课最终学习成果

今天你完成了订单管理系统整体架构的第一版设计。

你应该掌握以下五个概念：

1. **模块化单体**：一个应用内部划分清晰的业务模块。
2. **微服务**：多个可以独立运行和部署的服务。
3. **高内聚、低耦合**：模块内部职责集中，模块之间依赖清晰。
4. **模块边界**：一个模块不能随意修改另一个模块的数据。
5. **事务边界**：一次业务操作中的关键数据变化需要保持一致。

结合当前项目，我建议坚持：

**模块化单体 + 业务模块独立 + 明确接口 + 统一事务管理。**

这既能快速开发，也能为后续扩展留下空间。
