## 计算机网络 {#net}

计算机网络是前后端面试共同的重点，三次握手、四次挥手、HTTPS、HTTP 缓存、TCP/UDP 是高频考点。本章先按主题讲解基础知识，章末附面试一问一答速查。

### 浏览器输入 URL 后的完整流程 {#net-url-flow}

考点：超高频面试题，是串起整个网络协议栈的主线，答好它可以引导面试官追问你熟悉的方向。

1. 输入并解析 URL：浏览器解析出协议、主机、端口、路径，构造 HTTP 请求；同时根据请求头判断是否命中 HTTP 缓存，命中则直接使用本地缓存。
2. DNS 域名解析：将域名解析为目标服务器的 IP 地址。
3. 建立 TCP 连接：客户端与服务端进行三次握手。
4. 发送 HTTP/HTTPS 请求到 Web 服务器。
5. 服务器处理请求并返回响应报文：一般包含网页内容、状态码、压缩类型、缓存策略、设置的 Cookie 等。
6. 浏览器渲染页面：解析 HTML/CSS/JS，构建 DOM 树和渲染树，涉及回流与重绘。
7. 断开连接：TCP 四次挥手。

从数据包视角看（对应原文第二遍讲解），一次请求在协议栈中的完整旅程：

1. 浏览器解析 URL（省略路径时访问默认文件如 `/index.html`），生成 HTTP 请求信息。
2. 通过 DNS 服务器查询域名对应的 IP 地址。
3. 应用程序调用 Socket 库委托协议栈工作：TCP 负责收发数据，IP 负责控制网络包的收发。
4. TCP 层：先三次握手建立连接（连接本质是双方维护的状态机，可用 `netstat -napt` 查看）；超过 MSS 的数据按 MSS 为单位拆分，每块加上 TCP 头部交给 IP 模块；源端口为浏览器随机端口，目的端口为 80（HTTP）或 443（HTTPS）。
5. IP 层：填源 IP（多网卡时按路由表选择）和目标 IP，协议号填 06（十六进制）表示 TCP；`route -n` 可查看路由表，目标地址与子网掩码全为 0.0.0.0 的条目是默认网关。
6. MAC 层：通过查路由表 + ARP 协议获得下一跳（网关）的 MAC 地址，写入 MAC 头部；协议类型 0800 表示 IP，0806 表示 ARP；ARP 结果会缓存在内存中几分钟（`arp -a` 查看）。
7. 网卡：将数字信息转为电信号发送，发送前加上报头、起始帧分界符和用于检错的帧校验序列 FCS。
8. 交换机（二层设备，端口无 MAC 地址）：查 MAC 地址表转发；找不到表项或目标为广播地址（`FF:FF:FF:FF:FF:FF` / `255.255.255.255`）时，向除源端口外的所有端口转发。
9. 路由器（三层设备，端口具有 MAC 地址和 IP 地址）：校验 FCS 与接收方 MAC 后，去掉 MAC 头部，查路由表确定输出端口，再通过 ARP 获取下一跳 MAC，重新封装发送。
10. 服务器逐层"扒皮"（去各层头部），最终应用层处理请求并按原路返回响应。

关键结论：传输过程中源 IP 和目标 IP 始终不变，源 MAC 和目标 MAC 在每一跳不断变化，因为 MAC 只负责以太网内相邻两台设备间的传输。

### DNS {#net-dns}

考点：DNS 是什么、解析流程、递归与迭代查询的区别。

DNS（Domain Name System）是一种将域名（如 www.baidu.com）转换为 IP 地址的分布式系统。若采用集中式设计会有三大问题：单点故障、远距离集中式数据库导致时延、维护成本巨大，因此 DNS 采用分布式设计。

域名的层级关系：域名用句点分隔（如 www.server.com），越靠右层级越高（根域 → 顶级域 → 权威域）。

DNS 解析过程：

1. 查询浏览器缓存中是否有该域名对应的 IP。
2. 没有则查询本地 Hosts 文件。
3. 仍没有则向本地 DNS 服务器（通常由 ISP 提供）发起查询请求。
4. 本地 DNS 解析器若无缓存，则向根 DNS 服务器查询；根服务器不负责解析，只告知该去哪个顶级域（.com/.net/.org）DNS 服务器继续查。
5. 本地 DNS 向顶级域 DNS 服务器查询；顶级域也不解析具体域名，只告知去哪个权威 DNS 服务器查询。
6. 本地 DNS 向权威 DNS 服务器查询，权威服务器存储着特定域名与 IP 的映射，返回结果。
7. 本地 DNS 将 IP 返回给浏览器，并将解析结果缓存在本地。
8. 浏览器使用该 IP 与目标服务器建立连接。

递归查询与迭代查询：

| 对比 | 递归查询 | 迭代查询 |
| --- | --- | --- |
| 含义 | 要求上层服务器直接给出完整解析结果，上层自行向下级查询 | 上层只告知下一级服务器地址，客户端自行逐级查询 |
| 适用对象 | 普通用户、客户端 | DNS 服务器之间的通信 |

补充：DNS 使用 53 端口，一般先用 UDP 请求，响应包太大时改用 TCP。

### HTTP 特性与版本演变（1.0/1.1/2/3）{#net-http}

考点：各版本的演进动机与特性，尤其是队头阻塞在各版本中的表现位置。

HTTP 的特性：简单（报文为 header+body，头部是 key-value 文本）、灵活易于扩展（请求方法、URI/URL、状态码、头字段均可自定义扩充；下层协议可替换，如 HTTPS 在 HTTP 与 TCP 之间加 SSL/TLS，HTTP/3 把 TCP 换成基于 UDP 的 QUIC）、应用广泛跨平台。同时 HTTP 无状态、明文传输、不安全：明文可能被窃听、不验证通信方身份可能被伪装、无法证明报文完整性可能被篡改，可用 HTTPS 解决。

WWW 的三大构建技术：HTML（页面标记语言）、HTTP（文档传输协议）、URL（指定文档地址）。

各版本总览：

| 版本 | 关键特性 | 遗留问题 |
| --- | --- | --- |
| HTTP/0.9（1991） | 只支持 GET，无请求头，只能返回 HTML | 功能过于简单 |
| HTTP/1.0（1996，RFC1945） | 引入请求头/响应头，支持多种请求方法和状态码 | 短连接，每次请求都要新建 TCP 连接 |
| HTTP/1.1（1997） | 长连接、管道化、Host 字段、chunked 分块、range 断点续传 | 头部冗余、队头阻塞、无请求优先级、请求只能由客户端发起 |
| HTTP/2 | 头部压缩 HPACK、二进制帧、多路复用（Stream）、服务器推送 | 基于 TCP，存在传输层队头阻塞 |
| HTTP/3 | 底层改用 UDP 上的 QUIC：无队头阻塞、快速建连、连接迁移、前向纠错 | — |

HTTP/1.1 的主要改进：

- 长连接（持久连接）：只要任意一端没有明确提出断开，就保持 TCP 连接，默认开启 Keep-Alive。
- 管道网络传输：同一 TCP 连接中客户端可连续发出多个请求而不必等待响应；但服务器必须按接收顺序响应，前面的慢会阻塞后面的（响应队头阻塞）。管道化非默认开启，且浏览器基本不支持。
- 其余：新增 Host 字段（一台服务器可建多个 Web 站点）、新增 24 个错误状态码、range 头域支持部分请求（206 断点续传）、chunked 响应分块利于传输大文件。

HTTP/2 的四大特性（基于 HTTPS，安全性有保障）：

1. 头部压缩：HPACK 算法由静态表（61 组高频字段）、动态表（同一连接上重复传输的相同头部，用索引号表示）和 Huffman 编码共同完成；动态表过大会占内存，服务器可用类似 `http2_max_requests` 的配置限制单连接请求数。
2. 二进制帧：报文由文本改为二进制格式，分为头信息帧和数据帧，共 10 种帧类型（数据帧与控制帧两类），用位运算高效解析。
3. 并发传输：引入 Stream 概念，多个 Stream 复用一条 TCP 连接，各自用唯一的 Stream ID 区分；不同 Stream 的帧可乱序发送，接收端按 Stream ID 有序组装。三个概念：HTTP 消息（Message）由多个 Frame 构成，一个 Frame 可由多个 TCP 报文构成。
4. 服务器推送：服务器可对一个请求发送多个响应，如访问 HTML 时主动推送 CSS，减少消息传递次数。

HTTP/2 仍存在队头阻塞，但问题在传输层：TCP 是字节流协议，必须保证字节完整且连续，前一个字节没到，后收到的字节只能留在内核缓冲区，应用层无法读取。

HTTP/2 基于TCP 的三大缺陷：

1. 队头阻塞（如上）。
2. TCP 与 TLS 握手时延：TCP 三次握手 + TLS 四次握手，共 3 RTT 才能发出请求数据。
3. 网络迁移需要重新连接：TCP 连接由四元组（源 IP、源端口、目标 IP、目标端口）确定，IP 变化就要重新建连，不利于移动设备切换网络。

HTTP/3 把传输层协议改为 UDP，并在应用层实现了 QUIC 协议（拥有类似 TCP 的连接管理、拥塞窗口、流量控制，把不可靠的 UDP 变为可靠）：

- 无队头阻塞：Stream 之间无依赖，某个 stream 丢包不影响其他 stream。
- 更快的连接建立：QUIC 内部包含 TLS（使用 TLS 1.3），握手只需 1 RTT 即可同时完成连接建立与密钥协商；第二次连接时应用数据可与握手信息一起发送，达到 0-RTT。
- 连接迁移：通过连接 ID 而非四元组标识连接，网络切换（Wi-Fi 到移动网络）时连接可迁移。
- 前向纠错：每个数据包携带部分其他包的冗余数据，少量丢包可直接组装无需重传（牺牲单包数据上限）。
- 头部压缩改用 QPACK：静态表扩到 91 项，并解决了 HPACK 动态表时序性导致的解码阻塞问题；HTTP/3 直接复用 QUIC 的 Stream，帧结构更简单。

### HTTP 缓存 {#net-cache}

考点：强缓存与协商缓存的字段、判定流程、Last-Modified 与 ETag 的优缺点。

对已请求过的资源，客户端或代理服务器保存副本，下次请求先检查是否有有效副本，有则不再通过网络获取。HTTP 缓存分两种：强制缓存和协商缓存。

强制缓存：命中则直接从内存读取资源，无需与服务器通信。

- `Expires`：设置过期时间，与本地时间戳比较，本地时间不准就失效，已基本废弃。
- `Cache-Control`（HTTP/1.1 增加）：`max-age`（客户端缓存时长，秒）、`s-maxage`（代理服务器缓存时长）、`no-cache`（强制走协商缓存）、`no-store`（禁止任何缓存）、`public`（浏览器与代理都可缓存）、`private`（仅浏览器缓存，默认值）。
- 流程：首次请求时服务器在响应头返回 Cache-Control；再次请求时浏览器计算是否过期，未过期用缓存，过期则重新请求，服务器再次更新 Cache-Control。

协商缓存：由服务器告知客户端是否可使用缓存，命中时返回 304。

- 基于 `Last-Modified` / `If-Modified-Since`：服务器把文件修改时间放入 Last-Modified（并设置 `Cache-Control: no-cache`），客户端下次请求携带 If-Modified-Since，服务器比对修改时间：较新则返回 200 和新资源，较旧则返回 304 走缓存。缺点：内容未变但修改时间变了会误判缓存失效；修改时间最小单位是秒，几百毫秒内的修改无法感知。
- 基于 `ETag` / `If-None-Match`：改比较时间戳为比较文件指纹（根据内容计算的唯一哈希）。客户端把上次的 ETag 放入 If-None-Match，服务器重新计算指纹比对：相同返回 304 + 空响应体，不同则返回新资源和新 ETag。ETag 优先级更高。缺点：计算指纹有开销（文件大、数量多、计算频繁时影响性能）；分强验证（精确到每字节，保证绝对不变但耗计算）与弱验证（提取部分属性，快但准确率低）。

注意：协商缓存字段需配合 `Cache-Control` 使用，只有在未命中强缓存时才发起带协商缓存字段的请求。

### HTTPS（加密与证书、连接建立）{#net-http-secure}

考点：HTTPS 与 HTTP 的区别、对称/非对称加密、数字证书与信任链、建连流程。

HTTPS = HTTP + SSL/TLS（SSL：Secure Socket Layer 安全套接层；TLS：Transport Layer Security 安全传输层协议）。

HTTPS 解决的三大风险与手段：

| 风险 | 解决手段 |
| --- | --- |
| 窃听 | 信息加密：对称 + 非对称的混合加密，保证机密性 |
| 篡改 | 校验机制：摘要算法生成唯一「指纹」，保证完整性 |
| 冒充 | 身份证书：服务端公钥放入 CA 数字证书 |

加密方式对比：

- 对称加密（私钥加密）：加密解密使用相同密钥，速度快，但密钥必须保密，无法安全交换密钥。
- 非对称加密（公钥加密）：公钥加密只能私钥解密，私钥加密可被公钥验证（数字签名）；公钥可任意分发解决了密钥交换问题，但速度慢。
- 混合加密：通信建立前用非对称加密交换会话密钥，之后全部使用对称的会话密钥加密数据，兼顾安全与性能。

摘要算法与数字签名：摘要算法（哈希）为内容生成唯一标识以验证完整性，但不能保证发送者身份。数字签名流程：

1. 发送者用私钥加密消息的摘要，生成数字签名。
2. 将原始消息与数字签名一起发送。
3. 接收者用发送者公钥解密签名得到摘要，再对收到的消息计算摘要，两者相同则说明未被篡改且来源可信。

数字证书：防止中间人篡改公钥。流程：实体生成公私钥对 → 生成证书请求 CSR（含公钥、实体信息）发给 CA → CA 验证身份后用自己的私钥签名，生成包含公钥、实体信息、CA 信息和签名的数字证书 → 接收者用 CA 公钥验证证书签名，确认未被篡改且由合法 CA 签发。

证书信任链：根证书（内置在操作系统/浏览器中，信任起点）→ 中间 CA 证书（由根 CA 签发，作为中继）→ 服务器证书（由中间 CA 签发）。验证时依次校验整条链，任何一环失败则证书不可信。

HTTPS 建立连接（SSL/TLS 基本流程：索要并验证公钥 → 协商生成会话密钥 → 用会话密钥加密通信）：

1. 客户端发送 ClientHello 请求，要求建立加密通信。
2. 服务端事先将公钥交给 CA，CA 用自己的私钥对服务端公钥加密生成 CA 数字证书。
3. 服务端响应 ServerHello，将数字证书发给客户端。
4. 客户端解析证书（浏览器内置了大部分 CA 机构的公钥），验证合法性；不合法则告警，合法则取出服务端公钥。
5. 客户端生成一个随机码 key（对称加密的密钥）。
6. 客户端用服务端公钥加密随机码 key 后发送给服务端。
7. 服务端用私钥解密，获得随机码 key。
8. 此后双方使用该 key 对称加密传输数据。

HTTPS 与 HTTP 的区别：HTTP 明文传输，HTTPS 在 TCP 与 HTTP 之间加入 SSL/TLS 加密传输；HTTPS 在 TCP 三次握手后还需 SSL/TLS 握手才进入加密报文传输；默认端口 HTTP 为 80、HTTPS 为 443；HTTPS 需向 CA 申请数字证书保证服务器身份可信。HTTPS 的代价：握手阶段时延较高、需购买 CA 证书、加解密占用 CPU 资源。

### TCP 与 UDP 报文格式 {#net-tcp-udp-header}

考点：首部字段的作用（序列号、确认号、窗口、标志位）与 TCP 选项。

UDP 头部共 8 字节，四个字段各 16 位：

- 源端口 / 目标端口：告诉 UDP 协议把报文发给哪个进程。
- 包长度：UDP 首部长度与数据长度之和。
- 校验和：检查报文段是否出现差错。

TCP 头部固定 20 字节，最长 60 字节：

- 源端口 / 目的端口：多路复用/分解，标识报文段来自哪个应用、传给哪个应用。
- 序列号：本报文段首字节的字节流编号，解决网络包乱序问题。
- 确认应答号：收到的报文段序列号 + 1，解决不丢包问题。序列号与确认号共同实现可靠传输。
- 首部长度：标识 TCP 头部字节数，最长 60。
- 窗口大小：接收窗口，告知对方本端缓冲区剩余空间，用于流量控制。
- 标志位：ACK（确认应答号有效）、RST（重置混乱连接或拒绝无效请求）、SYN（请求建立连接）、FIN（断开连接）。
- 检验和：用 CRC 算法检查头部+数据是否出错，同 UDP。

TCP 选项（options）为可变长可选信息，最多 40 字节，由 kind（类型）、length（总长度）、info（具体信息）构成，常见 7 种：

| kind | 选项 | 说明 |
| --- | --- | --- |
| 0 | EOP 选项表结束 | 放在末尾用于填充 |
| 1 | NOP 空操作 | 将选项总长度填充为 4 字节整数倍 |
| 2 | MSS 最大报文段长度 | 连接初始化时协商，通常为 MTU-40，以太网为 1460 字节，避免 IP 分片 |
| 3 | 窗口扩大因子 | 16 位窗口最大仅 65535 字节，实际窗口 = 窗口值 * 2^M（M 取 0～14），只能出现在 SYN 报文中 |
| 4 | SACK-permitted | 连接初始化时表示是否支持选择性确认 |
| 5 | SACK | 告诉发送方已收到并缓存的不连续数据块（每块信息 8 字节，最多 4 块），发送方据此只重传丢失部分 |
| 8 | 时间戳 | 较准确地计算 RTT，为流量控制提供信息 |

### TCP 三次握手 {#net-handshake}

考点：握手过程与状态变迁、为什么是三次、半连接队列、SYN 攻击。

TCP 是面向连接的协议，使用前必须先通过三次握手建立连接。双方初始均为 CLOSED 状态，服务端监听端口后处于 LISTEN 状态：

1. 第一次握手（SYN 报文）：客户端随机初始化序列号 client_isn 放入首部，SYN 置 1，发送后进入 SYN-SENT 状态。
2. 第二次握手（SYN+ACK 报文）：服务端收到后，放入自己的初始序列号 server_isn，确认应答号填 client_isn + 1，SYN 和 ACK 置 1，发送后进入 SYN-RCVD 状态。
3. 第三次握手（ACK 报文）：客户端收到后发送 ACK 置 1、确认应答号填 server_isn + 1 的报文，随后进入 ESTABLISHED 状态；服务端收到后也进入 ESTABLISHED。此次报文可以携带数据，前两次不可以。

为什么需要三次握手（而不是两次或四次）：

1. 阻止重复历史连接的初始化（主因）：网络阻塞导致新旧两个 SYN 先后到达时，客户端能根据序列号判断出历史连接并发送 RST 中止；若只有两次握手，服务端收到 SYN 就进入 ESTABLISHED 并开始发送数据，造成资源浪费。
2. 同步双方的初始序列号：序列号是可靠传输的关键（去重、按序接收、标识已收数据）。一来一回才能保证双方的初始序列号都被可靠确认；两次只能确认一方，四次虽也可以但可省略为三次。
3. 避免资源浪费：两次握手下，服务端每收到一个 SYN（包括阻塞后重发的）都会建立连接，产生多个冗余无效连接。

半连接队列（SYN 队列）：存放已发送 SYN 但未完成三次握手的连接请求（服务端处于 SYN_RCVD 状态）。全连接队列（Accept 队列）：存放已完成三次握手、完全建立连接的连接。

SYN 攻击：攻击者发送大量伪造的 SYN 请求但不完成后续握手，让服务器一直等待确认，消耗半连接队列和系统资源；队列满后新 SYN 报文被丢弃，正常连接无法建立。

### TCP 四次挥手 {#net-wave}

考点：挥手过程与状态变迁、为什么是四次、TIME_WAIT 的意义与 2MSL。

挥手前双方均为 ESTABLISHED 状态，以客户端主动关闭为例：

1. 第一次挥手：客户端发送 FIN 置 1 的报文，进入 FIN_WAIT1 状态。
2. 第二次挥手：服务端收到后回 ACK 应答报文（序列号为客户端序列号 + 1），进入 CLOSE_WAIT 状态。
3. 第三次挥手：服务端处理完数据后发送 FIN 报文，进入 LAST_ACK 状态。
4. 第四次挥手：客户端收到 FIN 后回 ACK，进入 TIME_WAIT 状态。
5. 服务端收到 ACK 后进入 CLOSE 状态，完成关闭。
6. 客户端经过 2MSL 时间后自动进入 CLOSE 状态。

为什么挥手需要四次：客户端发送 FIN 只表示不再发送数据但还可接收；服务端收到 FIN 后可能还有数据要处理和发送，所以先回 ACK，等自己不再发送数据时才发 FIN。ACK 和 FIN 一般分开发送，因此比三次握手多一次。

为什么需要 TIME_WAIT 状态（仅主动关闭方会有）：

1. 防止历史连接中的数据被后面相同四元组的新连接错误接收：经过 2MSL，两个方向上的旧数据包都会在网络中自然消失。
2. 保证被动关闭方能被正确关闭：若最后一个 ACK 丢失，服务端会重发 FIN；客户端处于 TIME_WAIT 就能重新回应 ACK，否则只能回 RST，服务端会将其解释为错误。

为什么等待 2MSL：MSL（Maximum Segment Lifetime）是报文最大生存时间。1 个 MSL 确保主动方最后的 ACK 能到达对端，另 1 个 MSL 确保对端没收到 ACK 时重传的 FIN 能到达，一来一回共 2 倍。Linux 中 MSL 固定为 30 秒，即 2MSL 为 60 秒；若期间收到重传的 FIN，则 2MSL 重新计时。

TIME_WAIT 过多的危害：占用内存资源；占用端口资源（一个 TCP 连接至少消耗一个本地端口），占满后无法创建新连接。

### TCP 重传机制 {#net-retransmit}

考点：超时重传、快速重传、SACK、D-SACK 的触发条件与区别。

TCP 通过序列号与确认应答实现可靠传输，数据包丢失时依靠重传机制解决。

1. 超时重传：发送数据后启动计时器，超过指定时间（RTO）未收到 ACK 就重发。RTT 是数据包往返时延，RTO 应略大于 RTT 且动态变化；RTO 过大重发慢效率低，过小可能没丢就重发造成网络负担。每次遇到超时重传，下一次的超时时间间隔设为先前的两倍。
2. 快速重传：不以时间而以数据驱动。当收到三个相同的 ACK 报文时，在定时器过期之前重传丢失的报文段。它解决了超时时间的问题，但面临「重传一个还是重传所有」的疑问。
3. SACK（选择性确认）：在 TCP 头部选项字段中加入 SACK，将已收到的数据信息发给发送方，发送方据此只重传丢失的数据。
4. D-SACK（Duplicate SACK）：用 SACK 告诉发送方有哪些数据被重复接收，可以让发送方知道：是发出去的包丢了还是回应的 ACK 丢了、数据包是否被网络延迟、数据包是否被网络复制。

### TCP 滑动窗口 {#net-window}

考点：窗口的意义、累计确认、发送/接收窗口的分段与指针。

TCP 若每发一个数据就等一次应答，往返时间越长吞吐量越低。引入窗口后，无需等待确认应答就可继续发送数据的最大值就是窗口大小，窗口本质是操作系统开辟的缓存空间，发送方在收到确认前必须在缓冲区保留已发送数据。

累计确认（累计应答）：中途某个 ACK 丢失也没关系，只要收到后一个确认（如 ACK 700），就表示之前的所有数据接收方都收到了。

窗口大小由接收方的窗口大小决定：TCP 头部的 window 字段是接收方告知发送方自己还有多少缓冲区可接收数据，发送量不能超过接收窗口。

发送方缓存按处理情况分四部分：

- #1 已发送并收到 ACK 确认的数据。
- #2 已发送但未收到 ACK 确认的数据。
- #3 未发送但总大小在接收方处理范围内（可发送）的数据。
- #4 未发送且超过接收方处理范围（不可发送）的数据。

用三个指针跟踪：SND.WND（发送窗口大小，由接收方指定）、SND.UNA（绝对指针，指向 #2 第一个字节，即已发送未确认的第一个字节）、SND.NXT（绝对指针，指向 #3 第一个字节，即未发送但可发送的第一个字节）；指向 #4 第一个字节的是相对指针（SND.UNA + SND.WND）。可用窗口大小 = SND.WND - (SND.NXT - SND.UNA)。

接收窗口分三部分：#1+#2 已成功接收并确认（等待应用读取）、#3 未收到但可接收、#4 未收到且不可接收。用 RCV.WND（接收窗口大小，通告给发送方）和 RCV.NXT（指向期望收到的下一个字节，即 #3 第一个字节）两个指针划分。

接收窗口与发送窗口并非完全相等而是约等于：接收窗口随应用读取速度动态变化，新窗口大小通过 TCP 报文的 Windows 字段告知发送方，传输存在时延。

### TCP 流量控制 {#net-flow-control}

考点：流量控制的原理与实现手段，即滑动窗口如何约束发送速率。

流量控制的基本原理是使用滑动窗口机制，让接收方通过调整窗口大小告知发送方自己当前的处理能力，避免接收方处理不过来而丢包：

1. 接收窗口：接收方维护一个窗口，表示可接收的数据范围，大小随处理能力调整。
2. 通告窗口大小：接收方通过 TCP 报文中的确认信息（窗口字段）通告当前接收窗口，发送方据此控制发送速率。
3. 窗口滑动：接收方处理能力恢复后可通告更大的窗口，窗口向前滑动。
4. 发送速率控制：接收窗口变小表示处理能力减弱，发送方减慢发送；反之加快。
5. 动态调整：流量控制是动态的，适应网络和接收方的变化。

若窗口为 0，发送方停止发送。

### TCP 拥塞控制 {#net-congestion}

考点：四个算法（慢启动、拥塞避免、拥塞发生、快速恢复）中 cwnd 与 ssthresh 的变化规则。

网络拥塞时继续发大量数据包会导致时延、丢失，重传又进一步加重负担，形成恶性循环。拥塞控制通过拥塞窗口 cwnd 防止过多数据注入网络；发送窗口 swnd = min(cwnd, rwnd)（拥塞窗口与接收窗口的较小值）。发送方在规定时间内未收到 ACK（发生超时重传）即认为网络拥塞；无拥塞则 cwnd 增大，有拥塞则减小。

1. 慢启动：连接刚建立时一点点提高发包数量。每收到一个 ACK，cwnd 加 1，发包个数呈指数增长。门限 ssthresh：cwnd < ssthresh 时用慢启动，cwnd >= ssthresh 时改用拥塞避免（ssthresh 一般为 65535 字节）。
2. 拥塞避免：每收到一个 ACK，cwnd 增加 1/cwnd，即每个 RTT 约增加 1 个 MSS，由指数增长变为线性增长。
3. 拥塞发生：
   - 超时重传触发：ssthresh 设为 cwnd/2，cwnd 重置为 1，重新开始慢启动（方式激进，会造成网络卡顿）。
   - 快速重传触发（认为不严重，只丢了一小部分）：cwnd 设为原来的一半，ssthresh 设为该值，进入快速恢复。
4. 快速恢复（与快速重传同时使用，能收到 3 个重复 ACK 说明网络没那么糟糕）：
   - cwnd = ssthresh + 3（3 表示确认有 3 个数据包被收到）；
   - 重传丢失的数据包；
   - 再收到重复 ACK 则 cwnd 加 1；
   - 收到新数据的 ACK 后，把 cwnd 设置为第一步中的 ssthresh，重新进入拥塞避免状态。

### IP 基础 {#net-ip}

考点：IP 与 MAC 的分工、地址分类与 CIDR、NAT、ARP/DHCP/ICMP/IGMP、IPv6。

IP 位于 TCP/IP 参考模型第三层（网络层），作用是实现主机与主机之间的通信（点对点）。与数据链路层的分工：MAC 实现直连的两个设备之间通信；IP 负责在没有直连的两个网络之间传输。传输中源/目标 IP 不变，源/目标 MAC 每跳变化。

IP 地址由「网络标识 + 主机标识」组成。相关概念：

- 地址分类：A、B、C 类用于主机（最大主机数 = 2^主机号位数 - 2，去掉全 0 的网络地址和全 1 的广播地址）；D 类用于多播（前四位 1110，224.0.0.0～239.255.255.255），无主机号；E 类预留。优点是简单明了、选路简单；缺点是同一网络下无地址层次、C 类太少（254 台）B 类太多（6 万多台），与现实网络不匹配。
- 广播：本地广播在本网络内（如 192.168.0.0/24 的广播地址 192.168.0.255，路由器不转发）；直接广播跨网络发往其他网段的广播地址（多数路由器默认不转发）。
- CIDR 无分类地址：32 位 IP 划分为网络号 + 主机号，表示形式 a.b.c.d/x（前 x 位为网络号）；也可用子网掩码，掩码与 IP 按位 AND 得到网络号。子网划分是从主机号借位作为子网号（如 C 类地址用 255.255.255.192 掩码借 2 位，划分出 4 个子网）。
- 公有与私有 IP：私有 IP（办公室、家庭、学校常用）由组织内部自行分配、可重复；公有 IP 由 ICANN 统一分配，全网唯一。环回地址 127.0.0.1（localhost）用于同机程序间通信，数据包不流向网络。
- 路由控制：路由表记录网络地址与下一跳；发送 IP 包时查表找相同网络地址的记录，多条匹配时取相同位数最长的（最长匹配）。
- IP 分片与重组：不同数据链路 MTU 不同（以太网 1500 字节），IP 包大于 MTU 时被分片，重组只能由目标主机完成。某分片丢失则整个 IP 数据报作废，因此 TCP 用 MSS 在传输层分片（避免 IP 层分片），UDP 则尽量不要发送大于 MTU 的数据报文。

IPv6：128 位地址（每 16 位一组用冒号分隔，连续 0 可用 :: 省略且只允许一次）；地址更多、可自动配置（无需 DHCP 也能即插即用）、首部固定 40 字节并去掉了首部校验和、取消分片/重组字段（只允许源与目标主机分片）、有防伪造 IP 和防窃听功能。地址类型：单播（一对一，分链路本地、唯一本地（相当于私有 IP）、全局单播（相当于公有 IP））、组播（一对多）、任播（通信最近的节点），没有广播地址。IPv4 与 IPv6 不兼容，普及依赖设备与运营商升级。

配套协议：

- ARP（地址解析协议）：已知 IP 求 MAC。主机广播 ARP 请求（含目标 IP），同链路中 IP 匹配的设备将 MAC 地址放入 ARP 响应返回；结果缓存在内存中，超期限清除。RARP 相反，已知 MAC 求 IP，常用于打印机等嵌入式设备接入网络（需 RARP 服务器注册映射）。
- DHCP（动态主机配置协议）：动态获取 IP，全程 UDP 广播通信，客户端监听 68 端口、服务端监听 67 端口；租约快到期时客户端请求续租，服务器同意回 DHCP ACK 延长租期，不同意回 NACK 则停止使用。跨网段时由 DHCP 中继代理转发（收广播转单播给服务器），实现统一管理。
- NAT（网络地址转换）：私有 IP 与公有 IP 的转换，缓解 IPv4 耗尽。NAPT 把 IP + 端口一起转换，多个私有地址可共用一个公有 IP（转换表在 TCP 首次握手的 SYN 发出时生成，收到关闭连接 FIN 的确认后删除）。缺点：外部无法主动与 NAT 内部服务器建立连接；转换表有性能开销；NAT 路由器重启会重置所有 TCP 连接。解决：改用 IPv6 或 NAT 穿透技术。
- ICMP（互联网控制报文协议）：确认 IP 包是否成功送达、报告废弃原因、改善网络设置；分查询报文（诊断）和差错报文（通知出错原因）两类，自身使用 IP 发送。
- IGMP（因特网组管理协议）：工作在主机（组播成员）与最后一跳路由器之间，管理组播组的加入与退出。报文用 IP 封装，协议号 2，TTL 通常为 1。常规查询与响应：路由器周期性向 224.0.0.1 发查询，主机启动随机「报告延迟计时器」（0～10 秒），超时后发送成员关系报告，同组其他主机已发则不再发（减少报文数）。离开组：主机向 224.0.0.2 发离组报文，路由器以 1 秒间隔连发 2 个特定组查询，有成员响应则继续转发，无响应则停止转发。

### TCP 抓包实践与连接优化 {#net-tcp-opt}

考点：tcpdump/Wireshark 的搭配、握手丢包的表现、Nagle 与延迟确认、连接建立与断开的优化。

抓包工具：tcpdump 和 Wireshark 是最常用的组合，先用 tcpdump 在 Linux 服务器上抓包（保存成 .pcap 文件），再拖到 Windows 电脑用 Wireshark 可视化分析。

三次握手异常实战：

- 第一次握手 SYN 丢包：客户端收不到 SYN+ACK，会超时重传 SYN（重传次数由参数控制）。
- 第二次握手 SYN+ACK 丢包：如客户端防火墙粗暴丢弃来自服务端的数据，服务端收不到 ACK 会重传 SYN+ACK，超过次数后释放连接。
- 第三次握手 ACK 丢包：如服务端防火墙屏蔽 ACK 包，服务端收不到确认会重传 SYN+ACK；客户端不发送数据时，连接最终由 TCP 保活机制断开。

TCP 快速建立连接：使用 TCP Fast Open（TFO）功能可减少 TCP 连接建立的时延。

延迟确认与 Nagle 算法：当 TCP 报文承载的数据非常小时网络效率很低，两种常见优化策略：

- Nagle 算法：避免大量小报文传输，来了小报文先不急发，等凑成大包再一起发送；最先开始时一定会有一个小报文。
- 延迟确认：解决 ACK 传输效率低的问题，接收方稍作等待再统一确认。
- 两者混合使用会导致耗时增长，解决办法：发送方关闭 Nagle 算法（TCP_NODELAY 选项），或接收方关闭延迟确认。

TCP 连接建立优化（客户端视角）：发起 SYN 包时可通过 `tcp_syn_retries` 控制重传次数；服务端也有相应参数（半连接队列等）；绕过三次握手可使用 TCP Fast Open。

TCP 四次挥手优化：主动关闭方与被动关闭方思路不同。

- 关闭方式：进程异常退出时内核发送 RST 报文暴力关闭，不走四次挥手；安全关闭通过进程调用 close / shutdown 函数发起 FIN（shutdown 参数须传入 SHUT_WR 或 SHUT_RDWR）。
- close 与 shutdown 的区别：close 完全断开连接（不能收也不能发），调用方成为「孤儿连接」（`netstat -p` 可见进程名为空）；shutdown 可只关闭一个方向：SHUT_RD(0) 关读方向（收到的数据 ACK 后悄悄丢弃）、SHUT_WR(1) 关写方向（即「半关闭」，发送缓冲区数据立即发出并随 FIN）、SHUT_RDWR(2) 两方向都关。
- FIN_WAIT1 优化：此状态连接多时降低 `tcp_orphan_retries`（FIN 重传次数），超过次数直接关闭（发 RST 强制关闭）；`tcp_max_orphans` 定义孤儿连接最大数量。
- FIN_WAIT2 优化：shutdown 关闭的连接可一直停留此状态；close 关闭的孤儿连接由 `tcp_fin_timeout` 控制时长，默认 60 秒，超时未收到 FIN 直接关闭。
- TIME_WAIT 优化：`tcp_max_tw_buckets` 限制 TIME_WAIT 连接数量，超出后新关闭的连接直接关闭（不宜过大，内存和端口有限）；`tcp_tw_reuse` 复用 TIME_WAIT 端口，仅用于客户端（connect 时生效），且要求 TIME_WAIT 状态超过 1 秒、双方开启 TCP 时间戳支持。开启时间戳后，重复数据包会因时间戳过期被自然丢弃，2MSL 问题不复存在，还可防止序列号绕回。
- 双方同时关闭：TCP 是双工协议，双方同时发 FIN 时都进入 FIN_WAIT1，等来对方 FIN 后进入 CLOSING 新状态（替代 FIN_WAIT2），回复 ACK 后进入 TIME_WAIT，等 2MSL 后关闭。

TCP 数据传输性能提升：

- 滑动窗口影响传输速度：TCP 报文发出后须等 ACK（期间存于内核缓冲区），滑动窗口允许批量发送批量应答；接收方把当前可接收大小放在 TCP 头部窗口字段通告给发送方。
- 窗口字段只有 2 字节，最多表达 65535 字节（64KB），高速网络下不够用；TCP 选项字段定义了窗口扩大因子（2^14），使窗口从 16 位扩大为 30 位，最大可达 1GB。
- 最大传输速度受发送窗口、接收窗口和网络传输能力限制。带宽时延积 BDP = 带宽 × RTT，决定网络中飞行报文的大小：发送缓冲区超过 BDP 的部分无法有效传输且易丢包；小于 BDP 则不能发挥网络效率。
- 缓冲区调整：发送缓冲区大小可自动调节（动态范围最小值、初始默认值、最大值）；接收缓冲区需配置 `tcp_moderate_rcvbuf` 为 1 开启自动调节——系统空闲内存多则增大缓冲区提升传输量，内存紧张则减小以支持更多并发连接。缓冲区配置过小无法充分利用带宽，过大易耗尽服务器资源导致新连接无法建立。

常用观测命令：`netstat -napt` 查看 TCP 连接状态、`route -n` 查看路由表、`arp -a` 查看 ARP 缓存。

### Linux 收发网络包 {#net-linux}

考点：网卡收发数据包的完整链路，NAPI 机制的意义。

网卡是专门负责收发网络包的硬件，收到网络包后通过 DMA 技术将其放入 Ring Buffer（环形缓冲区）。

发送流程：

1. 应用程序调用 Socket 发送接口（系统调用），从用户态陷入内核态 Socket 层，数据被拷贝到 Socket 发送缓冲区。
2. 网络协议栈从缓冲区取出数据包，按 TCP/IP 从上到下逐层处理：TCP 传输协议则加 TCP 包头；网络层加 IP 包头、查路由表确认下一跳 IP、按 MTU 分片；网络接口层通过 ARP 获得下一跳 MAC 地址，加帧头帧尾，放入发包队列。
3. 触发软中断通知网卡驱动，驱动通过 DMA 从发包队列读取网络包放入硬件网卡队列，物理网卡发送出去。

接收流程：

1. 网络包到达，网卡发起硬件中断，执行中断处理函数后暂时屏蔽中断，唤醒软中断以轮询方式处理数据，直到没有新数据才恢复中断——这是 Linux 2.6 引入的 NAPI 机制（中断 + 轮询混合），一次中断处理多个网络包，降低频繁中断的性能开销。
2. 软中断从 Ring Buffer 拷贝数据到内核 struct sk_buff 缓冲区，交给协议栈逐层处理。
3. 网络接口层：检查报文合法性（不合法丢弃），找出上层协议类型（IPv4/IPv6），去掉帧头帧尾。
4. 网络层：取出 IP 包，判断走向（交给上层还是转发）；确认发给本机后，看上层协议是 TCP 还是 UDP，去掉 IP 头交给传输层。
5. 传输层：取出 TCP/UDP 头，根据四元组（源 IP、源端口、目的 IP、目的端口）找出对应的 Socket，把数据拷贝到 Socket 接收缓冲区。
6. 应用层程序调用 Socket 接口，从接收缓冲区读取数据。

### 面试一问一答速查 {#net-qa}

**OSI 七层模型是什么？**
国际标准化组织 ISO 制定的标准体系，从下到上：物理层（传输比特流）、数据链路层（帧传输、MAC 寻址、差错校验）、网络层（路由转发、IP 寻址）、传输层（端到端传输，TCP/UDP）、会话层（建立管理终止会话）、表示层（格式转换、加解密）、应用层（为应用提供网络服务，HTTP/FTP/SMTP/DNS）。口诀「物数网传会表应」。

**TCP/IP 四层模型是什么？**
互联网最常用的协议栈：应用层（对应 OSI 的应用、表示、会话层）、传输层（TCP/UDP）、网际层（IP，路由转发）、网络接口层（对应数据链路层和物理层）。比 OSI 简洁实用，是互联网通信的主要参考模型。

**五层网络体系结构是什么？**
综合 OSI 和 TCP/IP 而来：应用层、传输层、网络层、数据链路层、物理层，是教学和工程中常用的折中模型。

**从输入 URL 到页面展示发生了什么？**
URL 解析与请求构造 → DNS 域名解析 → TCP 三次握手（HTTPS 还要 TLS 握手）→ 发送 HTTP 请求 → 服务器处理并返回响应 → 浏览器解析渲染（DOM 树、渲染树、执行 JS、加载子资源）→ 四次挥手断开连接。

**HTTP 报文的结构？**
请求报文：请求行（方法 URI 版本）、请求头（Host、User-Agent、Accept、Content-Type、Authorization 等）、空行、请求体。响应报文：状态行（版本 状态码 状态消息）、响应头（Content-Type、Content-Length、Server、Location、Set-Cookie 等）、空行、响应体。

**TCP 粘包是什么？如何解决？**
TCP 是无边界字节流协议，业务上的完整包可能被拆分发送（拆包）或多个小包合并发送（粘包）。原因：数据大于缓冲区或超过 MSS 会拆包；数据小于缓冲区、Nagle 算法凑包、接收方不及时读取会粘包。解决：应用层定长消息、包头 + 包长 + 包体、指定开始/结束符；发送方可关闭 Nagle 算法（TCP_NODELAY）。

**UDP 会产生粘包吗？**
不会。UDP 面向消息传输，有保护消息边界，接收方一次只接收一条独立消息，不存在粘包；代价是数据大于 MTU 时在 IP 层分片，任一分片丢失整个数据报作废。

**HTTP 请求方法有哪些？**
GET（获取资源）、POST（提交数据）、PUT（更新/创建资源）、DELETE（删除资源）、PATCH（部分更新）、HEAD（只要响应头）、OPTIONS（查询服务器支持的方法）、TRACE（测试回显请求）、CONNECT（代理）。

**GET 和 POST 的区别？**
GET 获取资源，安全幂等，参数在 URL 中（受浏览器约 2KB 限制、只接受 ASCII、URL 编码），会被浏览器缓存、可存书签、回退无害；POST 提交数据会修改服务器资源，不安全不幂等，参数在请求体中（长度与类型无限制、支持多种编码），默认不缓存。本质都是基于 TCP 的 HTTP 方法；浏览器行为上 GET 一个 TCP 包发完，POST 常先发 header（服务端回 100 continue）再发 data。

**常见 HTTP 状态码有哪些？**
200 成功；206 部分内容（断点续传，需 Range 头）；301 永久重定向；302 临时重定向；304 协商缓存命中（无响应体）；400 请求语法错误；401 需要认证；403 禁止访问；404 资源不存在；500 服务器内部错误；503 服务器正忙。

**HTTP 缓存有几种？**
两种。强制缓存：Expires（已废弃）和 Cache-Control（max-age 等），命中直接读本地不与服务器通信。协商缓存：Last-Modified/If-Modified-Since（比时间戳）和 ETag/If-None-Match（比文件指纹，优先级更高），服务器判断资源未变则返回 304。协商缓存需配合 Cache-Control，未命中强缓存才发起。

**HTTP/1.0 和 HTTP/1.1 的区别？**
1.1 默认长连接（Keep-Alive），1.0 默认短连接；1.1 引入更多缓存控制头（Entity tag/If-None-Match）；1.1 支持管道化；1.1 增加 Host 字段（支持虚拟主机）；1.1 新增 24 个错误状态码；1.1 引入 range 头域支持断点续传（206）。

**HTTP/1.1 有什么特性？**
持久连接（Keep-Alive）、管线化、新增 PUT/DELETE/OPTIONS/PATCH 等方法、新增 24 个错误状态码、新增缓存字段（If-Modified-Since、If-None-Match）、range 断点续传、chunked 分块传输、Host 字段。

**HTTP/2.0 和 HTTP/1.1 的区别？**
二进制帧传输替代文本解析；多路复用（一个请求一个 ID，多请求共享连接，接收方按 ID 归属）；HPACK 头部压缩（双方缓存 header 字段表避免重复传输）；服务器推送（随 index.html 一起推送所需资源）。底层仍有 TCP 层队头阻塞。

**HTTP/3 有什么特点？**
底层传输协议从 TCP 改为 UDP 上的 QUIC：无队头阻塞（stream 间无依赖）、更快建连（QUIC 内含 TLS 1.3，1 RTT 完成建连与密钥协商，二次连接 0-RTT）、连接迁移（基于连接 ID 不依赖四元组）、前向纠错减少重传；头部压缩用 QPACK（静态表 91 项）。

**HTTPS 和 HTTP 的区别？**
HTTPS 在 TCP 与 HTTP 之间加入 SSL/TLS，报文加密传输；HTTPS 在 TCP 三次握手后还需 SSL/TLS 握手；默认端口 HTTP 80、HTTPS 443；HTTPS 需向 CA 申请数字证书保证服务器身份可信。

**SSL/TLS 是什么？**
SSL（安全套接字层）与 TLS（安全传输层协议）是 HTTPS 的安全基础，通过加密（防窃听）、身份验证（数字证书防冒充）、数据完整性（消息摘要防篡改）确保安全通信。

**什么是对称加密和非对称加密？**
对称加密加解密用同一密钥，速度快但密钥交换不安全；非对称加密用公钥/私钥对，公钥加密私钥解密（或私钥签名公钥验证），解决密钥交换但速度慢。HTTPS 用混合加密：建连时非对称交换会话密钥，通信中对称加密数据。

**HTTPS 是如何建立连接的？**
客户端发 ClientHello → 服务端返回 CA 数字证书 → 客户端验证证书并取出公钥 → 客户端生成随机会话密钥，用公钥加密后发送 → 服务端用私钥解密得到会话密钥 → 双方用会话密钥对称加密通信。

**URL 和 URI 是什么？**
URI 是统一资源标识符，标识互联网资源；URL 是统一资源定位符，是 URI 的子集，还提供资源的位置信息。URL 组成：协议、域名/IP、端口、路径、查询参数、片段标识，如 `https://www.example.com:8080/path/resource?param=value#section`。

**DNS 是什么？**
Domain Name System，将域名转换为 IP 地址的分布式系统，使用 53 端口（一般 UDP）。分布式设计避免了单点故障、远距离时延和维护成本问题。

**DNS 解析过程是什么？**
依次查浏览器缓存 → 本地 Hosts 文件 → 本地 DNS 服务器（ISP 提供）；本地无缓存则依次向根 DNS（告知顶级域服务器）、顶级域 DNS（告知权威服务器）、权威 DNS（返回域名与 IP 映射）查询，结果返回浏览器并缓存，随后浏览器用该 IP 建立连接。

**递归查询和迭代查询的区别？**
递归查询要求上层服务器直接返回完整结果（上层自行向下查询），适合普通用户和客户端；迭代查询上层只告知下一级服务器地址，客户端自行逐级查询，适用于 DNS 服务器之间的通信。

**TCP 和 UDP 的概念和特点？**
TCP：面向连接、可靠、基于字节流的传输层协议，通过三次握手建立连接、序列号与确认机制保证有序完整，有流量控制和拥塞控制，适用于文件传输、邮件、网页浏览。UDP：无连接、不可靠、轻量快速，不保证有序不重传，适用于实时音视频、游戏等实时性优先的场景。

**TCP 和 UDP 的区别？**
连接：TCP 面向连接需握手，UDP 无连接；服务形式：TCP 一对一，UDP 支持一对一、一对多、多对多；可靠性：TCP 确认应答 + 重传保证不丢不重有序，UDP 尽力交付；控制：TCP 有流量/拥塞控制，UDP 无；首部：TCP 至少 20 字节（可到 60），UDP 固定 8 字节；传输方式：TCP 字节流无边界，UDP 数据报有边界；分片：TCP 在传输层按 MSS 分片（丢一片重传一片），UDP 大于 MTU 时在 IP 层分片（一片丢失整报作废）。

**TCP 和 UDP 分别适用于什么场景？**
TCP 适合可靠性要求高的场景：文件传输、电子邮件、网页浏览；UDP 适合实时性优先、容忍丢包的场景：实时游戏、流媒体、音视频通话，以及 DNS、广播/多播。

**TCP 如何保证可靠性？**
校验和（检错）、序列号 + 确认应答（有序、不丢、不重）、超时重传与快速重传（丢包恢复）、连接管理（握手挥手）、流量控制（不压垮接收方）、拥塞控制（不压垮网络）。

**怎么用 UDP 实现可靠传输？**
传输层无法保证，只能在应用层模拟 TCP 的机制：自定义首部携带确认序列号和时间戳（计算 RTT 得出合适的 RTO）；停等方式发送，超时重传且 RTO 翻倍；接收端按序列号排序并丢弃重复报文、回传确认。已有实现：RUDP、RTP（实时传输）、UDT（面向连接，支持高速广域网海量数据传输、P2P、防火墙穿透）。

**三次握手的过程？**
客户端发 SYN（携带初始序列号 client_isn），进入 SYN-SENT；服务端回 SYN+ACK（携带 server_isn，确认号 client_isn+1），进入 SYN-RCVD；客户端回 ACK（确认号 server_isn+1，可携带数据），双方进入 ESTABLISHED。目的：保证双方都具有发送和接收能力。

**四次挥手的过程？**
客户端发 FIN 进入 FIN_WAIT1；服务端回 ACK 进入 CLOSE_WAIT；服务端数据发完后发 FIN 进入 LAST_ACK；客户端回 ACK 进入 TIME_WAIT，等 2MSL 后关闭，服务端收到 ACK 后关闭。因为 TCP 全双工，两个方向要分别关闭，故需四次。

**Keep-Alive 是什么？**
HTTP 层（应用层实现）的长连接机制：完成一次请求响应后不立即关闭连接，后续请求复用，避免反复建连的开销。HTTP/1.0 需配置 `Connection: Keep-Alive`，HTTP/1.1 默认开启。优点：减少建连开销、支持同连接多请求、共享头部信息；缺点：长时间占用服务器资源，需设置超时时间。

**TCP KeepAlive 是什么？**
TCP 层（内核态实现）的保活机制，与 HTTP Keep-Alive 不是一回事。连接在一段时间内无数据传输时，操作系统定期发送空的探测报文：对端正常响应则重置保活时间；对端程序崩溃则回 RST 重置连接；探测报文不可达且达到保活探测次数后关闭连接。用于检测空闲连接是否存活并释放资源。

**CDN 是什么？**
内容分发网络（Content Delivery Network），将内容存储在分布式服务器上，使用户从距离较近的节点获取内容，减少传输时间和距离，提高传输速度、降低延迟。

**CDN 的工作流程？**
用户访问时 DNS 解析返回距用户最近的 CDN 节点 IP（而非源站 IP）→ 请求路由到最近节点（结合负载与可用性动态分发）→ 节点有缓存直接返回，无缓存则回源获取并缓存到节点供后续请求使用。

**CDN 是如何加速的？**
就近访问（全球节点缩短传输距离）、内容缓存（静态资源直接命中）、前置缓存（热门内容提前缓存）、智能负载均衡、压缩技术减小传输量、并行下载（多路复用同连接下载多个资源）。

**Cookie 和 Session 是什么？**
都是管理用户状态和身份的机制。Cookie 是服务器通过响应头 Set-Cookie 下发、存储在浏览器中的小型文本文件，后续请求自动携带，服务器据此识别用户；Session 是服务器把客户端信息记录在服务端的机制，通过 Session ID（常以 Cookie 传递）关联，用于维护登录状态、存储临时数据。

**Cookie 和 Session 的区别？**
存储位置：Cookie 在浏览器端，Session 在服务器端；容量：Cookie 约 几 KB，Session 取决于服务器配置；安全性：Cookie 可被用户读取篡改，Session 更安全；传输：Cookie 每次请求自动携带，Session ID 通过 Cookie 或 URL 参数传递。

**TCP 重传机制是怎么实现的？**
超时重传：RTO 内未收到 ACK 则重发，RTO 略大于 RTT 且动态变化，每次超时间隔加倍；快速重传：收到 3 个重复 ACK 立即重传丢失段，不必等超时；SACK：选项字段告知已收到的数据块，只重传缺失部分；D-SACK：告知重复接收的数据，帮助发送方判断丢的是数据包还是 ACK、是否延迟或被复制。

**TCP 流量控制是怎么实现的？**
通过滑动窗口动态调整发送速率：接收方把缓冲区剩余空间（接收窗口）通过 TCP 报文窗口字段通告发送方；窗口为 0 时发送方暂停发送，接收方读取数据后窗口扩大，发送方再加速发送，防止接收缓冲区溢出。

**TCP 拥塞控制是怎么实现的？**
维护拥塞窗口 cwnd，发送窗口 = min(cwnd, rwnd)。慢启动：每收到一个 ACK cwnd 加 1，指数增长，达到 ssthresh 后进入拥塞避免；拥塞避免：每个 ACK cwnd 增加 1/cwnd，线性增长；拥塞发生：超时重传则 ssthresh = cwnd/2、cwnd 重置为 1 重新慢启动，快速重传则 cwnd 减半进入快速恢复；快速恢复：cwnd = ssthresh + 3，重传丢失包，收到新数据 ACK 后回到拥塞避免。

**什么是 SSO？**
单点登录（Single Sign-On）：用户一次登录后即可访问多个关联应用或服务，无需再次输入凭据。普通登录认证在多系统下需反复登录。优点：降低密码重用风险、用户体验流畅、应用可将认证授权交给 SSO 系统简化开发。

**HTTP 请求过程是什么？**
输入 URL 回车 → 依次查浏览器缓存、系统缓存、路由器缓存，命中直接显示 → 否则 DNS 解析获取 IP → TCP 三次握手 → 浏览器发送 HTTP 请求 → 服务器处理并返回数据 → 浏览器检查状态码，成功则解析渲染（DOM 树、CSS、JS），失败给出提示 → 关闭连接（四次挥手）。

**HTTP 优化方案有哪些？**
TCP 复用（多个客户端请求复用到服务端一个 TCP 连接）、HTTP 复用（一个客户端多个请求复用一个连接）、内容缓存（常用内容直接内存获取）、压缩（文本压缩减少带宽）、SSL 加速、TCP 缓冲（提高服务端响应时间和处理效率）。

**浏览器地址栏输入 URL 回车后涉及哪些流程？**
查 DNS 缓存（浏览器 → 操作系统 → 路由器 → ISP），都没有则发起 DNS 查询（先 ARP 获得 DNS 服务器或网关 MAC，53 端口 UDP 请求，必要时 TCP；逐层递归查询）→ 封包（传输层加 TCP 头、网络层加 IP 头、链路层加以太网头）→ 三次握手建立 TCP 连接 → HTTP 直接请求；HTTPS 则服务端返回 3xx 重定向，重新以 443 端口建连并完成 SSL/TLS 协商 → 发送 GET/POST 请求 → 服务器处理并响应（网页、状态码、压缩类型、缓存策略、Cookie）→ 浏览器渲染 HTML 并请求图片/CSS/JS 等资源（静态文件可被缓存）→ 展示页面。

**什么是 SYN 攻击？**
攻击者伪造不同 IP 的 SYN 报文请求连接，服务端分配资源回复 SYN+ACK 后收不到回应，半连接队列被占满无法正常工作。防范：调大半连接队列、减少超时重传次数尽早丢弃无效连接；半连接队列满时启用 syn cookie——连接不进半连接队列，而是计算 cookie 值作为序列号返回，收到合法 ACK 确认后直接加入 accept 队列。

**TCP 保活机制是什么？**
定义时间段内连接无任何活动时，每隔一定间隔发送探测报文等待响应：对端正常响应则重置保活时间；对端程序崩溃则响应 RST 重置连接；探测报文不可达且达到探测次数后关闭连接。它解决的是第三次握手 ACK 丢包后客户端不发数据时，连接何时断开的问题。

**TCP 为什么需要流量控制？**
双方网速不同，一方发送过快会导致对方处理不过来，只能把数据放入缓冲区；缓冲区满后继续发送的数据包会被丢弃。因此用接收窗口（win 字段）控制发送速率，win=0 时发送方停止发送。

## 操作系统 {#os}

### 操作系统基础 {#os-basics}

操作系统是介于硬件与应用程序之间的系统软件，概念、四大特征、功能与角色定位是基础概念题的常考点。

**什么是操作系统**：操作系统（Operating System）控制和管理整个计算机系统的硬件与软件资源，调度计算机的工作与资源的分配，为用户和其他软件提供服务，是计算机系统中最基本的系统软件。

**四大特征**：

| 特征 | 含义 |
| --- | --- |
| 并发 | 两个或多个事件在同一时间间隔内发生；注意与并行（同一时刻）区分 |
| 共享 | 资源可供多个并发进程共同使用，分互斥共享（一段时间内只允许一个进程访问，即临界资源）与同时访问（宏观同时、微观交替） |
| 虚拟 | 把一个物理实体变为若干逻辑上的对应物，如虚拟内存、虚拟处理器 |
| 异步 | 进程以不可预知的速度向前推进 |

**操作系统的功能**：资源分配与回收（CPU、内存、硬盘、I/O 设备等有限资源，分配如进程调度、内存分配，回收如内存回收后的合并）；为应用程序提供服务（将硬件操作封装为统一的系统调用接口）；管理应用程序（控制进程生命周期，从环境配置、资源分配到结束后的回收）；内核四大能力：进程调度、内存管理、硬件通信、系统调用。

**操作系统的角色**：既是管理者（CPU、内存、外存、I/O 管理，并维护自身的健壮性与安全性），也是魔术师（让每个进程都认为自己独占 CPU 和整片物理内存，实际只占用一段时间片和一小块物理内存）。

**用户程序与操作系统的关系**：相互调用。计算机启动后第一个软件是操作系统，随后所有进程运行其上、使用其服务、被其监控、结束后由其回收；进程则通过调用操作系统的服务实现自身功能。

### 进程与线程 {#os-process-thread}

进程是资源分配的基本单位，线程是 CPU 调度的基本单位，二者的对比、状态转换、调度算法与通信方式是操作系统面试的核心考点。

#### 进程基础

- **概念**：运行中的可执行程序就是进程；严格定义是"具有独立功能的程序在一个数据集合上运行的过程，是系统进行资源分配和调度的独立单位"。
- **PCB（进程控制块）**：描述进程的基本情况和运行状态，是进程存在的唯一标识。包含进程描述信息（进程标识符、用户标识符）、控制管理信息（状态、优先级）、资源分配清单（地址空间、打开文件、I/O 设备）、CPU 相关信息（切换时保存的寄存器值，以便断点续行）。PCB 以链表方式组织，相同状态的进程链成队列。
- **进程状态**：基本状态为运行（占用 CPU）、就绪（可运行，等待 CPU）、阻塞（等待某事件如 I/O 完成）；另有创建、终止两个基本状态。大量阻塞进程会被换出到硬盘，由此引入挂起状态：阻塞挂起（在外存且等待事件）、就绪挂起（在外存，进入内存即可运行）。
- **状态转换特点**：只有就绪态和运行态可相互转换，其余转换单向；时间片用完由运行态转就绪态；因缺少资源（不含 CPU 时间）由运行态转阻塞态；等待的事件发生后由阻塞态转就绪态。
- **上下文切换**：切换内容包括用户空间资源（虚拟内存、栈、全局变量）和内核空间资源（内核堆栈、寄存器）。触发场景：时间片耗尽、阻塞等待、高优先级进程运行、中断处理、进程通过 sleep 主动挂起。
- **进程控制原语**：创建（分配 PCB → 分配资源 → 初始化 → 入就绪队列）；终止（终止执行，子进程交 1 号进程接管，归还资源并删除 PCB）；阻塞（保护现场入等待队列）；唤醒（移出等待队列入就绪队列）。

#### 线程基础

- **概念**：线程是进程中的一条执行流程，是程序执行的最小单位、被系统独立调度的基本单位。同一进程内多个线程共享代码段、数据段、打开的文件等资源，但各自拥有独立的寄存器和栈。
- **与 Linux 的关系**：Linux 内核不区分进程和线程，只在用户层面区分。fork 与 pthread_create 底层都调用同一个内核函数 clone——复制对方地址空间产生"进程"，共享对方地址空间产生"线程"，因此线程操作函数 pthread_* 是库函数而非系统调用。
- **线程的实现方式**：
  - 用户线程（ULT）：在用户空间实现，由用户级线程库管理。优点：切换不用进入内核空间、调度算法可进程专用、与平台无关；缺点：一个线程阻塞于系统调用则整个进程的线程都无法运行、运行中的线程无法被操作系统打断、时间片按进程分配导致多线程时每个线程时间片较少。
  - 内核线程（KLT）：由操作系统管理调度，TCB 存放在内核中。优点：一个线程阻塞不影响其他线程、时间片分配给线程可获得更多运行时间；缺点：创建、终止、切换都要经系统调用，开销较大。
  - 轻量级进程（LWP）：内核支持的用户线程，每个 LWP 与一个内核线程一对一映射，由内核管理并像普通进程一样被调度。
- **线程共享与非共享资源**：
  - 共享：文件描述符表、信号处理方式、当前工作目录、用户 ID 和组 ID；
  - 非共享：线程 id、处理器现场和栈指针（内核栈）、独立的栈空间（用户空间栈）、errno 变量、信号屏蔽字、调度优先级。
- **线程的优缺点**：优点是提高并发性、开销小、数据通信与共享方便；缺点是库函数实现不够稳定、调试编写困难（gdb 支持不好）、对信号支持不好。
- **线程属性要点**：默认为非分离状态（需 pthread_join 返回后线程才终止并释放资源）；分离状态的线程运行结束立即释放资源。注意事项：主线程退出而其他线程不退出时应调用 pthread_exit；避免僵尸线程可用 pthread_join、pthread_detach 或创建时指定分离属性；应避免在多线程模型中调用 fork（除非马上 exec）；信号语义复杂，应避免在多线程中引入信号机制；注意 Cache 伪共享（多线程同时读写同一 Cache Line 的不同变量导致缓存失效，可通过 Cache Line 字节对齐、字节填充解决）。

#### 进程与线程的对比

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 定位 | 资源分配的基本单位 | CPU 调度的基本单位 |
| 资源 | 拥有独立地址空间和资源 | 仅拥有寄存器和栈等运行必需资源，可访问隶属进程的资源 |
| 开销 | 创建、终止、切换开销大（需切换页表） | 创建、终止、切换开销小（同进程线程切换无需切换页表） |
| 通信 | 需管道、消息队列、共享内存等 IPC 机制 | 共享内存空间，直接读写共享数据即可 |
| 独立性 | 一个进程崩溃不影响其他进程 | 一个线程出错可能影响整个进程 |
| 并发性 | 进程间可并发 | 同进程、跨进程的线程均可并发，并发性更好 |

**进程切换为何比线程慢**：进程切换涉及虚拟地址空间（页表）的切换，而同进程的线程共享地址空间无需切换。页表查找本身很慢（至少访问 2 次内存），通常用 TLB（快表）缓存常用地址映射；进程切换后页表更换导致 TLB 失效、命中率降低，地址转换变慢，因此进程切换比同进程下的线程切换慢。

#### 进程调度

调度算法的性能指标：CPU 利用率、系统吞吐量（单位时间完成作业数）、周转时间（提交到完成的总时间）、等待时间（就绪队列排队时间）、响应时间（请求到首次响应）。调度方式分非抢占（进程一直运行到退出或阻塞）与抢占（可按原则暂停当前进程）。

常见调度算法：

| 算法 | 思路 | 特点 |
| --- | --- | --- |
| 先来先服务 FCFS | 按到达顺序运行完或阻塞 | 简单公平，对短作业不利，适合 CPU 繁忙型 |
| 最短作业优先 SJF | 选估计运行时间最短的作业 | 吞吐量高，长作业可能长期不被调度（饥饿） |
| 高响应比优先 | 响应比 =（等待时间 + 要求服务时间）/ 要求服务时间，选最高者 | 兼顾短作业与长作业，长作业响应比随等待增加而提高 |
| 时间片轮转 RR | 每进程运行一个时间片，用完则排到队尾 | 适合交互系统；时间片 20ms~50ms 是较合理的折中（太短切换开销大，太长响应慢） |
| 最高优先级 | 选优先级最高的进程（静态/动态优先级） | 可能导致低优先级进程永远不执行 |
| 多级队列 | 不同类型进程固定分配到不同就绪队列，各队列可用不同算法 | 满足不同用户对调度策略的不同要求 |
| 多级反馈队列 | 融合时间片轮转与优先级调度，动态调整优先级和时间片 | 综合性能最好，UNIX 采用 |

多级反馈队列实现要点：设置多个优先级递减的就绪队列；优先级越高的队列时间片越小（第 i+1 级是第 i 级的 2 倍）；每个队列用 FCFS；新进程进入第 1 级队尾，一个时间片未完成就降到下一级，最后一级用时间片轮转；仅当第 1~i-1 级队列全空时才调度第 i 级队列；高优先级队列来了新进程可抢占。

#### 进程间通信

进程之间相互独立，但内核空间是每个进程共享的，所以进程通信必须通过内核。

- **共享存储**：通信进程间存在一块可直接访问的共享空间，通过读写这片空间交换信息。存储映射 I/O（mmap）使磁盘文件与内存缓冲区相映射，进程直接读写内存即可操作文件，不需要 read/write，也无需数据拷贝，是**最快的 IPC 形式**。要点：映射文件必须有实际大小（大小为 0 会出错）；offset 必须是 4K 的整数倍；munmap 的地址必须是 mmap 的返回值；用 MAP_ANONYMOUS 标志可创建不依赖文件的匿名映射实现父子进程通信。
- **消息队列**：内核中的消息链表，消息体是固定大小的存储块，读走即删除；不主动释放则一直存在。缺点：通信不及时；每个消息体有最大长度限制、所有消息总长度也有上限；存在用户态与内核态之间的数据拷贝开销。
- **管道**：连接读进程和写进程的共享文件（pipe 文件），数据以字符流形式单向流动。特点：半双工；数据遵循先进先出；数据无格式，需双方事先约定格式；只存在于内存中，对应一个缓冲区；读数据是一次性操作，读走即释放空间；通信效率低，不适合频繁交换数据。
  - 匿名管道：无名字，用完销毁，Linux 的 `|` 就是匿名管道，只适用于父子进程间通信。
  - 命名管道（FIFO）：以路径名关联，作为特殊文件存在于文件系统中（内容存放在内存中），不相关的进程只要能访问该路径即可通信，进程退出后 FIFO 文件仍保留。命令 `mkfifo` 或函数 `mkfifo()` 创建。
- **信号量**：一个整型计数器，用于实现进程间的互斥与同步，而不是缓存通信数据。P（Wait）操作减 1，减后小于 0 则阻塞等待；V（Signal）操作加 1，加后小于等于 0 则唤醒阻塞进程。初始化为 1 即互斥信号量（任意时刻只有一个进程访问共享资源）；初始化为 0 即同步信号量（保证进程 A 在进程 B 之前执行）。
- **信号**：Linux 提供几十种信号（`kill -l` 查看），事件来源有硬件来源（如 Ctrl+C）和软件来源（如 kill 命令），是进程间**唯一的异步通信机制**。详见下文「Linux 信号」相关内容。
- **Socket**：网络编程中常见的通信方式，也可用于同一台机器上的进程间通信。`int socket(int domain, int type, int protocol)`：domain 指定协议族（AF_INET 为 IPv4、AF_INET6 为 IPv6、AF_LOCAL/AF_UNIX 为本机）；type 指定通信特性（SOCK_STREAM 字节流对应 TCP、SOCK_DGRAM 数据报对应 UDP、SOCK_RAW 原始套接字）；protocol 基本废弃，一般写 0。

#### 线程通信与僵尸进程、守护进程

- **线程通信**：目的是线程同步。同一进程的线程共享同一份内存区域，将数据复制到共享（全局或堆）变量即可，但需避免多个线程同时修改同一份数据。
- **多线程**：同一进程内所有线程共享进程内存空间，全局变量被所有线程共享。i++ 不是原子操作（涉及取数、计算、写回内存），线程切换可能发生在任何环节，需考虑线程依赖关系与同步互斥问题。多线程的好处：简化并发程序设计模型；共享同一地址空间和可用数据（多进程没有）；比进程开销小、易创建释放；IO 密集型活动可重叠运行加快执行。
- **僵尸进程**：子进程退出后、父进程读取其状态前，子进程为僵尸进程，保留进程 ID、终止状态、CPU 时间等信息供父进程 wait/waitpid 获取，但会占据内核资源。避免方法：父进程调用 wait/waitpid 等待（wait 会阻塞，waitpid 可非阻塞）；捕获 SIGCHLD 信号并在处理函数中调用 waitpid 回收；`signal(SIGCHLD, SIG_IGN)` 通知内核由 init 进程回收（并发服务器常用优化）。
- **守护进程（Daemon）**：在后台运行、没有控制终端相连、周期性执行某种任务的进程，Linux 大多数服务器（如 web 服务器 httpd）都以守护进程实现，是特殊的孤儿进程，名字一般以 d 结尾。创建模型：
  1. 创建子进程，父进程退出（必须，形式上脱离控制终端）；
  2. 子进程调用 setsid() 创建新会话（必须，脱离原登录会话、进程组和控制终端）；
  3. 可选清理：chdir() 改变当前目录为根目录（防占用可卸载的文件系统）、umask() 重设文件权限掩码、关闭不再需要的文件描述符；
  4. 开始执行守护进程核心工作（必须）。
- **相关概念**：进程组是一个或多个进程的集合，用于简化多进程管理；会话可有一个控制终端，建立连接的会话首进程为控制进程，会话中的进程组分为前台进程组与后台进程组；终端检测到断开连接时向控制进程发送挂断信号。创建会话注意：调用进程不能是进程组长；新会话丢弃原有控制终端；建立新会话的标准做法是先 fork 让父进程终止，子进程调用 setsid。

### 互斥与同步 {#os-sync}

互斥锁、读写锁、条件变量、信号量四种同步机制，加上死锁四大条件与经典 IPC 问题，是并发编程面试的高频考点。

#### 互斥锁

互斥锁（mutex）通过简单的加锁方法控制对共享资源的访问，只有加锁（lock）和解锁（unlock）两种状态。访问临界区前加锁，访问完成后解锁；加锁后其他试图再加锁的线程将被阻塞直到锁被释放。数据类型 `pthread_mutex_t`，相关函数：`pthread_mutex_init`（初始化）、`pthread_mutex_destroy`（销毁）、`pthread_mutex_lock`（阻塞加锁）、`pthread_mutex_trylock`（非阻塞，已加锁返回 EBUSY）、`pthread_mutex_unlock`（解锁）。

#### 死锁

如果一个进程集合中的每个进程都在等待只能由该集合中其他进程引发的事件，该进程集合就是死锁。

**资源分类**：可抢占资源（可从拥有它的进程抢占而不产生副作用，如存储器）；不可抢占资源（在不引起相关计算失败的情况下无法抢占）。

**死锁产生的四个必要条件**（须同时满足）：互斥（每个资源要么已分配给一个进程，要么可用）；占有和等待（已得到资源的进程可以再请求新资源）；不可抢占（已分配的资源不能被强制抢占，只能由占有进程显式释放）；环路等待（存在由两个以上进程组成的环路，每个进程都在等待下一个进程占有的资源）。

**处理方法**：

- 鸵鸟算法：不采取任何措施。解决死锁代价很高，死锁影响不大或概率很低时性能更好。
- 死锁检测与恢复：单资源类检测通过判断有向图是否存在环（深度优先搜索访问已标记节点即有环）；多资源类检测逐个寻找"请求小于等于可用资源"的未标记进程并释放其资源，算法结束后未标记的进程即死锁进程。恢复手段：利用抢占恢复（挂起进程强行取走资源）、利用回滚恢复（复位到更早的检查点状态）、杀死进程恢复（杀掉环中进程或牺牲环外进程）。
- 死锁预防（破坏必要条件）：破坏互斥（如假脱机打印机技术）；破坏占有和等待（开始前申请全部资源，或请求新资源时先释放已占资源）；破坏不可抢占（请求不到新资源就释放已有资源）；破坏环路等待（所有资源统一编号，按升序申请）。
- 死锁避免：判断当前状态是否安全——即使所有进程突然请求最大需求，仍存在某种调度次序使每个进程运行完毕则状态安全。银行家算法：对请求的满足若会导致不安全状态则拒绝，否则分配。

#### 读写锁

读多写少的场景下，读写锁允许多个线程同时读、只允许一个线程写：有其他线程读数据时允许其他线程读但不允许写；有其他线程写数据时其他线程既不能读也不能写。即读锁可与读锁共存（共享），写锁与任何锁互斥（排他）。POSIX 数据类型 `pthread_rwlock_t`，函数包括 `pthread_rwlock_init`、`pthread_rwlock_destroy`、`pthread_rwlock_rdlock`（读锁定，可多次执行但需解锁相同次数）、`pthread_rwlock_wrlock`（写锁定）、`pthread_rwlock_unlock` 及对应的 try 版本。

#### 条件变量

条件变量是用来等待而不是用来上锁的，**本身不是锁**，用于自动阻塞一个线程直到某特殊情况发生，通常与互斥锁同时使用。类型 `pthread_cond_t`。

- 两个动作：条件不满足时阻塞线程；条件满足时通知阻塞的线程开始工作。
- 核心函数：`pthread_cond_wait`（阻塞等待；进入时原子地"阻塞 + 释放互斥锁"，被唤醒返回时重新获取互斥锁）、`pthread_cond_timedwait`（限时等待）、`pthread_cond_signal`（唤醒至少一个阻塞线程）、`pthread_cond_broadcast`（唤醒全部阻塞线程）。
- 相比直接用 mutex 的优势：减少无意义竞争。若无条件变量，消费者之间也要竞争互斥量，但汇聚中没有数据时这种竞争毫无意义；有了条件变量，只有生产者完成生产后才会引起消费者竞争，提高程序效率。
- 标准使用模式：在 while 循环中检查条件并 wait（防止虚假唤醒），生产者修改共享数据后 signal/broadcast。

#### 信号量与管程

- **信号量**：广泛用于进程或线程间的同步和互斥，本质是非负整数计数器，控制对公共资源的访问；值大于 0 可访问，否则阻塞。PV 原语：一次 P 操作（sem_wait）减 1，一次 V 操作（sem_post）加 1 并唤醒等待线程。类型 `sem_t`，函数：`sem_init`（pshared 为 0 表示线程间共享，非 0 表示进程间共享）、`sem_destroy`、`sem_wait`、`sem_trywait`、`sem_timedwait`、`sem_post`、`sem_getvalue`。
- **管程**：使用信号量实现的生产者消费者问题需要客户端代码做很多控制，管程把控制的代码独立出来，不容易出错，也使客户端调用更容易。

#### 经典问题：哲学家进餐与读者写者

**哲学家进餐问题**：错误的解法是每个哲学家先拿起左边筷子再拿右边筷子——若所有人同时拿起左筷子，则都在等待他人释放筷子，造成死锁。避免死锁的两个条件：必须同时拿起左右两根筷子；只有在两个邻居都没有进餐时才允许进餐。

```c
// 哲学家进餐：检查自己与邻居状态，满足条件才允许进餐
void check(int i) {
    if (state[i] == HUNGRY && state[LEFT] != EATING && state[RIGHT] != EATING) {
        state[i] = EATING;
        up(&s[i]); // 通知第 i 个哲学家可以开始进餐
    }
}
```

**读者写者问题**：允许多个进程同时读数据，但不允许读和写、写和写同时发生。用一个整型变量 count 记录读进程数量，count_mutex 对 count 加锁，data_mutex 对数据加锁：第一个读者进入前对数据加锁（防止写进程访问），最后一个读者离开时解锁；写者直接对数据加锁写。

### 存储系统 {#os-memory}

存储层级、虚拟内存、分段分页与页面置换算法构成内存管理的完整考点链。

#### 存储器层级结构

| 层级 | 器件 | 特点 |
| --- | --- | --- |
| 寄存器 | — | 速度最快，半个 CPU 时钟周期内完成读写（2GHz 主频约 0.5ns） |
| CPU Cache | SRAM（静态随机存储器） | 有电数据即保持；通常分 L1/L2/L3 三层 |
| 内存 | DRAM（动态随机存取存储器） | 一个晶体管 + 一个电容存一位，电容漏电需定时刷新故称"动态"；密度高、功耗低、容量大、便宜；速度约 200~300 个时钟周期 |
| SSD 固态硬盘 | — | 断电数据仍保留；内存读写比 SSD 快 10~1000 倍 |
| HDD 机械硬盘 | — | 物理读写方式访问数据，比内存慢约 10 万倍 |

层级关系要点：CPU 不直接和每种存储器打交道，每种存储器只和相邻的存储器打交道；速度越快的器件成本越高，容量只能越小（寄存器、L1/L2/L3 Cache 小容量，内存、硬盘大容量）。

#### 虚拟内存

虚拟内存允许程序访问比物理内存更大的地址空间。需区分：**虚拟内存地址**是程序使用的内存地址，**物理内存地址**是实际存在于硬件里的空间地址。操作系统在两者之间建立地址映射，进程持有的虚拟地址通过 CPU 中的内存管理单元（MMU）转换成物理地址再访问内存。它由硬件异常、硬件地址翻译、主存、磁盘及内核软件共同实现。

虚拟内存三个重要能力：高速缓存（按存储层次将更小更快的上层设备作为下层设备的缓存，虚拟页分未分配、未缓存（仅磁盘）、已缓存（已在内存页框）三种类型）；内存管理（为进程提供独立内存空间，简化链接、装载与内存分配）；内存保护（通过页表条目 PTE 的标志位控制访问权限，禁止修改只读代码段、读写内核数据、访问其他进程私有内存）。

为什么需要虚拟内存：结合磁盘和物理内存的优势，提供速度足够快、容量足够大的存储；提供独立内存空间并借助多层页表翻译，进程可共享物理内存、简化链接装载和内存分配；控制进程对物理内存的访问权限，隔离进程、提高安全性。

#### 分段、分页与段页式

- **内存分段**：将物理内存划分成不同的逻辑段（代码段、数据段、堆栈段、共享库段等），每段大小和属性不同。虚拟地址由段选择子和段内偏移量组成，段号作为段表索引，段表保存段的基地址、界限和特权等级；段基地址 + 段内偏移量即物理地址。
- **内存分页**：把虚拟和物理内存切成固定大小的页（Linux 下每页 4KB），通过页表映射。虚拟地址分为页号和页内偏移，页号作为页表索引找到物理页基地址，再与页内偏移组合成物理地址。访问的虚拟地址在页表中查不到时产生缺页异常，进入内核空间分配物理内存、更新页表，再返回用户空间恢复运行。分页的优点：以页为单位释放内存，不会产生无法使用的小内存（解决外部碎片问题）；内存不足时只把最近未使用的页面暂时写入硬盘，需要时再加载（解决交换效率低的问题）；加载程序无需一次性装入物理内存，用到哪页加载哪页。
- **简单分页的空间缺陷**：32 位系统、页 4KB、虚拟内存 4GB，共 2^20 个页，每页表项 4 字节，单级页表需 4MB；100 个进程需 400MB。多级页表下二级页表在需要时才创建，只需 1024 个页表项即可覆盖全部虚拟地址空间。
- **TLB 加速**：转换检测缓冲区（TLB，快表）将虚拟页号直接映射到物理页框号。转换时硬件将虚拟页号与 TLB 所有表项同时匹配：命中则直接取出页框号不必查页表；未命中则查询页表，并淘汰一个 TLB 表项用新页表项替换。
- **段页式**：地址由段号、段内页号和页内位移三部分组成。先访问段表得到页表起始地址，再访问页表得到物理页号，最后组合页内位移得到物理地址；软硬件结合实现，增加硬件成本和系统开销，但提高内存利用率。

#### 内存碎片

内存碎片指空闲空间被分割成多个不连续的小块而非连续大块，导致内存资源利用不充分。

- **外部碎片**：整体内存容量足够，但已分配块之间的空闲空间太小，无法为较大的内存请求分配连续块。
- **内部碎片**：分配的内存块大于进程实际需要，部分内存浪费在块内部。

#### 分段与分页的对比

| 维度 | 分页 | 分段 |
| --- | --- | --- |
| 基本单位 | 固定大小的页 | 大小可变的逻辑段 |
| 对程序员的透明性 | 透明，无需干预 | 需显式划分每个段 |
| 地址空间维度 | 一维 | 二维（段号 + 段内偏移） |
| 大小是否可变 | 页大小不可变 | 段可动态改变 |
| 碎片 | 内部碎片（页内未用空间） | 外部碎片（段间空闲空间） |
| 出现原因 | 实现虚拟内存，获得更大地址空间 | 划分逻辑独立的地址空间，利于共享和保护 |

分段的好处：有助于进程间共享过程和数据（如共享库）；每个段可独立增大减小而不影响其他段。段页结合：程序地址空间先划分成多个独立段，每个段内再划分成大小相同的页，兼得共享保护与虚拟内存功能。

#### 页面置换算法

发生缺页中断时需要选择一个页面换出，常见算法：

1. **最佳置换算法（OPT）**：置换未来最长时间不访问的页面。实际系统无法实现（无法预知未来），仅作为其他算法效率的衡量标准。
2. **先进先出（FIFO）**：页面以队列保存，最先进入的先被置换。实现简单，但可能淘汰常用页面，且可能出现 Belady 异常（分配的页框数增加，缺页次数反而增加）。
3. **最近最久未使用（LRU）**：按未访问时长排列页面，置换最久未使用的页面。效果好但实现复杂，需记录访问时间或维护访问顺序列表。
4. **时钟页面置换算法**：所有页面保存在环形链表中，每页有一个访问位。缺页时顺时针遍历：访问位为 1 则改为 0 继续，直到遇到访问位为 0 的页面进行置换。
5. **最不常用（LFU）**：记录每个页面的访问次数，置换访问次数最少的页面；需统计每次访问，额外开销大。

### 文件系统 {#os-fs}

文件是对磁盘存储的抽象，考点集中在文件与目录的抽象、文件在磁盘上的实现方式与管理优化手段。

#### 文件

文件是一种抽象机制，提供在磁盘上保存信息且方便以后读取的方法，使用户不必了解信息存储的方法、位置和磁盘工作方式的细节。

- **文件结构**：字节序列（最大灵活度）、记录序列（固定长度记录）、树（记录树，按键字段排序可快速查找）。
- **文件类型与访问**：普通文件、目录、字符特殊文件、块特殊文件（UNIX）；访问方式分顺序访问（按序读取全部字节，早期系统仅有此方式）与随机访问（以任何次序读取）。
- **文件属性与操作**：属性是文件名和数据之外的信息（创建者、所有者、当前大小、日期时间等）；常见系统调用有 create、delete、open、close、read、write、append（末尾追加）、seek（定位当前位置指针以支持随机访问）、get/set attributes、rename。

#### 目录

目录用于记录文件的位置，很多操作系统中目录本身也是文件。

- 目录结构：一级目录系统（所有文件在根目录中），文件众多时采用层级目录系统（目录树）。
- 路径名：绝对路径由根目录到文件的路径组成（UNIX 以 `/` 开头，如 `/usr/ast/mailbox`）；相对路径配合工作目录（当前目录）使用。特殊目录项：`.` 指当前目录，`..` 指父目录。
- 目录操作（Unix）：create、delete、opendir、closedir、readdir、rename、link（允许同一文件出现在多个目录中）、unlink（删除目录项）。

#### 文件系统的实现

- **文件系统布局**：磁盘分为多个分区，每分区有独立文件系统。0 号扇区为主引导记录（MBR），结尾是分区表（给出各分区起止地址）；计算机引导时 BIOS 读入并执行 MBR，MBR 确定活动分区、读入其第一个块（引导块）并执行，引导块中的程序装载该分区中的操作系统。
- **文件的实现**（记录文件用到哪些磁盘块）：
  - 连续分配：文件作为一连串连续数据块存储。只需记住首块地址和块数即可，单个操作就能读出整个文件、只需一次寻道；但增删代价大、易产生碎片。
  - 链表分配：每块第一个字作为指向下一块的指针。充分利用磁盘块、不浪费空间；但指针占用字节使数据块不再是 2 的整数次幂，且随机访问需要逐块拼接信息，开销大。
  - 内存中的表进行链表分配（FAT，文件分配表）：把指针字放在内存的表中，解决链表分配的不足。
  - i 节点：给每个文件赋予一个数据结构，列出文件属性和磁盘地址。
- **目录的实现**：读文件前必须先打开，操作系统利用路径名找到目录项。简单目录在目录项中放磁盘地址和属性；采用 i 节点的系统把属性放在 i 节点中，目录项更短。
- **共享文件**：共享文件与目录的联系称为链接（link），此时文件系统是有向无环图（DAG）而非一棵树。
- **日志文件系统**：保存一个记录系统下一步将要做什么的日志，崩溃重启后查看日志完成未竟任务。微软 NTFS、Linux 的 ext3 和 ReiserFS 都使用日志。（日志结构文件系统 LFS 设计诱人但未被广泛应用。）
- **虚拟文件系统（VFS）**：将多个文件系统整合到统一结构中，用户视角只有一个文件系统层级。如 Linux 可用 ext2 作根文件系统、ext3 装载在 /usr、ReiserFS 硬盘装载在 /home、ISO 9660 光盘装载在 /mnt。

#### 文件系统的管理和优化

- **磁盘空间管理**：文件分割成固定大小的块存储，块大小历史上多设在 1~4KB，大磁盘时代可提升到 64KB 并接受浪费。记录空闲块的方式：磁盘块链表（每块存放尽可能多的空闲块号）、位图（空闲块用 1 表示、已分配用 0 表示）。磁盘配额机制限制每个用户拥有的文件和块的最大数量。
- **备份**：应对意外灾难恢复和错误操作恢复两个问题。
- **一致性**：读取磁盘块修改后再写回，若写回前崩溃（尤其是 i 节点块、目录块、空闲表块）会处于不一致状态。
- **性能优化**：块高速缓存（逻辑上属于磁盘、实际保存在内存中的块）；块提前读（仅对顺序读取的文件有效，随机访问无效）；减少磁盘臂运动（把可能顺序访问的块放在一起，最好同柱面）。
- **磁盘碎片整理**：移动文件使它们相邻，把空闲空间集中到一个或多个大的连续区域。

### 磁盘 {#os-disk}

磁盘的核心矛盾是寻道慢，多层抽象与调度算法都围绕减少寻道时间展开。

#### 磁盘结构与 IO 过程

- **结构**：盘面（多个堆叠的盘片）、磁道（盘面上的同心圆）、扇区（磁道上的一段小区域）。
- **磁盘 IO 三步骤**：寻道（磁头移动到指定磁道）→ 旋转（盘片旋转使磁头对准指定扇区）→ 传输（对指定扇区进行数据读写）。
- **生磁盘与熟磁盘**：根据盘块号使用磁盘是生磁盘；根据文件使用磁盘是熟磁盘。磁盘工作方式：发送 out 指令 → 文件视图 → 中断。

#### 三层抽象

1. **一层抽象（盘块号）**：直接使用柱面 C、磁头 H、扇区 S 编址对用户不友好，于是抽象为盘块号 block，由系统计算 C/H/S。编址公式：`block = C × (Heads × Sectors) + H × Sectors + S`。由于寻道时间更长，编址时一个磁道用完后向下一个柱面继续编号（而非下一磁道），以缩短寻道时间。
2. **二层抽象（请求队列 + 调度算法）**：多个磁盘访问请求进入队列，操作系统用磁盘调度算法挑选请求服务。
3. **三层抽象（文件）**：普通用户不知道扇区为何物，在盘块之上再引入文件抽象——用户眼中的文件是字符流，磁盘上的文件是盘块集合，需建立字符流到盘块集合的映射。常见映射（文件实现）方式：顺序结构（FCB 记录文件起始块号，按 `n / 块大小 + 起始块号` 计算盘块号，不利于增删修改）、链式结构（利于增删，不利于查询）、索引。

#### 磁盘调度算法

| 算法 | 思路 | 优点 | 缺点 |
| --- | --- | --- | --- |
| FCFS | 按请求到达顺序服务 | 公平 | 不提供最快服务，磁头往返移动耗时长 |
| SSTF | 每次选距当前磁头最近的请求 | 寻道时间最短 | 远距离请求可能"饥饿" |
| SCAN（电梯算法） | 先处理一个方向的请求，再处理反方向 | 不会有请求饥饿 | 平均寻道时间不是最优 |

### 外设管理 {#os-device}

外设驱动的统一套路是「out 指令 + 文件视图 + 中断」三步。

- **让外机动起来的三步**：CPU 向外设的控制器发送指令（out 指令）；将外设统一抽象为文件视图（统一 out 指令的形式）；外设处理完成后通过中断通知 CPU 继续接手下一步处理。
- **键盘如何工作**：按键触发中断，中断处理程序根据扫描码获取对应的 ASCII 码，将其加入缓冲队列 read_que，等待上层程序调用读取。
- **显示器如何工作**：printf 本质是向显卡控制器的显存写入字符数据，由显示设备按刷新周期输出，同样经由文件视图与 out 指令完成。

### Linux 专题 {#os-linux}

IO 多路复用、进程内存布局、五种 IO 模型与软硬链接是 Linux 方向面试的高频主题。

#### Linux 设计要点

Linux 设计要点：MultiTask 多任务（多个任务同时执行，可为并发或并行）；SMP 对称多处理（每个 CPU 地位相等、权限相同，共享一个内存，均可访问完整内存和硬件资源）；ELF 可执行文件链接格式（Linux 可执行文件的存储格式）；宏内核（进程调度、内存管理、文件系统、设备驱动等所有模块都运行在内核态，内核是拥有最高权限的完整可执行程序）。

#### Linux 进程内存管理

进程的虚拟地址空间从低到高分为：

1. 程序文件段（TEXT）：二进制可执行代码，只读；
2. 已初始化数据段（DATA）：已初始化的全局变量和静态常量；
3. 未初始化数据段（BSS）：未初始化的静态变量和全局变量；
4. 堆段：动态分配的内存，从低地址向高地址增长；
5. 文件映射段：动态库、共享内存等，从低地址向上增长（与硬件和内核版本有关）；
6. 栈段：函数参数、局部变量、函数调用上下文，从高地址向低地址增长，大小固定（一般 8MB，可自定义）。

#### Linux 虚拟内存

32 位处理器的虚拟内存空间为 4GB，每个进程都认为自己拥有连续的 4GB 空间，实际只对应少量物理内存碎片，一部分还存在磁盘上按需交换。应用程序需要两次映射：先映射到虚拟内存空间，再映射到物理内存空间；第二次映射由硬件（存储管理单元 MMU）与操作系统内存管理模块共同完成。

- 缺页异常处理：进程访问的虚拟地址在页表中查不到时，产生缺页异常，进入内核空间分配物理内存、更新进程页表，再返回用户空间恢复运行。
- 上下文切换涉及内容：寄存器（含 TLB）、程序计数器、用户栈、内核栈、内核数据结构（页表、task_struct、mm_struct）。

#### Linux 信号

信号是用户、系统、进程发送给目标进程的信息，通知某个状态的改变或系统异常。常用信号：

- SIGHUP：控制终端挂起；
- SIGPIPE：向读端关闭的通道或 socket 连接中写数据；
- SIGURG：socket 连接上收到紧急数据。

信号的详细机制：

- **特点**：简单、不能携带大量信息、满足特定条件才发送；是软件层次上对中断机制的模拟（软件中断）、异步通信方式；周期为产生 → 注册/注销 → 执行信号处理函数。
- **信号编号**：不存在 0 号信号，也没有 32、33 号；1~31 为常规信号（普通/标准信号），34~64 为实时信号。需记住的重要信号：SIGINT（Ctrl+C 终止进程）、SIGQUIT（Ctrl+\ 终止进程）、SIGSEGV（无效内存访问即段错误，终止进程并产生 core 文件）、SIGPIPE（向无读端的管道写数据）、SIGCHLD（子进程结束时父进程收到）。SIGKILL（9）和 SIGSTOP（19）不允许忽略和捕捉，只能执行默认动作。
- **信号四要素**：编号、名称、事件、默认处理动作（Term 终止、Ign 忽略、Core 终止并生成 core 文件、Stop 暂停、Cont 继续）。
- **信号状态**：产生（终端按键、硬件异常、软件异常、kill/raise/abort 等系统函数、kill/killall 命令）、未决（产生但未被处理）、递达（已被处理）。
- **阻塞信号集（信号掩码）与未决信号集**：屏蔽某信号后收到该信号，处理将推迟到解除屏蔽之后；信号产生时未决信号集中对应位翻转为 1，处理完翻转为 0。sigprocmask 检查或修改阻塞集（SIG_BLOCK 并集、SIG_UNBLOCK 删除、SIG_SETMASK 覆盖）。
- **信号相关函数**：kill（给指定进程发信号）、raise（给自己发信号，等价 kill(getpid(), sig)）、abort（发送 SIGABRT）、alarm（定时发送 SIGALRM，每进程唯一）、setitimer（微秒精度、可周期定时）、sigaction（信号捕捉，替代 signal）、sigpending（读取未决信号集）。
- **可重入与不可重入**：不可重入函数使用了静态数据结构、调用了 malloc/free 或标准 I/O 函数；可重入函数尽量使用局部变量，全局变量需加保护（关中断、信号量等互斥方法）。信号处理函数中应避免调用不可重入函数。

#### 五种 IO 模型

一次输入操作分两个阶段：等待数据准备好（数据从网络到达并复制到内核缓冲区）、从内核向进程复制数据（内核缓冲区复制到应用进程缓冲区）。五种模型：

1. **阻塞式 I/O**（默认）：调用 recvfrom 后进程阻塞，直到数据准备好并复制完成才返回。设备不可操作时进程休眠让出 CPU；耗费时间，适合并发低、时效性要求低的场景。
2. **非阻塞式 I/O**：数据未准备好时内核立即返回 EWOULDBLOCK 错误，进程通过轮询（polling）反复询问，某次发现就绪则复制数据。缺点是耗费大量 CPU 时间。
3. **I/O 复用（select/poll）**：进程阻塞在 select/poll 系统调用上而非真正的 I/O 调用上；任意一个被监听的 fd 数据就绪，select 返回，进程再调用 recvfrom 拷贝数据。优点是可以同时等待多个描述符就绪。
4. **信号驱动式 I/O**：通过 sigaction 安装 SIGIO 信号处理函数后立即返回不阻塞；数据准备好后内核产生 SIGIO 信号，在信号处理函数中调用 recvfrom 读取。等待期间进程不被阻塞。
5. **异步 I/O**：进程调用 aio_read 告知内核整个操作（包括把数据拷贝到用户空间）完成后如何通知自己，然后立刻去做其他事；内核完成整个操作后才通知进程。与信号驱动的区别：信号驱动是内核通知"何时可以启动一个 I/O 操作"，异步是内核通知"I/O 操作何时完成"。

前四种为同步 I/O（区别在第一阶段等待数据的处理方式，第二阶段均阻塞于 recvfrom），异步 I/O 不导致请求进程阻塞。

#### IO 多路复用：select/poll/epoll

I/O 多路复用是在单个线程或进程中处理多个输入输出操作的机制：单个进程同时监视多个文件描述符（通常是套接字），一个或多个 fd 准备好读或写时立即响应，避免了创建多个线程或进程的开销。

| 对比项 | select | poll | epoll |
| --- | --- | --- | --- |
| fd 组织方式 | 位图（fd_set） | 动态数组（链表形式组织） | 内核红黑树 + 就绪链表 |
| fd 数量限制 | 有（通常 1024，64 位系统 2048） | 无限制（受系统 fd 上限约束） | 无限制（1GB 内存约可监听 10 万个端口） |
| 就绪检测方式 | 轮询扫描整个集合，O(N) | 遍历整个数组，O(N) | 事件驱动回调，只返回就绪 fd，O(1) |
| 数据拷贝 | 每次调用两次拷贝（用户↔内核），需每次重设集合 | 每次调用需重设数组 | 通过内核与用户空间共享内存，只需传入待检测的 socket |
| 触发模式 | 仅 LT | 仅 LT | 支持 LT 和 ET |
| 平台 | POSIX 规定，多数 OS 均有 | 多数 OS | Linux 特有（BSD 对应 kqueue） |

epoll 细节：

- `epoll_ctl()` 把需要监控的 socket 加入内核红黑树（增删查 O(logn)），不需要每次传入整个集合，减少了内核和用户空间的大量数据拷贝与内存分配；
- 内核维护就绪链表记录就绪事件（socket 有事件时通过回调函数加入链表），`epoll_wait()` 只返回有事件发生的文件描述符的个数，无需轮询扫描整个集合；
- **边缘触发（ET）**：可读事件发生时只从 epoll_wait 苏醒一次，即使没调用 read 也只通知一次，程序必须一次性把内核缓冲区数据读完；
- **水平触发（LT）**：只要内核缓冲区还有数据没读完，就不断地把事件传递给用户，直到数据被 read 读完。

性能结论：一般 epoll 效率高于 select 和 poll；但活动连接很多时回调函数触发频繁，epoll 不一定占优——epoll 在"连接总数多、活动连接少"的场景下优势最明显。

#### Linux 服务器模型

提升服务器响应能力的方式：多进程服务器（父进程处理连接、fork 子进程处理业务，开销大且需处理僵尸进程与父子通信问题）；I/O 复用服务器（不额外创建进程即可同时服务多个请求端）；多线程服务器（同进程线程共享系统资源、通信方便、切换开销小，需考虑线程创建销毁、线程安全与线程通信）。

#### 软链接与硬链接

| 对比项 | 软链接（符号链接） | 硬链接 |
| --- | --- | --- |
| 物理实现 | 独立文件，包含指向目标文件或目录的路径 | 目标文件的额外目录项，多个目录项指向相同 inode |
| 链接目标 | 可链接文件或目录，甚至不存在的文件 | 只能链接文件，且必须同一文件系统 |
| 删除原文件的影响 | 软链接仍在但失效（坏链接 dangling link） | 不受影响，只是 inode 的另一个引用；所有硬链接删除后才释放数据块 |
| 链接计数 | 不增加 inode 链接计数 | 增加 inode 链接计数，计数为 0 时释放数据块 |
| 创建命令 | `ln -s target_file link_name` | `ln target_file link_name` |
| 跨文件系统 | 可以 | 不可以 |

### 面试一问一答速查 {#os-qa}

**什么是中断和异常？**
二者都会使处理器暂停当前任务、转去执行特定处理程序，处理完后返回被打断的任务继续执行。区别：中断由系统外部事件触发（时钟中断、I/O 设备中断、硬件错误），目的是及时响应重要事件；异常由系统内部事件触发（非法操作码、地址越界、运算溢出），与正在执行的程序或指令有关，不能被屏蔽。

**用户态和核心态有什么区别？什么场景下切换？**
用户态只能访问受限资源、执行受限指令，不能直接访问内核和硬件；核心态是特权级别，可执行特权指令、直接访问硬件、执行系统调用。切换场景：系统调用、异常、外部设备中断。

**并行和并发是什么？**
并行是同一时刻执行多个任务（多个处理单元如多核同时执行）；并发是相同时间段内执行多个任务，任务交替执行，靠时间片轮转或事件驱动调度实现。

**什么是内部碎片和外部碎片？**
内部碎片：分配的内存块大于进程实际需要，块内部有浪费；与分页（页大小固定）相关。外部碎片：整体容量足够，但空闲空间被分割成不连续小块，无法满足较大的连续内存请求；与分段相关。

**说一说僵尸进程和孤儿进程。**
孤儿进程：父进程退出而子进程仍在运行，子进程成为孤儿进程，被 init 进程（1 号进程）收养并完成状态收集。僵尸进程：子进程退出后父进程未调用 wait/waitpid 获取状态，子进程的进程描述符仍保存在系统中；僵尸进程占据内核资源，应通过 wait/waitpid、捕获 SIGCHLD 后回收、或 signal(SIGCHLD, SIG_IGN) 交内核回收来避免。

**信号和信号量有什么区别？**
信号是一种处理异步事件的方式，是较复杂的通信机制，用于通知接收进程某事件发生，也可发给进程本身。信号量是进程间（及线程间）处理同步互斥的机制，协调各方合理使用公共资源。

**常用的 Linux 命令有哪些？**
文件目录类：ls、cd、pwd、touch、mkdir、rm、cp、mv、cat、vi、head/tail、find、chmod、chown；进程类：ps、kill；系统类：df、tar、ifconfig、ping、ssh；文本搜索：grep；包管理：apt（Debian/Ubuntu）、yum（Red Hat/CentOS）。

**Linux 中如何查看一个进程？**
`ps aux | grep myprocess` 用 ps 列出进程并用 grep 过滤；`pgrep myprocess` 和 `pidof myprocess` 直接按进程名查找 PID。

**如何杀死一个进程？**
`kill [options] PID` 向进程发送信号终止进程；`killall` 按进程名杀死所有匹配进程。注意杀死父进程并不会杀死子进程，子进程会成为孤儿进程由 init 接管（可用 pstree 观察）。

**什么是局部性原理？**
一段时间内程序倾向于多次访问相同或相近的数据而非随机访问内存。时间局部性：被访问的数据不久后很可能再次被访问（如循环中反复访问数组元素），可将其缓存以减少访存；空间局部性：被访问数据附近的数据也很可能被访问（如遍历数组访问相邻元素），文件系统将相关数据块放在相邻扇区以加快访问。

**进程、线程的区别？**
进程是资源分配和调度的基本单位，线程是运算调度的最小单位、进程内的执行单元；一个进程至少有一个线程，多线程共享同一块内存。资源开销：进程有独立内存空间，创建销毁和上下文切换开销大，线程共享内存空间、开销小。通信：进程需管道、消息队列、共享内存等特殊机制，线程直接访问共享数据。安全性：进程相互隔离，一个崩溃不影响其他进程；线程共享内存，一个线程出错可能影响整个进程。

**进程的状态有哪些？**
三种基本状态：就绪（获得除处理机外的一切资源，得到 CPU 即可运行）、运行（在处理机上运行，单处理机系统中只有一个）、阻塞（等待某事件如 I/O 完成而暂停，即使分配 CPU 也无法运行）。五种状态：创建（申请 PCB、填写信息、分配资源）、就绪、执行、阻塞（I/O 请求、申请缓冲区失败等）、终止（结束、出错或被系统终止）。

**进程之间的通信方式有哪些？**
管道（半双工、单向流动、仅父子进程）、命名管道（半双工，允许无亲缘关系进程通信）、信号量（计数器，控制对共享资源的访问，作同步手段）、消息队列（内核中的消息链表，克服信号信息少、管道无格式字节流及缓冲区受限等缺点）、信号（通知接收进程某事件已发生）、共享内存（映射一段多进程可访问的内存，是最快的进程通信方式，常与信号量配合实现同步）、Socket（支持 TCP/IP 网络通信的基本操作单元，用于客户端与服务器间通信）。

**线程之间的同步方式有哪些？**
互斥锁（只允许一个线程访问临界区）、条件变量（线程间通信，等待条件满足并可被信号通知，通常与互斥锁一起使用）、读写锁（多线程同时读、只允许一个线程写）、信号量（控制多个线程对共享资源的访问）。

**介绍一下你知道的锁。**
两个基础的锁：互斥锁（任何时刻只有一个线程可持有，其他线程等待释放）与自旋锁（基于忙等待，不断轮询直到锁释放），其他锁都基于这两者。读写锁：允许多线程同时读、单线程写，分读（共享）和写（排他）两种状态。悲观锁：认为并发修改概率高，访问共享资源前先上锁；乐观锁：先修改共享资源，若出现同时修改再放弃本次操作。

**什么情况下会产生死锁？**
两个或多个进程争夺系统资源时互相等待对方释放资源而无法继续执行。必须同时满足四个条件：互斥条件（资源被占用时其他进程无法同时占用）、请求保持条件（请求资源阻塞时不释放已有资源）、不可剥夺条件（资源不能被强制剥夺，只能由持有者自愿释放）、环路等待条件（进程间形成循环等待链）。

**如何解除死锁？**
破坏四个条件之一即可。破坏请求与保持：一次性申请所有资源；破坏不可剥夺：申请不到新资源时主动释放已占有的资源；破坏循环等待：所有进程按相同顺序申请资源（按序申请、反序释放）。此外还可通过死锁检测（有向图找环）后用抢占、回滚或杀死进程的方式恢复。

**进程的调度算法有哪些？**
批处理系统：先来先服务（非抢占，按请求顺序，利于长作业不利短作业）、最短作业优先（非抢占，按估计运行时间最短，长作业可能饿死）、最短剩余时间优先（最短作业优先的抢占式版本）。交互式系统：时间片轮转（FCFS 排队，时间片用完由时钟中断送回队尾）、优先级调度（可随时间推移提高等待进程优先级防饿死）、多级队列（多个时间片和优先权不同的队列，可看作时间片轮转与优先级调度的结合）、最短进程优先。

**分段和分页的区别？**
分段：地址空间划分为不同逻辑段，段长可动态变化、各段可不同，可能产生内部碎片（段内未用空间）和外部碎片（段间空闲空间），逻辑地址 = 段号 + 段内偏移。分页：地址空间划分为固定大小的页面，物理内存划分为相同大小的页框，页长固定由操作系统定义，可能产生内部碎片（页内未用空间），逻辑地址 = 页号 + 页内偏移。

**页面置换算法有哪些？**
LRU（最近最少使用）：置换最长时间未被使用的页面，效果好但实现复杂。FIFO（先进先出）：置换最早进入内存的页面，简单但可能淘汰常用页面，且可能出现 Belady 异常（分配空间增加缺页反而增加）。OPT（最佳置换）：置换未来最长时间不访问的页面，实际无法实现，仅作衡量标准。时钟算法：环形链表加访问位，遍历到访问位为 0 的页面置换。最不常用（LFU）：置换访问次数最少的页面，统计开销大。

**什么是 IO 多路复用？**
在单个线程或进程中处理多个 I/O 操作的机制，单个进程同时监视多个文件描述符，一个或多个就绪时立即响应，避免创建多个线程或进程的开销。通过 select、poll、epoll 系统调用实现：select 最古老，用位图监视多个 fd 但有数量限制（通常 1024）且效率随数量增加而降低；poll 用动态数组改进了数量限制，但大量 fd 时仍需遍历、效率不足；epoll 为 Linux 特有，事件驱动、只在 fd 就绪时通知应用，处理大量 fd 高效，适合高并发场景。

## 数据库：MySQL {#mysql}

### MySQL 基础 {#mysql-basic}

一句话：主键/外键/索引、表连接与 SQL 执行流程是地基，后面的索引、事务、锁等高频问题都建立在这些概念之上。

**主键、外键、索引的区别**

| 对象 | 定义 | 作用 |
| --- | --- | --- |
| 主键 | 唯一标识一条记录，不允许重复、不允许为空 | 唯一标识表中每一行 |
| 外键 | 一个表中的字段，其值是另一个表的主键 | 与其他表建立联系 |
| 索引 | 没有重复值，但可以有一个空值 | 提高查询、排序的速度 |

主键和外键通常与索引有关，但索引不一定是主键或外键。

**表连接**

- 连接：将各表记录取出依次匹配后发给客户端；若结果包含两表所有记录的组合即为笛卡尔积（表 a 5 条、表 b 6 条，笛卡尔积为 30 条）。
- 连接过程：先确定驱动表，取驱动表中每条满足条件的记录到被驱动表中查找匹配；驱动表只访问一次，被驱动表可能多次访问。
- 内连接：驱动表记录在被驱动表中无匹配时不进入结果；外连接：无匹配也进入结果（左外连接左侧为驱动表，右外连接右侧为驱动表）。内连接两表顺序可互换，外连接不可。
- `where` 与 `on`：不符合 where 的记录一律不进入结果；on 在内连接中等价于 where，在外连接中无匹配的驱动表记录仍保留，被驱动表字段以 NULL 填充。嵌套循环连接：三表连接时，前两表连接的结果作为驱动表，再与第三张表连接。

**执行一次 select 语句发生了什么**

MySQL 架构分为 Server 层（建立连接、分析执行 SQL）和存储引擎层（数据存储提取，常用 InnoDB，B+ 树索引）：

1. 连接器：建立连接、获取并验证权限；空闲连接由 `wait_timeout` 控制（默认 8 小时）。建议用长连接，但过多长连接可能内存占用过大（OOM），可定期断开或用 `mysql_reset_connection`（5.7+）重置连接资源。
2. 查询缓存：命中则直接返回；表频繁更新会导致缓存不一致，不建议使用，MySQL 8.0 已移除。
3. 解析 SQL：词法分析识别关键字，语法分析判断是否符合语法并构建语法树。
4. 执行 SQL：预处理（判断表和字段是否存在）→ 优化（基于查询成本选择索引、决定多表连接顺序）→ 执行（先判断权限，再从存储引擎读取记录返回）。

**执行一次 update 语句发生了什么**：同样走一遍查询流程（表更新会使相关查询缓存失效），但额外涉及两个日志模块——redo log（重做日志）与 binlog（归档日志），详见日志章节。

### 账号与权限语句 {#mysql-account}

一句话：为安全应最小授权，用户账号统一存放在 `mysql` 库的 `user` 表中，不推荐直接 insert 该表。

- 新增用户：`CREATE USER zhangsan IDENTIFIED BY '123456';`；改名：`RENAME USER zhangsan TO lisi;`
- 修改密码：`SET PASSWORD FOR lisi = Password('135790');`（不指定用户名则修改当前登录用户）；删除用户：`DROP USER lisi;`（MySQL 5 以下需先 revoke 全部权限才能删除）
- 查看权限：`SHOW GRANTS FOR user;`，其中 `GRANT USAGE ON *.* TO ...` 表示没有任何权限。
- 授权与撤销：`GRANT select ON 库名.表名 TO 用户;` / `REVOKE select ON 库名.表名 FROM 用户;`

### 索引 {#mysql-index}

一句话：索引是为了提高查询效率的数据结构（类似书的目录），查询只有全表扫描和索引检索两种方式；用 `create index 索引名 on 表名(列名);` 创建、`drop index 索引名 on 表名;` 删除，SQL 前加 `explain` 查看是否走索引（type=ALL 为全表扫描）。

**索引的分类**：按数据结构分 B+tree、Hash、Full-text 索引；按物理存储分聚簇索引（主键索引）、二级索引（辅助索引）；按字段特性分主键索引（一张表最多一个，不允许空值）、唯一索引（值必须唯一，允许空值）、普通索引、前缀索引（对字符字段前几个字符建索引，减小索引大小）；按字段个数分单列索引、联合索引。

**从数据结构看索引选型**：哈希表插入快但无序，只适合等值查询；有序数组等值与区间查询都好（二分 O(logN)）但增删要移动数据，只适合静态存储；二叉搜索树兼顾查询与增删但需保持平衡，且索引要写磁盘、二叉树太高 IO 次数多；N 叉树通过增加分叉降低树高、减少读磁盘次数，是查询性能与 IO 次数的折中，广泛应用于数据库引擎。

**InnoDB 的 B+ 树索引模型**：每个索引对应一棵 B+ 树。主键索引（聚簇索引）叶子节点存放完整记录；二级索引叶子节点存放主键值，查询需先查到主键再回主键索引查整行（回表）。若查询所需数据在二级索引叶子节点即可获得则无需回表，称为覆盖索引，是常用的性能优化手段，因此应尽量使用主键查询。

**最左匹配原则**：联合索引按最左优先方式匹配，查询条件要从索引最左边列开始且不能跳过中间列，否则索引可能失效。遇到范围查询（>、<）时停止匹配，范围字段可用索引，其后的字段用不到联合索引。

**索引下推（ICP）**：MySQL 5.6 引入。在联合索引遍历过程中，先对联合索引中包含的字段做判断，直接过滤不满足条件的记录，减少回表次数。例如 `where name like '张%' and age=10 and ismale=1`，5.6 之前只能用「张」逐条回表再比对，索引下推后先在索引里过滤 age 条件，回表次数从 4 次降到 2 次。

**索引区分度**：字段不同值的个数占全表的比例；建联合索引时，区分度大的字段应排在前面。

**建索引的注意事项与时机**

- 需要：频繁查询的列、大表、查询经常包含唯一性条件的列、连接表的外键列、经常用于 ORDER BY / GROUP BY 的列。
- 不需要：小表、经常更新的字段、很少用于查询的字段、大量重复数据的字段（如性别）。
- 优缺点：优点是大大加快检索速度、唯一性索引保证行唯一性；缺点是空间消耗大（每个索引一棵 B+ 树，节点为 16KB 的页），且增删改时索引需动态维护。
- 优化方法：前缀索引、覆盖索引、主键用自增（避免随机插入导致页分裂）、避免过多索引。

**索引失效场景**：左或左右模糊匹配（`LIKE '%abc'`）；索引列上使用函数或表达式；OR 前是索引列而 OR 后不是；违背最左匹配原则；数据分布不均匀导致选择性降低；隐式类型转换（字符串与数字比较）。

**为什么使用 B+ 树**

1. 非叶子节点不存放实际数据仅存索引，同样数据量下比 B 树更「矮胖」，查询底层节点的磁盘 IO 次数更少。
2. 有大量冗余节点（非叶子节点都是冗余索引），插入、删除效率更高，不会像 B 树那样发生复杂的树变化。
3. 叶子节点之间用链表连接，有利于范围查询；B 树范围查询只能遍历，涉及多次磁盘 IO。

### 事务 {#mysql-transaction}

一句话：MyISAM 不支持事务因此被 InnoDB 取代；事务的核心是 ACID、并行事务问题与隔离级别、MVCC。

**ACID 四大特性**

| 特性 | 含义 | 实现依赖 |
| --- | --- | --- |
| 原子性 | 事务不可分割，要么全执行要么全不执行，出错回滚 | undo log（回滚日志） |
| 一致性 | 从一个一致状态转变到另一个一致状态 | 原子性 + 隔离性 + 持久性 |
| 隔离性 | 并发事务之间互不可见中间状态 | MVCC（多版本并发控制）或锁机制 |
| 持久性 | 提交后结果永久保存，系统故障也不丢失 | redo log（重做日志） |

**并行事务的问题**：脏读（读到其他事务未提交的数据，若对方回滚则数据无效）；不可重复读（同一事务内两次读同一数据结果不同，因被其他事务修改）；幻读（同一事务内两次查询同一范围的记录数量不一致，专指新插入的行）。

**四种隔离级别**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 |
| 读提交（RC） | 不可能 | 可能 | 可能 |
| 可重复读（RR，InnoDB 默认） | 不可能 | 不可能 | 可能 |
| 串行化 | 不可能 | 不可能 | 不可能 |

串行化通过加读写锁使事务效果如同顺序执行，并发性能最低；隔离级别越高一致性越强、并发性能越低，需按业务权衡。

**幻读是如何解决的**：InnoDB 默认 RR 级别下很大程度上可避免幻读。快照读（普通 select）通过 MVCC 解决；当前读（`select ... for update` 等）通过 next-key lock（记录锁 + 间隙锁）解决，锁住范围内无法插入新记录。

**事务隔离的实现与 Read View**

- 读未提交直接读最新数据，串行化加读写锁，RC 和 RR 通过 Read View 实现：RC 在每个 select 都生成新的 Read View，因此事务期间可能读到别人已提交的修改；RR 在事务启动时生成一个 Read View 并全程使用，保证事务期间读到的都是事务启动前的数据。
- Read View 包含：m_ids（活跃事务 id 列表）、min_trx_id（活跃事务中最小的 id）、max_trx_id（下一个待分配的事务 id）、creator_trx_id（创建者的事务 id）。聚簇索引记录有两个隐藏列：trx_id（最后改动该记录的事务 id）和 roll_pointer（指向 undo log 中的旧版本，串成版本链）。
- 可见性判断：记录的 trx_id 小于 min_trx_id 则可见（Read View 前已提交）；大于等于 max_trx_id 则不可见（Read View 后才启动）；介于两者之间时，在 m_ids 列表中则未提交、不可见，不在则已提交、可见。

**读已提交（RC）是怎么实现的**：基于 MVCC。读操作只能看到已提交事务产生的版本；写操作创建新的数据版本而不是直接修改原始数据，保证进行中的事务看不到未提交的更改。

**事务的启动方式与长事务**

- 显式启动：`begin / start transaction` + `commit / rollback`；或 `set autocommit=0`。后者会使后续查询都在事务中，长连接下导致长事务，建议 `set autocommit=1`。长事务可在 `information_schema` 库的 `innodb_trx` 表中查询。
- 避免：应用端（改回 autocommit=1、减少不必要的只读事务、`set max_execution_time` 控制语句最长执行时间）；数据库端（监控长事务阈值报警/kill、用 percona 的 pt-kill 工具、测试阶段分析日志、innodb_undo_table_spaces 设为 2 或更大）。

### 锁 {#mysql-lock}

一句话：锁是实现隔离级别的方式，按粒度分全局锁、表级锁、行级锁；InnoDB 绝大部分情况用行锁。

**全局锁**：`flush tables with read lock (FTWRL)` 使整个库只读，典型场景是全库逻辑备份；会阻塞数据增删改、DDL（建表改表结构）和更新类事务的提交。

**表级锁**

- 表锁：`lock tables ... read/write`，开销小加锁快，并发度最低；`unlock tables` 释放；还会限定本线程接下来的操作对象。
- 元数据锁（MDL）：访问表时自动加，无需显式使用（5.5 引入）。增删改查加 MDL 读锁，表结构变更加 MDL 写锁；读锁之间不互斥，读写、写写互斥；事务中语句开始时申请、事务提交才释放，可能引发死锁。
- 意向锁：指示事务未来可能对某些资源（行）加锁，分意向共享锁/意向排他锁。是表级锁，不与行级共享/排他锁冲突，意向锁之间也不冲突，只与表级共享/排他锁冲突，目的是快速判断表里是否有记录被加锁。
- AUTO-INC 锁：插入数据时加表级锁保证自增主键值连续递增，其他事务插入被阻塞，影响大批量插入性能。InnoDB 提供轻量级锁改进：为自增字段赋值后立即释放，不等整条插入语句执行完。

**行级锁**

- Record Lock（记录锁）：仅锁一条记录，分排他锁和共享锁。
- Gap Lock（间隙锁）：锁定一个范围但不包含记录本身，只存在于 RR 隔离级别，用于解决幻读；间隙锁之间是兼容的。
- Next-Key Lock：Record Lock + Gap Lock，锁定范围且锁定记录本身（前开后闭区间），既保护记录又阻止其他事务向前面间隙插入新记录。
- 特点：开销大、加锁慢，但锁冲突概率最低、并发度最高。
- 两阶段锁协议：行锁在需要时才加上，但要等事务结束才释放。因此事务中需要锁多个行时，应把最可能造成锁冲突、最影响并发度的锁尽量往后放。

**加锁规则**（RR 级别下验证，RC 下去掉间隙锁只剩行锁）：原则 1——加锁的基本单位是 next-key lock（前开后闭区间）；原则 2——查找过程中访问到的对象才会加锁。优化 1——索引上的等值查询，给唯一索引加锁时 next-key lock 退化为行锁；优化 2——索引上的等值查询，向右遍历且最后一个值不满足等值条件时退化为间隙锁。一个 bug——唯一索引上的范围查询会访问到不满足条件的第一个值为止（MySQL 8.0 后已修复）。

**锁的划分（两个角度）**

- 数据库角度：共享锁（S 锁/读锁）资源可被其他用户读取但不能修改；排他锁（X 锁/写锁）只允许持锁事务使用，INSERT/DELETE/UPDATE 自动加。行级：`select ... where id=10 lock in share mode` / `for update`；表级：`lock table t read/write`。
- 程序员角度：乐观锁——认为并发冲突是小概率事件，不依赖数据库锁机制，用版本号或时间戳在程序中实现，适合读多写少，无死锁问题；悲观锁——对数据修改持保守态度，用数据库自身锁机制保证排他性，适合写多场景，但加锁时间长、并发访问性不好。

**InnoDB 使用表锁还是行锁**：绝大部分情况使用行锁。用表锁的情况：表比较大且事务需要更新全部或大部分数据；事务涉及多个表比较复杂，可能引起死锁造成大量回滚。

### 日志 {#mysql-log}

一句话：三大日志各司其职——undo log 保原子性（回滚、MVCC）、redo log 保持久性（崩溃恢复）、binlog 用于备份和主从复制。

| 日志 | 所属层 | 内容 | 用途 |
| --- | --- | --- | --- |
| undo log | InnoDB 引擎层 | 记录更新前的值 | 事务回滚、MVCC |
| redo log | InnoDB 引擎层 | 物理日志，记录数据页的修改 | 掉电等故障恢复（持久性） |
| binlog | Server 层 | 逻辑日志，记录表结构变更与数据修改 | 数据备份、主从复制 |

**undo log**：事务执行插入、修改、删除时记录操作类型、修改前的数据值、数据位置、事务 id 等信息，用于回滚和 MVCC。每条 undo log 有 roll_pointer（把 undo log 串成版本链）和 trx_id（记录修改事务）。快照读时，MySQL 根据事务的 Read View 顺着版本链找到满足可见性的记录。

**redo log**：物理日志，记录「对某表空间中某数据页某偏移量做了什么更新」。事务提交时只需先将 redo log 持久化到磁盘即可保证持久性。

**redo log 与 undo log 的区别**：都是 InnoDB 引擎生成；redo log 记录事务完成后的数据状态（更新后的值），undo log 记录事务开始前的数据状态（更新前的值）；事务提交前崩溃，重启后用 undo log 回滚；提交后崩溃，重启后用 redo log 恢复。

**binlog**：完成更新操作后由 Server 层生成，事务提交时统一写入 binlog 文件；记录所有表结构变更和表数据修改，不记录 SELECT、SHOW 等查询操作。格式有 Statement、Row、Mixed 三种。

**redo log 与 binlog 的区别**：适用对象——binlog 是 Server 层实现所有引擎可用，redo log 是 InnoDB 实现；文件格式——redo log 是物理日志，binlog 是逻辑日志；写入方式——binlog 追加写（写满换新文件，保存全量日志），redo log 循环写（空间固定，保存未刷盘的脏页日志）；用途——binlog 用于备份恢复、主从复制，redo log 用于掉电等故障恢复。

**为什么需要两阶段提交**：事务提交后 redo log 和 binlog 都要持久化到磁盘，但两者是独立逻辑，可能出现半成功状态：只有 redo log 写入成功时，主库恢复出新值但从库（靠 binlog 复制）没有这条更新，主从不一致；只有 binlog 写入成功时则相反。因此两者必须保持一致。两阶段提交把提交拆成 Prepare 和 Commit 两个阶段，由内部 XA 事务协调（binlog 作为协调者，存储引擎是参与者）：

1. prepare 阶段：将内部 XA 事务 ID 写入 redo log，事务状态设为 prepare，并持久化到磁盘。
2. commit 阶段：把 XA 事务 ID 写入 binlog 并持久化到磁盘，然后调用引擎提交接口将 redo log 状态设为 commit（只需 write 到 page cache；只要 binlog 写盘成功，redo log 仍是 prepare 也认为事务执行成功）。

### 执行引擎 {#mysql-engine}

一句话：用 `SHOW ENGINES;` 查看支持的引擎；InnoDB 是默认事务型引擎，MyISAM 只适合读多写少。

- InnoDB：默认事务型存储引擎，支持事务提交与回滚、行级锁、外键约束和 MVCC；MyISAM：表级锁定，不支持事务，支持全文索引，适用于以读操作为主的应用；Memory：数据放内存，处理速度快，但重启或崩溃后数据丢失。

**InnoDB 与 MyISAM 的区别**

| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持，具备 ACID | 不支持 |
| 锁粒度 | 行级锁，并发性能好 | 表级锁，写多时并发差 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持 | 崩溃后恢复可能丢数据 |
| 全文索引 | 支持 | 支持，表现更好 |
| 适用场景 | 需要事务、高并发、高写入 | 读频繁、写少的场景 |

### 常见问题 {#mysql-faq}

一句话：这一节是实战连问，覆盖幻读、事务细节、脏页、表结构与 Count、查询效率等高频追问点。

**幻读连问**

- 什么是幻读：同一事务中前后两次查询同一范围数据，第二次看到了第一次没看到的行。出现场景：RR 隔离级别且是当前读；幻读仅专指新插入的行。危害是破坏行锁语义、破坏数据一致性；根本原因是行锁只能锁定已存在的行，对新插入操作没有限定；避免方式是存储引擎采用间隙锁。
- 间隙锁：锁住行与行之间的间隙，能阻塞新插入操作；引入新问题——降低并发度、可能导致死锁（不同线程可同时给同一间隙加锁，之后互相等待）。间隙锁只在可重复读级别下有效，间隙锁之间不冲突、但会阻塞插入。
- next-key lock：行锁 + 间隙锁的合称，左开右闭区间。补充：非唯一索引的范围查询会访问到不满足条件的第一个值且不执行两个优化；delete 语句加锁方式与查询相同；limit 语句遍历到满足条件的 n 条后不再加 next-key lock。

**事务相关追问**

- `for update` 的使用场景：长事务高并发下防止读到过期数据（如库存刚读到 1，另一进程立刻更新为 0），使事务保持当前读状态。
- MVCC 的实现：每个事务有严格递增的 transaction id；事务启动时找到已提交的最大事务 id 记为 up_limit_id；更新时把旧值和该行之前的 row trx_id 写入 undo log，并在数据页上记录本事务 id；读取时 up_limit_id 大于等于该行 transaction id 则可见，否则沿 undo log 版本链查找。
- RR 与 RC 的差异：快照读下 RR 不更新事务内的 up_limit_id，而 RC 每次更新为最新已提交事务 id，因此 RC 不可重复读；当前读下 RR 用 record lock + gap lock，RC 没有 gap lock。
- 普通索引还是唯一索引：查询性能差距微乎其微（InnoDB 按数据页读写）；更新涉及 change buffer——数据页不在内存时先缓存更新操作，下次访问该页再应用（purge），可持久化，能减少随机读磁盘 IO。唯一索引的更新不能使用 change buffer；写多读少的业务（账单、日志类）收益最大，写入后马上查询的业务反而有副作用。实践上尽可能使用普通索引。redo log 节省随机写 IO，change buffer 节省随机读 IO。
- char 与 varchar：char 定长（char(10) 存 abc 仍占 10 字节）；varchar 变长。compact 行格式下 varchar 记录真正数据 + 所占字节数（变长字段列表按列逆序存放）；变长编码字符集下 CHAR(M) 至少占 M 字节，VARCHAR(M) 无此要求。

**MySQL 抖一下与脏页**

- MySQL 抖一下：SQL 执行效率突然明显变慢。主因是 InnoDB 后台刷脏页（内存页写入磁盘）占用 IO 资源，或查询需要内存时淘汰脏页。应对：合理设置 innodb_io_capacity，关注脏页比例不要经常接近 75%。
- 脏页：内存数据页与磁盘数据页内容不一致；写入磁盘后一致则称干净页。脏页由 WAL 技术产生（把随机写转为顺序写的副作用）。随机写需重新定位磁盘位置很耗时，顺序写在上一位置之后直接写、速度快。

**表结构与表文件**

- 删除一半数据表文件大小不变：delete 只是逻辑删除，把记录或数据页标记为「可复用」，物理空间没有释放。空洞由 delete、页分裂、修改（先删后插）产生。
- 表数据存储位置：由 `innodb_file_per_table` 控制，可在共享表空间或单独的 .ibd 文件，建议单独存储（drop table 可直接删除文件释放空间）。表结构存储：MySQL 8.0 之前存在 .frm 文件，8.0 之后存在系统数据表中。
- 删除数据后让文件变小：重建表消除空洞——`alter table t engine=InnoDB`、`optimize table t`（recreate + analyze）、`truncate table t`（drop + create）。

**Count**：count 是聚合函数，逐行判断参数是否为 NULL，非 NULL 则累加。效率排序：count(字段) < count(主键 id) < count(1) ≈ count(*)——count(字段) 要取值并判空；count(主键 id) 要解析行并拷贝 id 值；count(1) 不取值，server 层每行放数字 1；count(*) 做了优化不取值。MyISAM 把总行数存在磁盘上直接返回；InnoDB 需要一行行从引擎读出累积计数，所以 count(*) 慢。

**查询效率**

- order by 的工作方式：为每个线程分配 sort_buffer 排序内存。内存足够时全字段排序（需要的字段都放入 sort_buffer，排序后直接返回）；sort_buffer_size 太小时借助磁盘临时文件（number_of_tmp_files 判断）；字段太长时改用 rowid 排序（只存主键 id 和排序字段，省空间但多一次回表）。避免排序可建立对应字段索引，进一步可用覆盖索引避免回表。
- 随机显示消息：`order by rand()` 需建临时表并全表扫描（总扫描行数 2×n+3）；sort_buffer 小时用磁盘临时表，高版本用优先队列（堆）排序；更优方案是随机 id 法——生成主键 id 最小值与最大值之间的随机数，取不小于该随机数的主键行（扫描 3 行，但 id 有空洞时概率不均）；严格随机则先取总行数再取随机值（扫描 C+Y+1 行）。
- 逻辑相同性能差异巨大：对索引字段做函数操作会破坏索引值的有序性，优化器放弃树搜索改走全表扫描。包括：条件字段函数操作（`month(t_modified)=7`）、隐式类型转换（字符串与数字比较相当于调用转换函数）、隐式字符编码转换（两表字符集不同时对低字符集一方执行升级转换函数）。
- 只查一行也慢的原因：MySQL 本身被堵住（系统或网络资源不够）；SQL 被堵住（表锁、行锁）；索引使用不当没走索引；数据特点导致一致性读需沿版本链回滚多次才能读到当前事务可见的值。
- 临时表可以重名：每个线程自己可见，线程退出自动删除；binlog_format='row' 时临时表操作不记入 binlog，避免主备不一致。
- group by 原则：无排序要求时加 `order by null`；尽量用上索引（explain 无 Using temporary 和 Using filesort）；数据量不大只用内存临时表（可调大 tmp_table_size）；数据量太大用 SQL_BIG_RESULT 提示优化器直接用排序算法。
- 一张表能存多少条：按 B+ 树估算。一条记录 1KB、页 16KB，叶子节点存 16 条；非叶子节点存关键字（int 4 字节）+ 指针（4 字节），一页可存 16384/8 = 2048 个单位；树高 2 可存 2048×16 = 32768 条；树高 3 可存 2048×2048×16 = 67108864 条（约 6700 万，可见索引高度一般在 3 左右）。
- 联合索引 (A,B,C) 查询 where a, c：不会有效使用索引。B+ 树叶子记录按 a、b、c 排序，跳过 b 后符合 where 条件的记录不一定相邻，无法区间定位，只能逐条找。

### 分库分表 {#mysql-sharding}

一句话：单库太大（IO 与处理能力瓶颈）就分库，单表太大（索引膨胀、查询超时）就分表；垂直拆结构、水平拆数据。

**四种拆分方式**

| 方式 | 拆分对象 | 特点与好处 |
| --- | --- | --- |
| 垂直分表 | 按列（字段） | 不常用字段、text/blob 大字段拆到扩展表；分离热点与非热点字段，避免大字段 IO |
| 垂直分库 | 按业务 | 不同业务的表放到不同数据库服务器；避免竞争同一物理机资源，业务清晰；未解决单表数据量过大 |
| 水平分表 | 按行（数据） | 同一库内按规则把大表拆成多个结构相同的小表；解决单表数据量过大，减少锁表时间 |
| 水平分库 | 按行（数据） | 同一表的数据按规则分到不同服务器的数据库；粒度更大，突破单库 IO/CPU/带宽瓶颈 |

- 垂直分表原则：不常用字段单独一张表；text、blob 等大字段拆到附表；业务经常组合查询的列放一张表。
- 水平切分规则：range（按范围）、hash 取模（按 ID 取模分配）、地理区域、时间范围。
- 时机：单表建议 1 千万以内（推荐百万级）；常规 SQL 和索引优化先行，再结合缓存、异步、NoSQL、MQ；分库分表不是宜早不宜迟，需提前评估 1~2 年业务增长与 QPS、连接数、容量。

**分库分表带来的问题**：跨节点 Join 关联查询困难；跨库操作带来分布式事务；跨节点的排序、翻页、函数计算（排序字段非分片字段时需各分片排序再汇总）；自增 id 导致的全局主键重复；容量规划与二次扩容；中间件技术选型（自研工具、tddl、shardingsphere、mycat 等）。

**解决的问题**：数据库连接数瓶颈（MySQL 默认最大连接数 100，服务允许最大 16384）；单表海量数据的查询性能；单台数据库的并发访问压力；系统磁盘 IO、网络 IO、CPU 瓶颈（可用 `show processlist` 找 CPU 高的 SQL，State 为 Sending data、Copying to tmp table、Sorting result 等可能有性能问题）。

### 排序思路 {#mysql-sort}

一句话：海量数据排序采用外部排序思想，优化方向是生成更长的顺串与更高效的多路归并。

1. 分割段阶段用替换-选择排序，生成大小大于可用内存的顺串，减少 IO。
2. 合并阶段适量增加归并路数以减少 IO 开销。
3. 归并路数增加会导致每个缓冲区选取最小值开销变大，引入败者树（类似堆排）优化内部归并。

### 主从复制 {#mysql-replication}

一句话：主从复制把主节点数据复制到一个或多个从节点，默认异步复制，服务于备份、读写分离与架构扩展。

- 用途：数据实时备份（故障切换）；读写分离（主库写、从库读，主库锁表也不影响读）；架构扩展（多节点分担 IO，提高单机 IO 性能）。
- 原理涉及三个线程：主节点 binary log dump thread（发送 binlog 内容）；从节点 I/O thread（接收更新写入本地 relay log）、SQL thread（读取 relay log 解析执行，保证主从一致）。
- 基本过程：
  1. 从节点 I/O 线程连接主节点，请求指定日志文件、指定位置之后的内容；主节点读取日志返回，同时带上本次返回的 bin-log file 和 bin-log position。
  2. 从节点把日志内容写入本机 relay log，并把 binlog 文件名和位置记到 master-info 文件，方便下次告知主节点更新位置。
  3. 从节点 SQL 线程检测到 relay log 新增内容，解析成主节点上实际执行的操作并执行。
- 复制模式：异步、半同步、全同步、GTID 复制。
- 高可用方案：主从复制 + keepalived/heartbeat 快速切换、基于 Galera 协议、基于 NDB 协议、基于中间件/proxy、基于共享存储、基于主机高可用。

### 架构升级 {#mysql-arch}

一句话：数据库架构沿「单机 → 主从 → 双主 → 分库分表」演进，优化时应先软优化、硬优化，最后才分库分表。

- 单机：请求量大查询慢；单机故障导致业务不可用。
- 主从：主从同步，从库水平扩展满足读需求；但单服务器 TPS、内存、IO 有限。
- 双主：写请求增多后增加主节点写入；多主数据一致性同步更复杂。
- 分库分表：借助自研工具、tddl、shardingsphere、mycat 等。
- 单表千万级、未来还增长的优化思路：先分析实际情况，不要一上来就分库分表。软优化（参数调优、慢 SQL 分析与执行计划、索引结构优化、表结构优化、引入 NoSQL 与架构调整）→ 硬优化（带宽、CPU、硬盘等硬件提升）→ 仍不满足再分库分表（先看只分表是否够用，分表解决单表查询效率但受单库 IO 限制，不够再分库分表一起）。

### 面试一问一答速查 {#mysql-qa}

- **排它锁和共享锁是什么，有什么区别？** 排它锁（X 锁/写锁）只允许持锁事务使用数据，其他事务无法查询或修改，INSERT/DELETE/UPDATE 自动加。共享锁（S 锁/读锁）允许多个事务同时读取但不能修改。共享锁非独占、可多事务同时持有，用于读；排它锁独占、一次只能一个事务持有，用于写。
- **MySQL 的行级锁有哪些？作用是什么？** Record Lock 记录锁：只锁一条记录，分 S/X 锁。Gap Lock 间隙锁：锁一个范围不含记录本身，仅 RR 级别，用于解决幻读，间隙锁之间兼容。Next-Key Lock 临键锁：记录锁 + 间隙锁，锁范围且锁记录，防止范围内插入新行。
- **数据库悲观锁和乐观锁的原理和使用场景？** 乐观锁认为并发冲突是小概率事件，不用数据库锁机制，程序上用版本号或时间戳实现，适合读多写少，无死锁问题。悲观锁持保守态度，用数据库自身锁机制保证排他性，适合写多场景，但加锁时间长、并发性差。
- **执行一条 select 语句，发生了什么？** 连接器建立连接并验证权限（wait_timeout 默认 8 小时）→ 查询缓存（8.0 已移除）→ 解析器词法/语法分析构建语法树 → 执行 SQL：预处理、优化（基于成本选索引和连接顺序）、执行（判断权限后从存储引擎读记录返回）。
- **事务的四大特性有哪些？** 原子性：全部成功或全部回滚（undo log）；一致性：从一个一致状态到另一个一致状态（由其他三者保证）；隔离性：并发事务互不干扰（MVCC 或锁）；持久性：提交后永久保存（redo log）。
- **数据库的事务隔离级别有哪些？** 读未提交（可能脏读、不可重复读、幻读）；读已提交（解决脏读）；可重复读（InnoDB 默认，解决不可重复读，仍可能幻读）；串行化（加读写锁，三者都解决但并发性能最低）。
- **为什么 MySQL 索引使用 B+ 树？** 非叶子节点只存索引不存数据，树更矮胖、磁盘 IO 更少；大量冗余节点使插入删除效率更高；叶子节点用链表相连，范围查询效率高于 B 树的树遍历。
- **你对关系范式有哪些了解？** 范式用于减少数据冗余、避免插入/更新/删除异常。1NF 确保每列原子不可再分；2NF 在 1NF 基础上要求非主键列完全依赖主键；3NF 在 2NF 基础上要求非主键列直接依赖主键（不能传递依赖）。
- **可以对数据库表做哪些优化？** 大表合理拆分；在经常查询的列建索引（注意过多索引影响写性能）；避免 select * 只取需要的列；选合适的数据类型（小整型替代 INT、VARCHAR 只分配需要的长度、整数/枚举替代字符串、TIMESTAMP 替代 DATETIME、少用 NULL）。
- **了解 MongoDB 吗，它和 MySQL 有哪些区别？** MySQL 是关系型数据库，表结构固定，SQL 查询，支持事务与复杂查询，扩展靠主从复制和垂直分区；MongoDB 是文档型数据库，BSON 存储、无模式、字段可动态添加，用自家查询方式，WiredTiger 引擎，支持分片横向扩展。结构化数据与事务选 MySQL，非结构化/半结构化与横向扩展选 MongoDB。
- **什么是慢查询？原因是什么？可以怎么优化？** 执行时间超过 long_query_time（默认 10 秒）的查询。原因：语句复杂（多表连接子查询）、数据量大、缺少索引全表扫描、表设计不合理、并发冲突、硬件资源不足。优化：先定位慢 SQL；选区分度高的字段；用 explain 分析索引使用；order by limit 让排序的表优先查；按建索引原则补索引；结合业务使用场景改写。

## 数据库：Redis {#redis}

### Redis 基础 {#redis-basic}

一句话：Redis 是基于内存的键值数据库，核心卖点是高性能与高并发，命令执行是单线程的。

**Redis 是什么，有哪些特点**：开源的基于内存的数据库，读写速度非常快，常用作缓存、消息队列、分布式锁和键值存储。支持字符串、哈希表、列表、集合、有序集合等多种数据结构，还支持事务、持久化、Lua 脚本、多种集群方案（主从复制、哨兵、切片集群）、发布/订阅、内存淘汰机制、过期删除机制。特点：基于内存、可持久化、多数据结构、原子性操作、分布式。

**为什么要用 Redis 而不仅仅依赖 MySQL**：Redis 具备高性能（读写快，把频繁访问的数据放缓存，减轻 MySQL 压力）与高并发（通过缓存和原子性操作降低数据库并发压力）两种特性；且数据结构丰富、处理特定数据更灵活。实际系统中常同时使用 MySQL 与 Redis。

**Redis 是单线程吗**：单线程指的是网络请求模块（命令执行）使用单线程，程序本身还有后台线程：2.6 版本启动 2 个后台线程处理关闭文件、AOF 刷盘；4.0 之后新增 lazyfree 线程异步释放内存（这些任务耗时，放主线程会阻塞）。Redis 6.0 采用多个 I/O 线程处理网络请求以提高网络 I/O 并行度，但命令执行仍是单线程。

**Redis 单线程为什么还这么快**：基于内存存储（内存远快于磁盘）；单线程避免上下文切换、资源竞争和锁开销（非阻塞单线程）；专门设计的高效数据结构（STRING、LIST、HASH 等）；I/O 多路复用同时监听多个 Socket，一个线程处理多个 IO 流。

### 数据类型与底层结构 {#redis-data-type}

一句话：五种基础类型各有典型场景，底层结构随版本演进（压缩列表被 listpack 取代，List 用 quicklist）。

| 类型 | 底层结构 | 应用场景 |
| --- | --- | --- |
| String | SDS | 缓存对象 JSON、计数（单线程命令原子）、分布式锁（SETNX）、共享 Session |
| List | 双向链表或压缩列表（3.2 后 quicklist，7.0 后 listpack） | 消息队列（lpush + brpop 左进右出）、按序显示的朋友圈点赞 |
| Hash | 压缩列表或哈希表（7.0 后 listpack） | 缓存对象（频繁变化的属性）、购物车（用户 id 为 key、商品 id 为 field、数量为 value） |
| Set | 哈希表或整数集合 | 点赞、共同关注（交集运算）、抽奖（去重防重复中奖） |
| Zset | 压缩列表或跳表 | 排行榜（成绩、积分、销量）、最新列表、需要分页的排序场景 |

- 编码阈值：List/Hash 元素个数小于 512 且每个值小于 64 字节用压缩列表；Set 元素都是整数且个数小于 512 用整数集合；否则用对应的主结构。
- 后续版本新增四种类型：BitMap（2.2，二值统计，签到、登录态判断）；HyperLogLog（2.8，基数统计，标准误算率 0.81%，内存固定且很小，百万级网页 UV）；GEO（3.2，地理位置，底层 Zset + GeoHash 编码经纬度为分数）；Stream（5.0，专为消息队列设计，自动生成全局唯一消息 ID、支持消费组，弥补 List 队列不能持久化、无法读历史消息的缺陷）。

**底层数据结构**

- SDS（简单动态字符串）：可存储二进制数据（含空字符）；头部保存长度信息，O(1) 获取长度；支持动态扩容。
- 双端链表：两端快速插入删除，获取表头/表尾/数量 O(1)；缺陷是节点内存不连续无法利用 CPU 缓存，且节点结构头内存开销大。
- 压缩列表：连续内存块的紧凑顺序结构，节省内存；缺陷是元素增多或变大时重新分配内存，可能引发连锁更新（只用于节点数少的场景）。
- 哈希表：O(1) 查询键值对，拉链法解决哈希冲突；整数集合：紧凑二进制表示存储整数，用于存储集合中的整数元素。
- 跳表：链表基础上改进的多层有序链表，数据量大时查找复杂度 O(logN)，用于有序集合。查找从头节点最高层开始逐层遍历：当前节点权重小于目标则访问下一个节点；权重相等且 SDS 数据较小时也向后走；否则沿当前节点 level 数组的下一层指针继续。
- quicklist：双向链表 + 压缩列表组合（链表节点是压缩列表），通过控制每个节点中压缩列表的大小或元素个数规避连锁更新。
- listpack：只记录当前节点长度、不记录前一节点长度，新增元素不影响其他节点的长度字段，从根本上避免连锁更新。

### 持久化 {#redis-persistence}

一句话：三种持久化方式——AOF 记命令、RDB 记快照、混合持久化取两者之长。

**AOF 日志**：每执行一条写操作命令，就把该命令追加写入一个文件；重启时读取日志重建数据。AOF 是写后日志（先执行命令写内存，再记录日志），好处是不会记录错误命令、不阻塞当前写操作（Redis 是内存 + 写后日志，MySQL 是磁盘数据 + 写前日志）。

**三种写回策略**

| 策略 | 做法 | 特点 |
| --- | --- | --- |
| Always | 每次写命令执行后同步写回硬盘 | 可靠性最高，性能最低 |
| Everysec | 先写内核缓冲区，每隔一秒写回硬盘 | 折中，最多丢一秒数据 |
| No | 写入内核缓冲区，由操作系统决定写回时机 | 性能最高，可靠性最低 |

**AOF 重写机制**：命令越多 AOF 文件越大，重写会扫描所有键值对，为每个键值对生成一条写操作命令写入新 AOF 文件，完成后替换旧文件。由后台子进程完成，不阻塞主进程（一处拷贝、两处日志）。触发时机：bgrewriteaof 命令执行；主从复制完成 RDB 文件解析和加载；AOF 重写被设置为待调度执行；AOF 启用且文件大小比例与绝对值均超出阈值。前提是当前没有正在执行的 RDB 子进程和 AOF 重写子进程。

**RDB 快照**：记录某一瞬间的内存数据（二进制实际数据），每次把所有数据记录到磁盘。频率太高影响性能，太低故障时丢数据多，通常至少 5 分钟保存一次。两个命令：`save` 在主线程执行（写文件太久会阻塞主线程）；`bgsave` 创建子进程生成 RDB 文件，避免阻塞。

**混合持久化**：Redis 4.0 新增，集成 AOF 与 RDB 的优点。工作在 AOF 重写过程：重写子进程先将与主线程共享的内存数据以 RDB 方式写入 AOF 文件，主线程期间的增量命令记录在重写缓冲区后以 AOF 方式追加。文件前半部分是 RDB 格式全量数据（加载快），后半部分是 AOF 格式增量数据（丢失少）。缺点：AOF 文件可读性变差、兼容性差（4.0 之前版本不支持）。

### 集群 {#redis-cluster}

一句话：高可用三板斧——主从复制做数据副本、哨兵做自动故障转移、切片集群做水平扩展。

**主从复制**：读写分离，读操作主从库都可接收，写操作先在主库执行再同步给从库。

- 全量复制（第一次同步）三阶段：从库与主库建立连接并告知将同步；主库用 FULLRESYNC 响应带上主库 runID 和复制进度 offset，并生成 RDB 发送给从库；主库再把第二阶段期间新收到的写命令发送给从库。
- 增量复制（从库断连重连后）：主库把断连期间写命令写入 repl_backlog_buffer；从库重连后发送 psync 命令并带上自己的 slave_repl_offset，主库比较两者的 offset 差距：差距超出 repl_backlog_buffer（已被覆盖）则无法增量复制、被迫全量复制；否则把差距部分发给从库执行。主从库间共有三种同步模式：全量复制、基于长连接的命令传播（常规同步阶段）、增量复制。
- 全量同步使用 RDB 而不是 AOF 的原因：RDB 是压缩的二进制文件、体积小，AOF 记录每条写命令文件大且含大量冗余操作；AOF 需要选择刷盘策略，选择不当严重影响性能，而 RDB 只在定时备份和主从全量同步时触发。
- 主从同步过程（细化）：从库发送 SYNC 命令协商连接（记录主库 runID 与复制进度）→ 主库执行 BGSAVE 生成 RDB 快照并发送，同时发送缓冲区写命令 → 从库载入 RDB 并执行缓冲区命令 → 转入增量复制，主库实时传播写命令 → 双方维持心跳检测存活。
- 如何避免主从数据不一致：主从都启用持久化和复制配置（从库重启可完整恢复）；保证网络稳定（如主从同机房）；监控复制延迟、连接状态并设置报警。

**哨兵模式**：解决主从服务器故障宕机需要手动恢复的问题。功能：监控（主从是否正常）、通知（出问题时通知相关人员）、故障迁移（自动主从切换）、统一的配置管理（获取主从地址）。

哨兵工作原理：

1. 监控：定期向 Redis 服务器发 PING 检测健康状态，连续多次未收到响应则认为主观下线。
2. 故障检测与选主：主节点不可用时，从可用从服务器中选择候选（通常复制偏移量 replication offset 最大），各哨兵投票（考量偏移量、连接质量、优先级），获得多数哨兵同意即选出新主；随后通知其他从节点改为复制新主节点。
3. 自动恢复与通知：原主节点重新可用后被降级为从节点；哨兵更新集群配置并把新主地址通知客户端。

**切片集群**：数据量大到一台服务器无法承载时使用，将数据分布到不同服务器，降低对单主节点的依赖、提高读写性能。工作原理：

1. 数据分片：整个数据集划分为 16384 个槽（slot），每个节点负责一部分槽；节点间通过 gossip 协议（PING、PONG 消息）共享节点信息与集群状态。
2. 数据分布与路由：新键按 CRC16 哈希值确定所属槽，存到负责该槽的节点，保证均匀分布；客户端同样计算哈希定位槽，直接请求负责节点，无需中间代理。
3. 故障检测与复制：节点不可用时其他节点发起故障检测，重新分配槽并选举新主；每个槽有一个主节点和若干从节点，主节点写入后异步复制到从节点。

**集群脑裂**：主节点网络突发问题与所有从节点失联，但与客户端的网络正常，客户端继续写入（数据缓存在主节点缓冲区）；哨兵发现主节点失联后从从节点中选出新主，集群出现两个主节点。网络恢复后旧主被降级为从节点，向新主请求第一次同步（全量同步）会清空本地数据，客户端期间写入的数据丢失。应对：当主节点发现从节点下线或通信超时的总数量小于阈值时，禁止主节点写入并直接返回错误给客户端；设置主节点连接的从节点至少 N 个、数据复制 ACK 延迟不超过 T 秒，否则主节点不再接收客户端写请求。这样旧主被降级清空数据也不会丢失新数据。

### 过期删除策略 {#redis-expire}

一句话：过期删除解决「过期键何时被删」，Redis 采用惰性删除 + 定期删除的组合。

三种策略对比：定时删除（设置过期时间时创建定时事件，到期自动删除；过期 key 尽快删除，但占用 CPU 时间）；惰性删除（不主动删，每次访问 key 时检测过期则删；CPU 友好，但过期 key 可能长期不删浪费内存）；定期删除（每隔一段时间随机取出一定数量 key 检查并删除过期的；折中方案，但难以确定执行时长和频率）。

Redis 的实现：

1. 惰性删除：依据 expireIfNeeded 函数，每次返回或修改 key 之前检查是否过期，过期则删除（lazyfree_lazy_expire 参数决定同步还是异步删除）并返回 null；未过期返回正常值。
2. 定期删除：默认每隔 10 秒（配置键 hz: 10）随机抽查 20 个 key，检查并删除已过期的；如果本轮过期 key 数量超过 5 个（占比大于 25%），继续重复抽查；小于 25% 则停止，等待下一轮。

### 内存淘汰 {#redis-eviction}

一句话：内存达到 maxmemory 上限后按淘汰策略删键，8 种策略围绕「是否淘汰」与「对哪些键用何种算法」两个维度。

- 不淘汰：NoEviction（默认），内存不足以执行写操作时直接返回错误。
- 在设置了过期时间的键中淘汰：VolatileTTL（优先淘汰更早过期的）、VolatileLRU、VolatileRandom、VolatileLFU（其余键相当于 NoEviction）。
- 在所有键中淘汰：AllKeysLRU（淘汰最久未使用）、AllKeysRandom（随机淘汰）、AllKeysLFU（淘汰使用频率最低）。用 `config get maxmemory-policy` 可查看当前策略。

**LRU 与 LFU 的区别**：LRU 假设最近被访问的数据未来更可能再次访问，淘汰最近最少使用的；Redis 实现的是近似 LRU——对象结构体记录最后访问时间，淘汰时随机采样 5 个（可配置）淘汰其中最久未使用的。LFU 假设使用频率低的对象未来仍较少被访问，维护使用计数，淘汰计数最低的。一句话：LRU 看最近访问情况，LFU 看使用频率。

### 缓存问题 {#redis-cache}

一句话：雪崩是大面积失效、击穿是热点失效、穿透是数据根本不存在；一致性靠 Cache Aside 模式保障。

**缓存雪崩**：某个时间点缓存中大量数据同时失效（过期时间设置相近），或 Redis 故障宕机，请求全部打到数据库。

- 大量数据同时过期的应对：均匀设置过期时间（过期时间加随机数）；互斥锁（发现数据不在 Redis 就加锁，保证同一时间只有一个请求构建缓存）；后台更新缓存（缓存「永久有效」，由后台线程定时更新）。
- Redis 故障宕机的应对：服务熔断（暂停对缓存服务的访问，直接返回错误）或请求限流（只放少量请求到数据库，其余入口拒绝）；构建 Redis 缓存高可靠集群（主从节点，主故障从切换，继续提供缓存服务）。

**缓存击穿**：某个热点数据过期时，大量并发请求查询该缓存不存在的数据，直接访问数据库。是缓存雪崩的子集，可用互斥锁或后台更新缓存应对。

**缓存穿透**：要访问的数据既不在缓存也不在数据库，无法构建缓存，后续请求都打到数据库。原因：业务误操作（缓存和数据库数据都被误删）；恶意攻击（构造不存在的 key 大量访问）。解决：对非法请求做限制；在缓存中设置空值或默认值；使用布隆过滤器快速判断数据是否存在，避免查库判断。

**如何保证数据库和缓存的一致性**：Cache Aside 策略。

- 读写策略：读——命中缓存直接返回，未命中则从数据库读取，写入缓存并返回；写——更新数据库中的数据，再删除缓存中的数据。
- 「先更新数据库 + 再删除缓存」可保证一致性，但每次更新都删缓存影响命中率。对命中率要求高可用「更新数据库 + 更新缓存」，但两个更新并发执行会出现数据不一致，可用分布式锁（同一时间只允许一个请求更新缓存）或给缓存加较短的过期时间兜底。
- 保证删除缓存一定成功：重试机制——引入消息队列，删除失败后从消息队列重新读取数据再次删除，超过一定次数仍失败则向业务层报错，成功后从队列移除避免重复操作；订阅 binlog——删除服务伪装成 MySQL 从节点发送 dump 请求，主节点推送 binlog，解析后转换为结构化数据再执行缓存删除。

### 面试一问一答速查 {#redis-qa}

- **什么是 Redis，具有哪些特点？** 基于内存的数据库，读写非常快，常用作缓存、消息队列、分布式锁、键值存储。支持字符串、哈希、列表、集合、有序集合等多种数据结构，还提供事务、持久化、Lua 脚本、发布/订阅、多种集群方案，并具备分布式特性。
- **Redis 为什么快？** 基于内存操作减少 IO；专门设计的高效数据结构；单线程省去上下文切换和锁竞争，避免死锁；I/O 多路复用同时监听多个 Socket 并分派事件处理器。
- **为什么 Redis 是单线程？** 单线程指网络请求（命令执行）模块；它减少了上下文切换开销和资源竞争的锁问题。官方解释：CPU 不是 Redis 的瓶颈，瓶颈最可能是机器内存或网络带宽，单线程容易实现且够用。
- **Redis 为什么又要引入多线程？** 瓶颈在网络 I/O 模块的 CPU 耗时，Redis 6.0 的多线程用于处理网络 I/O，充分利用 CPU、减少网络 I/O 阻塞损耗，性能提升至少一倍；命令执行仍是单线程。
- **Redis 有哪些数据类型？** 五种基础类型：String（字符串，最基本）、Hash（字段-值映射，存对象）、List（有序字符串列表）、Set（唯一无序元素）、Zset（元素关联分数可排序）。后续新增：BitMap（位运算、二值统计）、HyperLogLog（基数估算）、GEO（地理位置）、Stream（消息队列）。
- **Redis 数据类型的应用场景？** String：缓存对象、计数、分布式锁、共享 Session；List：消息队列（需自行实现全局唯一 ID、不能消费组消费）；Hash：缓存对象、购物车；Set：聚合计算（并交差集），点赞、共同关注、抽奖；Zset：排序场景、排行榜。BitMap：签到、登录态；HyperLogLog：海量 UV 统计；GEO：滴滴叫车类位置场景；Stream：消息队列（自动全局唯一 ID + 消费组）。
- **Redis 底层使用了什么数据结构？** SDS（二进制安全、O(1) 取长度、动态扩容）；双端链表（两端 O(1) 插入删除）；压缩列表（连续内存紧凑，但可能连锁更新）；哈希表（O(1) 查询、拉链法解决冲突）；整数集合（紧凑存储整数）；跳表（多层有序链表，O(logN)，实现 Zset）；quicklist（链表 + 压缩列表组合）；listpack（只记录当前节点长度，避免连锁更新）。
- **Redis 与 MySQL 的区别是什么？** Redis 基于键值对、多种数据结构，MySQL 是关系型用表组织数据；Redis 数据在内存（持久化写盘），MySQL 数据在磁盘；Redis 用自己的命令集，MySQL 用 SQL；Redis 追求高性能低延迟适合读多写少，MySQL 适合复杂查询、事务处理和大规模数据集。实践中常配合使用。
- **Redis 与 Memcached 有什么区别？** Redis 支持更丰富的数据结构，Memcached 只做简单键值存储；Redis 支持持久化，Memcached 重启丢数据；Redis 采用单线程模型通常比多线程的 Memcached 更快。需要丰富结构与持久性、高可用选 Redis，简单键值缓存选 Memcached。
- **Redis 为什么不使用红黑树，而使用跳表？** 跳表实现更简单、易理解易调试；跳表对范围查询支持好，天然契合有序集合按范围查找的特性；跳表在插入删除操作上性能表现较好，尤其适合有序集合场景。
- **Redis 如何实现分布式锁？** 用 SETNX：key 不存在才插入成功即加锁成功；加锁时设置 unique_value 标识客户端，解锁时先判断锁的 unique_value 是否为本客户端再删除 lock_key；并设置过期时间（EX/PX 参数）防止客户端异常导致锁无法释放，如 `SET lock_key unique_value NX PX 10000`。
- **Redis 持久化机制有哪些？** AOF 日志：每执行一条写命令就以追加方式写入文件；RDB 快照：将某一时刻的内存数据以二进制方式写入磁盘；混合持久化：Redis 4.0 新增，集成 AOF 与 RDB 的优点。
- **AOF 的三种写回策略？** Always 同步写回（可靠性最高、性能最低）；Everysec 每秒写回（先入内核缓冲区，每秒刷盘，折中）；No 由操作系统控制写回时机（性能最高、可靠性最低）。
- **什么是 Redis 事务？** 一组命令的有序执行序列，执行期间不被其他客户端命令打断，用 MULTI 和 EXEC 实现。MULTI 开启事务，之后的命令入队不立即执行，EXEC 按顺序一起执行；EXEC 前出错则整个事务取消并回滚。可用 WATCH 监视键，事务执行期间被其他客户端修改则事务取消，保证原子性。
- **缓存中的热点数据和冷数据是什么？** 热数据是访问次数较多的数据，冷数据是访问很少或从不访问的数据。只有热数据，缓存才有价值。
- **Redis 集群模式有哪些？** 主从复制：一个主节点其余从节点，主节点写操作传播到所有从节点；哨兵：监控实例状态，发现主节点故障并自动故障转移；切片集群：数据分布到不同服务器，降低对单主节点的依赖。
- **Redis 的哨兵是用来做什么的？** 监控 Redis 主从服务器状态（连接状态、能否执行命令、持久性问题等）；主服务器不可用时通过选举机制选一个从服务器升级为新主，并通知其他从服务器切换到新主；此外还提供通知与统一配置管理。
- **主从模式的同步过程？** 连接协商（从库发 psync，主库响应 runID 与复制进度 offset）→ 主库 BGSAVE 生成 RDB 快照发送给从库，同时发送缓冲区写命令 → 从库载入 RDB 并执行缓冲区命令，追平主库状态 → 转入增量复制，主库实时传播写命令 → 双方维持心跳保持一致。
- **哨兵的工作原理？** 定期 PING 检测节点存活，连续未响应判为主观下线；主节点下线后哨兵间协调选举新主（候选通常选复制偏移量最大的从节点，投票考量偏移量、连接质量、优先级，需多数哨兵同意）；选出后通知从节点复制新主、更新集群配置并告知客户端；原主恢复后被降级为从节点。
- **缓存雪崩、击穿、穿透和解决办法？** 雪崩：大量缓存同时失效或 Redis 宕机，请求直连数据库；办法：过期时间加随机值、互斥锁、后台定时更新缓存，宕机场景用熔断限流和高可用集群。击穿：热点数据过期后大量并发查库；办法：互斥锁（分布式锁）、先查缓存再查库并回写。穿透：查询的数据缓存和数据库都不存在，恶意构造 key；办法：布隆过滤器过滤、参数合法性校验、缓存空值。
- **如何保证数据库和缓存的一致性？** Cache Aside：读时先查缓存、未命中查库回填；写时先更新数据库再删除（失效）缓存，出现不一致的概率极低。删除失败可用消息队列重试或订阅 binlog 删缓存。其他模式：Read/Write Through 由缓存服务代理数据库读写，对调用方透明；Write Behind 只更新缓存、异步批量刷库，IO 快但非强一致且可能丢数据。
- **Redis 过期删除策略有哪些？** 定时删除（到期自动删，占 CPU）、惰性删除（访问时检测，省 CPU 但占内存）、定期删除（定期随机抽查删除，折中）。Redis 采用惰性删除 + 定期删除组合，在 CPU 时间和内存占用间取平衡。
- **在应用中是怎么使用 Redis 的？** 作为缓存层存储频繁访问的数据提高访问速度；用作消息队列（发布/订阅模式传递消息）；存储会话数据、计数器等。

## 设计模式 {#dp}

> 延伸阅读：卡码网设计模式精讲。面试重点：六大常用模式（单例、工厂、观察者、代理、策略、装饰）的原理、实现与场景，23 种模式分类速记，七大设计原则，以及手写单例等高频题。

### 单例模式 {#dp-singleton}

核心结论：确保一个类只有一个实例并提供全局访问点，避免全局使用的类被频繁创建与销毁、浪费系统资源。

关键概念（三要素）：

1. 私有构造函数：防止外部代码直接实例化；
2. 私有静态变量：保存该类的唯一实例；
3. 公有静态方法：对外提供获取实例的入口，实例不存在时在方法内部创建并返回——构造不让外部用、类只建一个实例、外部只能调方法获取，保证全局唯一。

6 种实现对比：

| 实现方式 | 线程安全 | 延迟加载 | 主要优点 | 主要缺点 |
| --- | --- | --- | --- | --- |
| 懒汉式（线程不安全） | 否 | 是 | 需要时才创建，避免资源浪费 | 多线程同时通过判空，会实例化多个对象 |
| 饿汉式 | 是 | 否 | 类加载时就创建，避免线程安全问题 | 不管是否使用都实例化，可能浪费资源 |
| 懒汉式（方法加锁） | 是 | 是 | 延迟加载且线程安全 | 实例化后每次仍要抢锁，性能低 |
| 双重检查锁 | 是 | 是 | 延迟加载、线程安全、性能较好 | volatile 对性能略有影响 |
| 静态内部类 | 是 | 是 | 延迟加载、线程安全、性能高 | — |
| 枚举 | 是 | 否 | 写法简单，天然防止反射和反序列化 | — |

双重检查锁实现（最常考）：

```java
public class Singleton {
    private volatile static Singleton uniqueInstance;
    private Singleton() {}
    public static Singleton getUniqueInstance() {
        if (uniqueInstance == null) {              // 第一次检查，避免无谓加锁
            synchronized (Singleton.class) {
                if (uniqueInstance == null) {      // 第二次检查，防止重复创建
                    uniqueInstance = new Singleton();
                }
            }
        }
        return uniqueInstance;
    }
}
```

为什么必须用 volatile：`uniqueInstance = new Singleton()` 分三步执行——分配内存空间、初始化对象、将变量指向内存地址。JVM 指令重排可能将顺序变为 1-3-2，单线程下没有问题，但多线程下线程 B 可能在线程 A 只执行了 1、3 时调用 `getUniqueInstance()`，拿到「不为空但尚未初始化」的实例。volatile 禁止指令重排，保证多线程环境下的安全。

静态内部类原理：外部类加载时静态内部类并不会加载进内存；调用 `getInstance()` 触发 `SingletonHolder.INSTANCE` 时，内部类才被加载并初始化实例，且 JVM 保证实例只被创建一次，兼得延迟加载与线程安全。

防止反序列化破坏单例：序列化是把 Java 对象转换为字节序列的过程，反序列化是通过字节序列在内存中新建对象的过程。将单例对象写到磁盘再读回来会得到新实例，破坏单例。枚举类天然防止反序列化；其他实现可重写 `readResolve()` 方法返回已有实例。

应用场景：资源共享（多模块共享同一资源）、控制资源访问（数据库连接池、线程池）、配置管理器（全局共享配置）、日志记录器（全局日志对象）、缓存（保证实例唯一，避免数据不一致和内存浪费）。典型例子：网站计数器、应用程序日志、Web 项目配置对象、数据库连接池、多线程池。总结：频繁实例化又销毁的对象、实例化耗时耗资源的常用对象（如连接池）、需要控制资源并方便资源间通信的场景（如线程池）。

### 工厂模式 {#dp-factory}

核心结论：工厂模式是常用的创建型模式，封装和管理对象的创建，不向客户端暴露创建逻辑，本质是对获取对象过程的抽象；细分为简单工厂、工厂方法、抽象工厂三类（GoF 将简单工厂视为工厂方法的特例）。

总体优点：解耦（创建与使用分离，客户端只依赖工厂接口和抽象产品接口）、复用（复杂创建过程多处复用）、易于扩展（新增产品只需扩展具体产品与工厂，符合开闭原则）、更符合单一职责原则。三种工厂对比如下：

| 类型 | 做法 | 优点 | 缺点 | 实际应用 |
| --- | --- | --- | --- | --- |
| 简单工厂 | 一个工厂类按传入参数创建多种产品（又称静态工厂方法模式，并非标准设计模式） | 实现创建与使用分离 | 工厂职责过重，新增产品要改工厂分支，违反开闭原则 | JDK 的 DateFormat、Calendar |
| 工厂方法 | 工厂抽象为接口，具体创建交给实现该接口的子工厂类 | 用多态解决分支问题，更符合开闭原则 | 新增产品要同时新增产品类和对应子工厂，类数量膨胀 | JDK 中 Collection 的 iterator()：LinkedList 生产 ListItr、ArrayList 生产 Itr |
| 抽象工厂 | 将相关产品组成「产品族」，由同一工厂统一生产 | 新增产品族方便，符合开闭原则 | 新增产品等级结构需对工厂结构大改 | Spring 的 BeanFactory |

（原 PDF 此处为三种工厂的 UML 图，要点即上表所述的工厂—产品层级关系）

应用场景：类不知道它所需要的类时；希望通过子类来指定创建对象时；将创建对象的职责委托给多个帮助子类中的某一个并局部化代理信息时。举例：按数据库类型（MySQL、Oracle 等）创建连接对象、按配置选择日志记录器、GUI 中创建不同风格的界面元素、按需选择加密算法（对称/非对称）、按文件类型选择解析器（XML/JSON）、创建 TCP/UDP 连接对象。

### 观察者模式 {#dp-observer}

核心结论：行为型模式，定义对象间一对多的依赖关系，让多个观察者同时监听某一主题对象，主题状态变化时通知所有观察者自动更新。

主要构成（四个角色）：

- Subject（主题）：被观察对象，包含一组观察者，提供添加、删除和通知观察者的方法；
- Observer（观察者）：声明更新接口，状态改变时被通知并更新；
- ConcreteSubject（具体主题）：维护状态，状态改变时通知观察者；
- ConcreteObserver（具体观察者）：实现更新方法，完成收到通知后的处理。

生活案例：公众号是被观察者，关注它的多个微信用户是观察者，公众号更新时通知所有订阅用户。

实现步骤：

1. 定义主题接口（注册、移除、通知观察者）；
2. 定义观察者接口（更新方法）；
3. 创建具体主题类，维护一组观察者并在状态改变时通知；
4. 创建具体观察者类，实现更新方法；
5. 客户端创建主题与观察者对象、注册观察者，然后改变主题状态触发通知。

优缺点：优点是解除耦合，耦合双方都依赖抽象，各自的变化互不影响；缺点是调试复杂，且 Java 中消息通知一般顺序执行，一个观察者卡顿会影响整体效率，此时一般采用异步实现。

使用场景：事件处理（GUI 按钮点击、鼠标移动）、发布-订阅模型（消息队列、事件总线）、MVC 架构中模型与视图的通信、异步编程中任务完成事件的通知。

### 代理模式 {#dp-proxy}

核心结论：结构型模式，在访问某个对象时引入代理对象，通过代理控制对原始对象的访问，可用于懒加载、控制访问、监控对象等场景。

主要角色：

1. 抽象主题（Subject）：定义代理对象和真实对象的共同接口，使代理能够替代真实对象；
2. 真实主题（RealSubject）：实际执行业务逻辑的被代理对象；
3. 代理（Proxy）：持有指向真实主题的引用，提供与真实主题相同的接口，控制对其的访问，并按需负责创建或删除真实主题实例。

（原 PDF 此处为代理模式结构图：客户端依赖 Subject 接口，Proxy 与 RealSubject 均实现该接口，Proxy 内部引用 RealSubject）

四类典型应用：

1. 远程代理：为存在于不同地址空间的对象提供局部代表，隐藏对象在远端的事实；
2. 虚拟代理：根据需要创建开销很大的对象。例如打开很大的 HTML 网页时先看到全部文字，图片一张张下载，未打开的图片框就是用虚拟代理替代真实图片（代理存储了真实图片的路径和尺寸）；
3. 安全代理：控制真实对象访问时的权限，用于对象应有不同访问权限的场景；
4. 智能指引：调用真实对象时代理附加一些内务处理，如计算引用次数（无引用时自动释放）、第一次引用持久对象时将它装入内存、访问前检查是否已锁定以确保其他对象不能改变它。

### 策略模式 {#dp-strategy}

核心结论：行为型模式，定义一系列算法并各自封装、可以互相替换，使算法独立于使用它的客户端而变化；相比大量 if-else 可降低复杂度、更易维护。

主要构成与实现思路：

- 策略接口（Strategy）：定义算法的抽象；
- 具体策略类（ConcreteStrategy）：实现策略接口，封装具体算法；
- 环境类（Context）：持有策略接口引用并提供设置策略的方法，构造或设置时通过多态传入不同具体策略，调用不同策略的方法；
- 客户端创建环境类对象，注入具体策略后调用方法执行算法。

优缺点：优点是避免多重条件转移语句，算法或行为逻辑不再混在一起，易维护；缺点是可能需要定义大量策略类，且客户端必须知道所有策略并自行决定使用哪一个（只适用于客户端知道全部算法或行为的场景）。

示例（商场销售系统按促销策略计算最终价格）：

```java
// 策略接口
public interface PricingStrategy {
    double calculatePrice(double price);
}

// 具体策略：打九折（类似可实现无折扣、满减等）
public class DiscountStrategy implements PricingStrategy {
    public double calculatePrice(double price) { return price * 0.9; }
}

// 环境类：运行时注入不同策略
public class ShoppingCart {
    private PricingStrategy strategy;
    public void setStrategy(PricingStrategy s) { this.strategy = s; }
    public double checkout(double total) { return strategy.calculatePrice(total); }
}
```

### 装饰模式 {#dp-decorator}

核心结论：结构型模式，在不改变原始类接口的情况下动态地添加功能或责任，通过装饰类包裹原始类实例来扩展功能，比生成子类更灵活。

主要角色：

1. 组件接口（Component）：定义具体组件和装饰器共同的接口，确保它们可以互相替换；
2. 具体组件（ConcreteComponent）：实现组件接口，是被装饰的对象；
3. 装饰器（Decorator）：持有组件对象的引用并实现组件接口，通常是抽象类，具体装饰逻辑交给子类；
4. 具体装饰器（ConcreteDecorator）：继承装饰器，实现具体装饰逻辑，并调用父类方法保持接口一致。

（原 PDF 此处为装饰模式 UML 结构图，要点即上述角色关系：装饰器与具体组件实现同一接口，装饰器内部包裹组件并可层层嵌套）

使用时机：把每个要装饰的功能放在单独的类中，让这个类包装它要装饰的对象。当需要执行特殊行为时，客户代码可以在运行时根据需要有选择地、按顺序地使用装饰功能包装对象。

### 23 种设计模式总览 {#dp-overview}

核心结论：GoF 的 23 种设计模式按目的分为创建型（5 种）、结构型（7 种）、行为型（11 种）三大类。

创建型模式（5 种）：

| 模式 | 一句话定义 |
| --- | --- |
| 工厂方法 | 定义一个创建对象的接口，但由子类决定需要实例化哪一个类，使子类实例化过程推迟 |
| 抽象工厂 | 提供一个接口，可创建一系列相关或相互依赖的对象，而无需指定它们具体的类 |
| 原型 | 用原型实例指定创建对象的类型，并通过拷贝这个原型来创建新的对象 |
| 单例 | 保证一个类只有一个实例，并提供一个访问它的全局访问点 |
| 建造者 | 将一个复杂类的表示与其构造相分离，使相同的构建过程能得出不同的表示 |

结构型模式（7 种）：

| 模式 | 一句话定义（速记关键字） |
| --- | --- |
| 适配器 | 将一个类的接口转换成用户希望的另一个接口，使原本不相容的接口得以协同工作（转换接口） |
| 桥接 | 将类的抽象部分和实现部分分离，使它们可以独立变化（继承树拆分） |
| 组合 | 将对象组合成树形结构表示「整体-部分」的层次，使用户对单个对象和组合对象的使用具有一致性（树形目录结构） |
| 装饰 | 动态地给一个对象添加额外职责，比派生子类更灵活（附加职责） |
| 外观 | 定义一个高层接口，为子系统中的一组接口提供一致的外观，简化子系统的使用（对外统一接口） |
| 享元 | 提供支持大量细粒度对象共享的有效方法 |
| 代理 | 为其他对象提供一种代理以控制这个对象的访问 |

行为型模式（11 种）：

| 模式 | 一句话定义（速记关键字） |
| --- | --- |
| 职责链 | 给多个对象处理请求的机会，将接收对象链接起来在链中传递请求，直到有一个对象处理（传递职责） |
| 命令 | 将一个请求封装为对象，可用不同请求对客户参数化、将请求排队或记录日志、支持可撤销的操作（日志记录、可撤销） |
| 解释器 | 给定一种语言，定义它的文法表示，并定义一个解释器根据文法解释语言中的句子 |
| 迭代器 | 提供一种方法顺序访问一个聚合对象中的各个元素，而不暴露该对象的内部表示 |
| 中介者 | 用一个中介对象封装一系列对象交互，使各对象不需显式相互调用（不直接引用） |
| 备忘录 | 在不破坏封装性的前提下捕获并保存一个对象的内部状态，以便以后将对象恢复到原先状态 |
| 观察者 | 定义对象间一对多的依赖关系，一个对象状态改变时所有依赖它的对象都得到通知并自动更新 |
| 状态 | 允许一个对象在其内部状态改变时改变它的行为（状态变成类） |
| 策略 | 定义一系列算法并一个个封装起来，使它们可以互相替换，从而让算法独立于使用它的用户而变化 |
| 模板方法 | 定义一个操作中的算法骨架，将一些步骤延迟到子类中，子类可不改变算法结构即可重定义特定步骤 |
| 访问者 | 表示一个作用于某对象结构中各元素的操作，使可在不改变各元素类的前提下定义作用于这些元素的新操作 |

### 设计原则 {#dp-principles}

核心结论：设计模式背后的指导思想，面试常与模式一起问「有哪些设计原则需要遵守」。

1. 单一职责原则：设计类时尽量缩小粒度，使功能明确、单一，不做多余的事（高内聚、低耦合）；单一职责下的类小而精悍，需要用结构型模式组合复用它们。
2. 开闭原则：软件实体（类、模块、函数等）应该对扩展开放、对修改关闭。关键在于做好封装、隐藏内部实现细节、开放足够的接口，让外部代码只通过接口扩展功能，不需要侵入类的内部。
3. 里氏替换原则：子类型必须能够替换掉它们的基类型而程序行为仍然正确。经典反例：基类「鸟」定义了飞行方法，企鹅、鸵鸟继承后却无法飞行——应使用接口代替继承来规避。
4. 接口隔离原则：不应该强迫一个类实现它不需要的接口，类不应对用不到的方法负责；应建立单一的小接口而非庞大接口。反例：宠物狗类实现「犬科」接口，被迫实现用不到的捕食、行走、奔跑等方法。
5. 依赖倒置原则：高层模块不应该依赖低层模块，两者都应依赖于抽象；抽象不依赖具体实现，具体实现依赖抽象。例：Java 定义了一组 JDBC 接口，由各个数据库去实现，Java 不依赖具体数据库，数据库依赖 Java。
6. 组合优于继承（组合复用原则）：优先使用组合（contains-a / 聚合 has-a）而不是继承（is-a）。继承耦合度高，基类固定、会把实现细节暴露给子类，破坏封装性，是白箱复用，且使用时要考虑里氏替换原则；组合通过成员对象接口存取，是黑箱复用，耦合低、更灵活，可在运行时动态引用与成员对象类型相同的对象。缺点是需要管理较多对象。
7. 迪米特法则（最少知识原则）：一个对象应当对其他对象有尽可能少的了解，即「不和陌生人说话」。只与「朋友圈」交流：该对象本身、方法中的参数、实例变量直接引用的对象、实例变量聚合对象中的元素、方法中创建的变量。配套要求：优先设计不变类、尽量降低类和成员的访问权限、谨慎使用 Serializable。优点是降低类之间耦合；缺点是过度使用会产生大量中介类，使设计复杂化。

### 面试一问一答速查 {#dp-qa}

Q1：手写单例设计模式。

要点：至少熟练写出饿汉式、双重检查锁懒汉式、静态内部类、枚举中的一种，并能说明线程安全的保障方式。双重检查锁写法：

```java
public class Singleton {
    private static volatile Singleton instance;   // volatile 禁止指令重排
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

饿汉式要点：`private static final Singleton instance = new Singleton();` 类加载时即创建；静态内部类要点：私有静态内部类持有 `static final` 实例，`getInstance()` 返回 `SingletonHolder.instance`；枚举要点：单元素枚举 `INSTANCE`，天然防反射与反序列化。

Q2：你在实际开发中用过哪些设计模式？单例模式（确保某类只有一个实例，用在数据库连接、日志管理等场景）、工厂模式（封装对象创建过程，用在创建复杂对象、按条件选择实现类时）、观察者模式（实现一对多依赖，用在用户界面与数据模型的通信、事件处理等场景）。

Q3：设计模式了解吗？有哪些设计原则需要遵守？

答单一职责、开闭、里氏替换、接口隔离、依赖倒置、组合优于继承、迪米特法则七项，并各用一句话解释（见设计原则一节）。

Q4：说一说你了解的工厂模式。

工厂模式提供了一种创建对象的接口，由子类决定实例化的类是哪一个；可将复杂的对象创建过程封装在具体工厂类中，客户端只需关心使用工厂接口创建产品。适用于需要将对象创建过程解耦，或系统中存在多个产品族、产品等级结构需要统一管理的情况。

Q5：说一说你了解的观察者模式。

定义了一对多的依赖关系，让多个观察者对象同时监听某一个主题对象，主题状态变化时通知所有观察者自动更新。经典示例是气象站：测量温度、湿度、气压，数据变化时通知观察者（如显示屏 Display、日志记录器 Logger）更新；主题接口提供 addObserver、removeObserver、notifyObservers 方法，观察者接口提供 update 方法。

Q6：代理模式和适配器模式有什么区别？

两者都属于结构型设计模式，区别在三点：

| 维度 | 代理模式 | 适配器模式 |
| --- | --- | --- |
| 目的 | 控制对对象的访问，可添加额外操作而不改变原始对象结构 | 使原本因接口不兼容而不能一起工作的类可以一起工作 |
| 角色 | 抽象主题、真实主题、代理 | 目标接口、适配器、被适配者 |
| 应用场景 | 控制对象访问、延迟加载、权限控制 | 解决两个已有接口不兼容的对接问题 |

## 计算机系统与 Linux {#csys}

> 计算机体系结构内容较难、考察较少，仅做了解即可；重点关注 Linux 相关的面试题。

### 字符编码 {#csys-encoding}

核心结论：字符与二进制通过「字符集对照表」这个中间层绑定，Unicode 解决统一编号问题，UTF-8（可变长度编码）解决存储问题。

基本概念：

- 一个字节 8 位，不考虑正负可表示 256 个数，两个字节可表示 65536 个数；对字符的表示，套用「计算机科学领域的任何问题都可以通过增加一个间接的中间层来解决」——在字符和二进制编码之间嵌套一个数字编号实现绑定；
- 字符集：收录很多字符并一一编号得到的对照表；二进制到字符称为解码，字符到二进制称为编码；
- 乱码根源：从 ASCII（英文、控制符号）到 GB2312（中文）存在很多字符集，同一个二进制在不同字符集中对应的字符不同，同一文件用不同字符集解码结果就不同；Unicode 就是覆盖所有字符、提供唯一编码的统一字符集。

Unicode 的存储问题——固定长度编码与可变长度编码：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定长度编码 | 不管编号大小，统一按最长位数编码，位数不够高位补零 | 高效，编码、解码快速 | 浪费内存；编码越大跨度越大，定长造成的浪费越显著 |
| 可变长度编码 | 小编号少占用字节，大编号多占字节 | 节省空间 | 如何划分边界是个问题 |

可变长度编码的边界方案：采用类似 IPv4 分类编址的形式，在二进制中占用几位作为长度标识——这就是我们熟知的 UTF-8 编码，也是 Go 语言默认的编码方式。

### 冯诺依曼模型 {#csys-von}

核心结论：冯诺依曼模型由内存、CPU、总线、输入设备、输出设备五大部件组成；理解各部件职责与程序执行的四级流水线是核心。

内存：

- 从 0 开始编号，最小存储单位是字节（byte）；
- 处理器执行程序时，内存主要存放程序指令以及数据；
- 内存和处理器之间通过总线传递数据；总线贯穿整个计算机系统，负责将信息从一个部件传递到另一个部件。

CPU：

- 位宽：一次能处理多少字节的数据。32 位 CPU 一次可计算 4 个字节，64 位一次 8 个字节；位宽越大可计算的数值越大（例如 32 位 CPU 能计算的最大整数是 4294967295）；
- 内部组件：控制单元（控制 CPU 工作）、逻辑运算单元（负责计算）、寄存器（计算速度快，可理解为临时存放数据的空间）；
- 寄存器工作方式：计算 a + b 时，处理器从内存读 a、b 分别暂存到寄存器 X、Y（会覆盖原值），ALU（算术逻辑单元）复制两个寄存器中的数值完成运算，结果存回寄存器；
- 常见寄存器类型：通用寄存器（放运算数据）、程序计数器 PC（存放 CPU 下一条要执行指令的内存地址）、指令寄存器（存放指令本身，取指后放入）；PC 实质是一个字大小的存储区域（32 位机器 4 字节、64 位机器 8 字节），从系统上电到断电，处理器不断执行 PC 指向的指令并更新 PC 指向下一条指令（与刚执行的不一定相邻）。

总线（3 种）：

- 地址总线：指定 CPU 将要操作的内存地址；
- 数据总线：读写内存的数据；
- 控制总线：发送和接收信号（如中断、设备复位），CPU 收到信号后进行响应；
- CPU 读写内存数据一般需要两条总线：先通过地址总线指定内存地址，再通过数据总线传输数据。

程序执行过程：现代大多数 CPU 使用流水线方式执行指令，一条指令通常分为 4 个阶段（4 级流水线）：

1. 取指令：控制单元向地址总线发送 PC 中的地址，从内存找到待执行指令，经数据总线传入 CPU 的指令寄存器，同时自动更新 PC 指向下一条待执行指令的地址；
2. 译指（分析指令）：CPU 分析指令寄存器中的指令，确定类型和参数——计算类型交给逻辑运算单元运算，存储类型交由控制单元执行；
3. 执行指令：根据译指结果，把指令交给 CPU 中相应的组件（逻辑运算单元/控制单元）执行；
4. 数据回写：CPU 将计算结果存回寄存器，或将寄存器的值存入内存。

各阶段的负责组件：取指令、译指令由控制器进行；指令执行中，算术操作、逻辑操作、数据传输、条件分支由逻辑运算单元（运算器）完成，跳转语句由控制器（控制单元）完成。

输入/输出设备：计算机系统还包含键盘、鼠标、显示器、磁盘等各种输入输出设备。控制器与适配器的主要区别在于封装方式，功能都是在 I/O 设备与 I/O 总线之间传递数据。

### 编译系统如何工作 {#csys-compile}

核心结论：理解编译系统有三大价值（优化性能、理解链接错误、避免安全漏洞）；hello 程序的运行展示了数据在磁盘、内存、CPU、I/O 设备间的完整搬运过程。

为什么要理解编译系统：

1. 优化程序性能：例如 switch 语句是不是比一连串 if-else 高效得多？函数调用的开销有多大？while 循环比 for 循环更高效吗？
2. 理解链接过程中出现的错误：例如静态变量和全局变量的区别是什么？静态库和动态库的区别是什么？
3. 避免安全漏洞：缓冲区溢出（buffer overflow）是导致互联网安全漏洞的主要原因；要避免写出有漏洞的代码，第一步是理解数据和控制信息在程序栈上如何存储，了解不严谨不规范的书写方式会引起什么后果。

运行 hello 程序：

- hello.c 经编译系统得到可执行目标文件 hello，存放在系统磁盘上；在 Linux 上打开 shell 输入文件名即可运行（`linux> ./hello`）；
- shell 是一个命令解释程序，输出提示符等待命令行输入后执行该命令；若命令行第一个单词不是内置的 shell 命令，shell 就假设这是一个可执行文件的名字，对该文件进行加载并运行；
- shell 加载并运行 hello 后，屏幕显示 hello, world，程序运行结束退出，shell 继续等待下一个命令。

程序执行流程：

1. 通过键盘输入 "./hello" 字符串，shell 程序将输入的字符逐一读入寄存器，处理器把该字符串放入内存；
2. 按下回车键后，shell 得知命令输入完成，执行一系列指令加载可执行文件 hello，将 hello 中的数据和代码从磁盘复制到内存；复制过程利用 DMA（Direct Memory Access）技术，数据可以不经过处理器、从磁盘直接到达内存；
3. 代码和数据加载到内存后，处理器开始执行 main 函数中的代码（本例只有一个打印功能）；CPU 将 "hello, world\n" 字符串从内存复制到寄存器文件，再从寄存器文件复制到显示设备，最终显示在屏幕上。

启示：即使执行如此简单的程序，数据信息也需要在磁盘、内存、处理器以及 I/O 设备之间搬运；数据搬运需要花费时间，缩短信息搬运所花费的时间是系统设计人员的主要任务之一。

### 如何设计一个秒杀系统 {#sd-seckill}

核心结论：秒杀的本质是「瞬时洪峰 + 极少成功请求」，设计核心是把请求尽量拦截在上游、降低下游压力，让最脆弱的数据库只承担能力范围内的请求。

场景特点：访问请求数量远远大于库存数量，只有少部分用户能秒杀成功；大量用户同一时间抢购，网站瞬时访问流量激增；业务流程比较简单，一般就是下订单减库存。

架构设计理念：

- 限流：鉴于只有少部分用户能成功，限制大部分流量，只允许少部分流量进入服务后端秒杀程序；
- 削峰：抢购开始瞬间峰值很高，高峰值流量是压垮系统的重要原因，要把瞬间高流量变成一段时间平稳的流量；常用方法有前端添加一定难度的验证码、后端利用缓存和消息中间件等；
- 异步处理：秒杀是高并发系统，异步处理模式可极大提高并发量，本质上是削峰的一种实现方式；
- 内存缓存：最大瓶颈一般是数据库读写（磁盘 IO 性能低），把部分数据或业务逻辑转移到内存缓存，效率极大提升；
- 可拓展：设计成弹性可拓展的，流量来了就扩展机器（如淘宝、京东双十一会增加大量机器应对交易高峰）。

设计思路：将请求拦截在系统上游（并发量极大但成功请求极少，不在上游拦截很可能造成数据库读写锁冲突甚至死锁，最终请求超时）；利用缓存预减库存拦截掉大部分请求；用消息队列异步处理，后台业务按自己的处理能力主动拉取消息处理。

前端方案：

1. 页面静态化：活动页面上所有可以静态的元素全部静态化，尽量减少动态元素，通过 CDN 抗峰值；
2. 禁止重复提交：用户提交之后按钮置灰；
3. 用户限流：某时间段内只允许用户提交一次请求，比如 IP 限流。

后端方案：

网关层（服务端控制器层）：限制 uid（UserID）访问频率——前端拦截挡不住恶意攻击或插件，需针对同一 uid 限制访问频率。

服务层（即使每个用户只有一个请求，例如 100 万用户抢 100 台手机，服务层并发压力也至少 100 万）：

1. 把秒杀商品的主要信息及库存初始化到 Redis 缓存中；
2. 做请求合法性校验（如是否登录），非法请求直接返回错误码并提示；
3. 内存标识判断：标记为 true（秒杀已结束）则直接返回秒杀结束；
4. Redis 中用 `decr` 预减库存：减后库存量小于 0，则把内存标记置为 true，并返回秒杀结束；
5. 用 Redis 布隆过滤器判断是否已秒杀到，防止重复秒杀：布隆过滤器对「不存在的数据」的判断百分百准确，判断没秒杀过就直接放行；判断已秒杀过则再查库确认（因为它对「可能存在的数据」有误判率），确认后返回重复秒杀错误码；
6. 发送秒杀成功的 MQ 消息给相应业务端处理，同时给客户端返回「排队中」，客户端收到后自动轮询查询，直到返回秒杀成功或失败；
7. 业务端真正处理：再次校验（秒杀是否结束、库存是否充足）→ 将用户和商品 id 作为 key 存入布隆过滤器标识秒杀成功 → 真正减库存（操作数据库）→ 生成秒杀订单 → 返回秒杀成功。注意：即使请求走到业务端也可能失败（秒杀结束、库存不足、减库存失败、订单生成失败等），失败则返回秒杀结束。

进一步优化：

- 秒杀接口隐藏：用户点击秒杀按钮时，根据用户 id 生成唯一加密串存入缓存并返回客户端；后续请求携带加密串，后端校验合法性，不合法直接返回请求非法；
- 限制接口访问频率：用拦截器配合自定义注解实现，与具体业务分离、减少入侵。

数据库层（最脆弱的一层，应用设计时就应在上游把请求拦截掉，通过服务层的队列和缓存让数据库只承担「能力范围内」的请求）：

- 防止秒杀出现负数订单或订单数大于库存：真正减库存时 update 语句加上 `where 库存 > 0` 条件；
- 给秒杀订单表加上用户 id 和商品 id 联合的唯一索引，防止重复下单。

### 如何设计一个本地缓存 {#sd-local-cache}

核心结论：设计本地缓存主要考虑 8 个点——数据结构、对象上限、清除策略、过期时间、线程安全、简明接口、是否持久化、阻塞机制。

1. 数据结构：最简单直接用 Map；复杂的可像 Redis 一样提供哈希、列表、集合、有序集合等多种类型，底层使用双端链表、压缩列表、跳表等数据结构；
2. 对象上限：本地缓存内存有上限，一般指定缓存对象数量上限（如 1024），达到上限后需要用清除策略删除多余数据；
3. 清除策略：常见的有 LRU（最近最少使用）、FIFO（先进先出）、LFU（最近最不常用）、SOFT（软引用）、WEAK（弱引用）等；
4. 过期时间：一般也给每个 key 设置过期时间，到期直接删除，采用「清除策略 + 过期时间」双重保证；
5. 线程安全：Redis 用单线程处理所以不存在线程安全问题，而本地缓存往往被多线程同时访问，线程安全不容忽视，且不应该抛给使用者去保证；
6. 简明的接口：提供 get、put、remove、clear、getSize 等常用方法，让使用者使用缓存不是负担而是享受；
7. 是否持久化：不是必须的，看需求。本地缓存中 ehcache 支持持久化，Guava 不支持；分布式缓存中 Redis 支持持久化，Memcached 不支持；
8. 阻塞机制：被缓存的数据往往生成费时（调外部接口、查数据库、计算量大），若多个线程同时 get 到 null 会重复计算浪费资源，理想做法是只有一个线程执行、其他线程等待；此功能基本交给使用者处理，很少有本地缓存自带。

### 如何设计一个 RPC 框架 {#sd-rpc}

核心结论：RPC 框架设计 = 接口定义 + 通信协议 + 序列化协议 + 远程调用机制 + 服务治理（注册发现、负载均衡）+ 安全、容错与可观测性，共 10 个要点。

1. 定义 RPC 接口：定义服务接口及其方法，这是 RPC 的核心，决定客户端可以调用哪些方法；
2. 选择通信协议：如 HTTP/REST、TCP、UDP 等，不同协议有不同优劣，取决于应用需求；
3. 选择序列化协议：将数据转换为字节流以便在网络传输，常见的有 JSON、Protobuf、Thrift 等，需考虑效率、可读性和平台兼容性；
4. 实现远程调用：实现将 RPC 请求发送到远程服务并接收响应的机制，涉及网络通信、数据解析和错误处理；
5. 服务注册与发现：提供服务注册中心，使服务能动态注册和发现，可用 Zookeeper、Consul、etcd 等工具；
6. 负载均衡：确保请求在多个服务节点之间分布均匀，常见算法有轮询、随机、最小连接数等；
7. 安全性：考虑数据传输安全，可使用加密协议（如 TLS/SSL）保护通信；
8. 错误处理：设计良好的错误处理机制，包括定义错误码、异常传播和日志记录，确保客户端能得知发生了什么问题；
9. 性能优化：考虑并发性、延迟和吞吐量等性能问题，使用连接池、异步 IO 等技术优化；
10. 监控和日志：实现监控和日志记录以便及时发现问题并排查故障，集成日志系统和监控工具（如 Prometheus、Grafana 等）。
