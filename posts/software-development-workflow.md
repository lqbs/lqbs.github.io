# 软件开发流程与订单系统实战

一家电商公司用 Excel 登记多渠道订单。运营人员会漏单，仓库偶尔发错货，两名员工还可能同时卖掉最后一件商品。要开发一套订单管理系统，可以先追踪一笔订单从哪里来、由谁处理、库存何时占用、仓库以什么为准确认出库。把这些问题问清楚，才能写出可验收的需求，也能判断哪些操作应该在同一个事务里完成。

《学习软件开发流程》的 52 轮对话按顺序分为 16 章，保留了提问、讲解、答题与讲评、代码示例、表格和 PRD。综合项目通过八轮模拟访谈形成订单管理系统（OMS）的 PRD 初稿，最后完成总体架构的第一版设计。文中的公司、访谈和运行数据均为教学情境。

### 六课串起软件开发流程

| 阶段 | 订单系统的练习 | 阶段产出 |
| --- | --- | --- |

| 系统设计 | 划分订单、库存和发货职责，设计实体关系 | 架构图、模块依赖、ER 图、约束与索引 |

#### 第一课　把业务问题写成可验收的需求

从业务目标、现状流程和用户角色开始。两名员工同时从 Excel 看到库存只剩一件，这是业务问题。需求可以写成「系统必须防止同一份库存被重复占用」。验收时准备一件库存，让两笔订单同时尝试各预留一件，确认只有一笔成功。数据库事务与条件更新属于后续的实现方案。

「经常忘记发货」还需要追问订单从哪一刻开始计时、超时时限、谁接收提醒，以及通知失败怎么处理。练习把时限设为 24 小时。用 Given / When / Then 描述一个场景：订单已支付 25 小时且尚未发货，系统执行超时检查，订单被标记并通知负责人。再补上未到期、已发货和重复检查的场景，明确何时不应产生新提醒。把这些规则、角色、范围和验收标准合在一起，就形成了第一份软件需求说明书（SRS）。

#### 第二课　设计模块、数据库与约束

订单模块判断订单能否取消，并调用库存模块释放预留。库存模块负责核对预留记录、更新库存并写流水。应用服务组织完整业务操作，这样订单状态和库存变化可以在同一次提交中生效。

数据库设计从实体关系开始。一笔订单有多条明细，每条明细关联商品并记录成交时的价格快照。库存余额表回答「现在还有多少」，预留表回答「哪些订单占用了多少」，库存流水回答「谁因为什么操作改变了库存」。唯一约束要反映实际业务粒度，例如多仓库练习中，每个仓库的同一商品有独立库存记录，约束随之扩展为仓库加商品。多仓库是建模练习，综合项目把多仓库管理放在后续版本。

联合索引练习查询某个商品在指定时间之后的库存流水，并按时间倒序查看。讲评将索引顺序修正为 `(product_id, created_at)`，先限定商品，再扫描该商品的时间范围。评审时用真实查询、数据分布和执行计划检验索引选择。

#### 第三课　实现一条可以联调的业务流程

用 React 和 TypeScript 实现订单列表、详情和创建表单。FastAPI 路由处理 HTTP 请求和字段校验，应用服务组织业务操作，SQLAlchemy 数据访问层负责持久化。首轮练习串起创建、库存预留和订单查询。订单、明细、预留记录和流水要一起提交，任何一项失败就回滚。综合项目在访谈后把预留时机调整为**审核通过时**。

库存预留使用数据库原子条件更新，把可用库存检查和数量更新放进同一个操作。涉及多个 SKU 时，只要有一个无法预留，就撤销本次全部预留。取消和出库也需要考虑重复请求。业务操作标识、唯一约束和状态校验配合使用，让同一笔操作重试时只产生一次有效变更。

联调练习里，创建订单返回 HTTP 422。查看浏览器 Network 面板中的请求体和错误详情，发现表单没有提交接口要求的 `customer_id`。把必填字段、数据类型、响应结构和错误处理写入接口契约，前后端就有同一套约定可核对。

#### 第四课　用测试验证业务规则

用 pytest 检查业务规则、数据库事务和幂等，用 FastAPI TestClient 检查请求校验、权限和错误响应，用 Playwright 从浏览器验证用户能否完成订单流程。并发用例使用两个独立数据库会话同时竞争最后一件库存，核对成功次数、剩余库存和有效预留记录。再覆盖多 SKU 预留失败、重复审核、取消释放库存和重复出库，检查失败或重试之后的业务状态。

缺陷练习比较了超卖、取消后库存未释放和按钮颜色错误。前两项直接破坏库存一致性，应优先修复并回归关联流程。测试报告还应列出环境、覆盖场景、遗留缺陷及其业务影响，用这些证据判断能否发布。

#### 第五课　部署、监控和恢复

课程用 Docker Compose 组织前端、FastAPI 和 MySQL，由 Nginx 提供 HTTPS、静态文件和 API 反向代理。GitHub Actions 负责测试、构建和镜像发布，生产更新使用可追溯的版本，并验证页面、API 和核心业务流程。数据库用卷持久化，备份单独保留并演练恢复。通过日志、指标和链路追踪定位问题，可以把接口错误率、响应时间和订单失败与具体发布关联起来。

回滚练习中，新版应用既有事务缺陷，也删除了旧版依赖的数据库字段。恢复前先控制受影响的操作，确认旧应用能否在现有库结构上运行，再决定发布兼容迁移或紧急修复。若已产生错误订单或库存数据，还要对账和补偿。恢复后用实际的订单、审核和库存场景复核，并在事故复盘中记录触发原因、影响范围和后续改进。

#### 第六课　用运营数据安排下一次迭代

课程以「每周有效完成订单数」衡量核心任务完成情况，用处理时长和任务完成率解释变化，用订单错误率、库存异常率和 API 失败率观察质量。定义处理时长时，要写明样本、起止事件和统计周期，并区分订单总流转时间、人工实际用时和各环节等待时间。处理效率下降时，可以按日期、渠道、订单类型和业务阶段拆解，再从明细和用户访谈验证原因。

版本复盘练习里，订单列表加载从 5 秒降至 1.8 秒，人工筛查从 30 分钟降至 12 分钟，但满意度只有 82%，低于 90% 的目标。运营人员反馈有正常订单被误标。下一版可以先收集误报样本、核对规则和影响范围，再确定改进范围。上线后同时检查误报率、漏报率和人工复核时间，判断新规则是否减少了工作量。

### 八轮访谈形成订单系统 PRD

综合项目从运营、仓库和管理者的实际工作切入。运营人员导入订单并处理数据异常，主管审核或审批，仓库负责拣货复核和出库，管理者查看经营情况。每轮模拟访谈都记录业务规则、候选需求、异常路径和待确认事项。

| 轮次 | 调研主题 | 纳入需求初稿的结论 |
| --- | --- | --- |
| 1 | 订单来源与接入 | 识别电商平台、内部系统和线下订单。接入方式包括 Excel、API 和人工录入，首期以 Excel 导入为入口。 |
| 2 | 创建、校验与商品匹配 | 保留导入原始数据与批次。通过关键校验和 SKU 匹配后创建正式订单。暂用渠道与外部订单编号识别重复，唯一范围须用真实渠道样本核对。 |
| 3 | 金额、优惠、退款与修正 | 区分买家实付、商家结算、运费及优惠承担方，保留成交快照与修改记录。退款状态和退货入库分别处理，完整退款流程排到后续。 |
| 4 | 审核与库存预留 | 授权人员审核，审核通过时尝试预留库存。多 SKU 一起预留，库存不足进入缺货处理，库存变更保留流水。 |
| 5 | 仓库履约与发货 | 预留成功后生成拣货任务，复核通过后打包。创建物流单号、实际出库和承运商揽收分别记录，以实际出库确认触发扣减。 |
| 6 | 取消、地址修改与异常 | 取消与地址修改受订单状态和权限约束。拣货中的订单先停拣并确认归位，已出库订单走拦截或售后。异常记录类型、责任人、进度与处理结果。 |
| 7 | 运营指标、报表与权限 | 为及时发货率、库存准确率和异常率写明口径、来源、周期与预警规则。按角色控制操作权限、数据范围和敏感字段。 |
| 8 | MVP、追踪矩阵与 PRD | 用 MoSCoW 排优先级，以导入到出库的闭环确定首期范围，形成 PRD V1.0-Draft 和需求追踪矩阵。 |

#### MVP 覆盖从导入到出库

首期主流程是 **Excel 导入 → 数据校验与商品匹配 → 创建订单 → 审核与库存预留 → 拣货、复核与打包 → 出库确认 → 记录物流单号**。查询、人工修正、取消、库存流水、异常处理和角色权限支撑这条流程。库存流水需要回答哪笔订单预留了多少、何时释放、实际扣减由哪次出库触发。

MoSCoW 把需求分为 Must、Should、Could 和 Won’t。首期 Must 包含 Excel 导入、重复识别、SKU 映射、审核、库存与仓库履约。部分发货、物流轨迹自动同步、完整退款与定期报表属于后续候选。多平台 API 自动接入和高级经营分析也留待后续版本。部分发货一旦纳入范围，每次出库都要记录对应明细和数量，未出库部分继续保留预留。其优先级和真实操作规则仍待业务确认。

库存数量可以用一笔订单手算。实际库存 100 件，已预留 30 件，可用库存 70 件。新订单审核时预留 8 件，实际库存仍为 100 件，预留变为 38 件，可用为 62 件。若这 8 件全部出库，实际库存变为 92 件，预留回到 30 件，可用仍是 62 件。若在出库前成功取消，则释放该订单的 8 件预留，可用库存恢复到 70 件。

#### 从需求追踪到验收

需求追踪矩阵（RTM）把业务问题、PRD 条目、设计、开发任务和验收用例串起来。下面沿用 PRD 初稿的编号，列出几条可以直接验证的场景。

| PRD 条目 | 验收用例 | 预期结果 |
| --- | --- | --- |
| FR-001 订单导入 | TC-003 重复上传同一订单 | 正式订单只创建一次，导入批次记录可追溯。 |
| FR-004 订单审核 | TC-008 重复审核 | 只产生一次有效库存预留。 |
| FR-005 库存管理 | TC-007 两笔订单争抢同一份库存 | 成功预留量不超过可用库存。 |
| FR-007 发货管理 | TC-011 重复提交发货 | 同一出库记录只扣减一次库存。 |
| FR-008 订单取消 | TC-009 取消未发货订单 | 释放对应的未出库预留，记录操作人和原因。 |

这份 PRD 来自模拟调研，状态为待评审。正式评审前，需要请运营核对 Excel 样本、渠道订单编号唯一范围和金额口径，请仓库确认出库凭证、部分发货与归位流程，并与项目负责人确认取消审批规则、MVP 范围和上线目标。并发量、导入规模和响应时间目标也要以真实业务数据为依据。

### 从 PRD 走到模块化单体

综合项目的第一版方案是 **React + TypeScript 前端、一个 FastAPI 应用、一个 MySQL 业务库**，用 SQLAlchemy 访问数据、Alembic 管理迁移，按需要引入 Redis 和 Celery。模块化单体把订单、商品、库存、仓库、物流、用户与权限、异常管理和经营分析放在同一个后端应用里部署，各模块有清晰的职责和业务接口。微服务允许模块独立部署和扩容，也会增加跨服务通信、数据一致性和运维成本。案例当前的开发规模与库存事务要求支持先采用模块化单体，日后再根据独立扩容或维护需求评估拆分。

#### 模块接口和事务边界

接口层处理输入、身份和权限。应用服务协调一次业务操作，领域层维护状态流转和库存规则，基础设施层提供数据库、文件存储和外部接口。订单模块通过库存模块暴露的接口申请预留，库存模块维护库存余额、预留和流水。仓库模块管理实际履约，物流模块跟踪发货和运输状态，经营分析读取业务数据。

以审核为例，订单应用服务在本地事务中锁定订单并检查状态，调用库存模块预留各 SKU，再更新订单状态并记录审核与库存流水。参与模块沿用该事务，由应用服务统一提交。若任一 SKU 预留失败，撤销本次全部预留，再按缺货规则记录处理结果。重复审核和审核与取消之间的竞争，都需要在状态机与并发测试中验证。

#### 对话进行到哪里

最后一轮形成了总体架构草案，末尾的架构测验尚未作答。综合项目下一课原定细化模块职责和依赖关系，之后还要设计 ER 图、状态机和 API，再进入编码、测试和部署。
